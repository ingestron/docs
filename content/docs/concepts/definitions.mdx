A project is a folder of YAML definitions. `project.yaml` identifies the project,
selects environments and lists the files to load. A definition only participates
when an `imports` pattern includes it.

The standard supplies policy across those tables. Packs resolve the required
actions and generate platform resources. A transform can read project tables
to produce another table when the selected packs support it.

## What each file owns

| Document       | Responsibility                                                                 |
| -------------- | ------------------------------------------------------------------------------ |
| `project.yaml` | Project ID, imports, shared values and environment overrides                   |
| `Standard`     | Packs, allowed methods, defaults, naming and fixed policy                      |
| `Platform`     | Shared infrastructure and operational configuration supported by the packs     |
| `Connection`   | Source connector, reachability and access settings                             |
| `Flow`         | Source objects, destination table definitions and ingestion choices            |
| `DataContract` | Expected columns, logical types, keys and other supported contract information |
| `Transform`    | Declared input tables and code that produces another table                     |
| `DataProduct`  | Who owns a set of published tables, their purpose and support, in ODPS         |

A data product is an Open Data Product Standard file, usually in `products/`,
whose output ports name the contracts it publishes; see
[Define a data product](/docs/how-to/define-a-data-product). A project needs
exactly one Standard and may have one Platform. It does not need
one Platform document per provider: method settings share that document under
their method IDs. Capabilities still depend on the selected packs.

## Link definitions by ID

A flow's `source` names a Connection ID. Each table's `contract` names its data
contract; `object` identifies the source object. These are different identities.
A transform's `inputs` names tables produced by the project.

Here `shop` is the source connection, `orders` is the project table, and

## IDs and names

A project's IDs link its documents; the names a pack generates identify
resources on a platform. Each comes from its own place, so changing one does
not rename the others.

| Identity                   | Where it comes from                                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Project and definition IDs | `id` in the project or document                                                                              |
| Project table name         | A flow table's key or a transform's `id`                                                                     |
| Contract link              | The table's `contract`, identifying a data contract                                                          |
| Platform resource name     | The pack's default patterns, or `naming` in the standard or platform; for ADF, the method's `resource_names` |

[Name tables and resources](/docs/how-to/name-things-your-way) shows how the
platform names are made.

## Keep reusable values out of individual definitions

Read values from `project.yaml` with `${values.…}` and name credentials with
`${secret:…}` where the connector accepts secret references. See
[YAML references and placeholders](/docs/concepts/yaml-references) for the syntax,
file includes and escaping rules.

To see these documents work together, follow
[Run your first project on your laptop](/docs/start/first-project). For a deeper
explanation of method selection, read
