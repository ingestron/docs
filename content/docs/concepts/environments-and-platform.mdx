---
title: Environments and the platform document
description: Reuse one project's definitions with different values and shared infrastructure settings.
---

An environment gives the same project another set of values, such as `dev`,
`test` and `prod`. It does not change the tools or create anything in the
cloud. Every environment is generated together, into one set of files per
platform that a deployment pipeline promotes from one environment to the next.

## Values that differ

Put shared values in `project.yaml` and override only the values that differ
under each environment. Mappings merge by key; scalar values and lists replace
the earlier value.

This concrete example uses Databricks workspace and storage values. The same
value mechanism also works for connector endpoints, landing paths and names

Read the selected values with `${values.…}` and the environment name with
`${environment.name}`. The [YAML syntax guide](/docs/concepts/yaml-references)
explains types, references and file includes.

## Shared platform configuration

The optional `Platform` document holds shared operational and infrastructure
configuration. Use `settings.<method>` for method-specific infrastructure;
put access settings in the Connection and table-specific reading choices in
the Flow. The [settings precedence](/docs/concepts/settings) determines overrides.

<Example name="connection-first-adf" file="platform.yaml" />

This example supplies landing storage, Key Vault, runtime and resource names for
an ADF method. A project still has one Platform document when it uses several
packs. The method reference says which fields it consumes and what must already
exist before deployment.

`schedule`, `tags` and `alerts` sit at the top of the platform, for every
pack that runs jobs: when they run, how they are tagged, and who is told when
a run fails. What only one platform reads goes in that pack's own section,
under its id: the Databricks workspace, identity, compute, permissions and
`manage` switches are under `databricks:`, and Synapse's grants switch under
`synapse:`. A section for a pack the standard
does not name is [`UNKNOWN_PACK`](/docs/reference/errors#UNKNOWN_PACK). See
[the `databricks:` section](/docs/reference/packs/databricks#platform)
and [ADF runtime and Key Vault](/docs/platforms/adf#runtime-and-key-vault) for
their effects. The platform's `accept` list holds the warnings the platform
team has decided to live with, each with its reason; see
[Accept a warning](/docs/how-to/accept-a-warning). Its `principals` say which
user, group or service principal each contract role is, often per environment
through a value; see
[Grant access, mask columns and filter rows](/docs/how-to/grant-access#roles).

## One set of files for every environment [#one-set-of-files]

<OldAnchor id="separate-generated-output" />

Ingestron fills in each environment's values when it generates, then writes
each platform's files once for every environment: a value that differs between
environments becomes a parameter of the bundle, the factory or the Synapse
script, set for each environment, and everything else is written once. So
environments may differ only in values; a table or resource present in some
environments only is
[`ENVIRONMENTS_DIFFER`](/docs/reference/errors#ENVIRONMENTS_DIFFER).
[Generated files and ownership](/docs/concepts/generated-files#where-the-files-go)
shows where each platform's files go.

Some values are not known until deployment, such as a storage account each
stage of your pipeline supplies. Write them as `${envvar:NAME}`: for
Databricks, Data Factory and Synapse they become values the deploying pipeline
supplies, not values read when generating; see
[Read an environment variable](/docs/concepts/yaml-references#read-an-environment-variable).
Generating never reads a secret or tests the deployed infrastructure.

Use [Add an environment](/docs/how-to/add-an-environment) to create another
environment and compare the resolved choices, and
[Deploy through environments](/docs/how-to/deploy-through-environments) to
deploy them in turn.
