---
title: "What a data contract does"
description: "Describe the columns you intend to publish, then review them."
---

A data contract describes the shape and meaning of a dataset. Ingestron uses ODCS
files for contracts. In the GitHub example, the contract selects a required integer
`id` and a required string `title`.

Discovery tells you what a source exposes. A contract tells Ingestron what you
intend to use. The review connects the two before extraction. It is a checkpoint
for the source identity, stream and projected fields, not a substitute for deciding
whether those fields mean the right thing for your users.

## Draft and review are different steps

The contract walkthrough drafts a file from imported metadata. You still need to
review it. The execution walkthrough includes a contract in its project and asks
you to inspect the generated review before approving the run.

A file can pass schema validation and still describe the wrong repository or
business field. Read it, keep it in version control and review changes with the
people who use the resulting data.

## Owners and status

A contract can name the people responsible for the data product with the ODCS
`team` section, and its lifecycle with `status`:

```yaml
status: active
team:
  name: Sales data
  members:
    - username: ana@example.com
      role: Data owner
    - username: ben@example.com
      role: Data steward
```

`ingestron check` lists each data product with its status and owner. A contract
with `status: active` must name at least one member whose role contains `owner`;
drafts do not. Members with a past `dateOut` no longer count. Sign-off for a
contract change is the review of that change in Git.

## Quality rules

Contracts can record ODCS `quality` rules on a column, a table or the whole
contract. Library rules use one of `nullValues`, `missingValues`,
`invalidValues`, `duplicateValues` or `rowCount` with one comparison such as
`mustBe` or `mustBeGreaterThan`:

```yaml
properties:
  - name: status
    logicalType: string
    physicalType: STRING
    quality:
      - id: status-valid
        metric: invalidValues
        arguments:
          validValues: [open, closed]
        mustBe: 0
        severity: error
```

`severity: error` means the load should fail when the rule fails; any other
severity only warns. A column with `primaryKey: true` also implies not-null and
unique rules unless you write them yourself. `text` rules are documentation only.
A malformed rule fails `check`.

SQL rules return one number and use the same comparisons. Write the query in
the target platform's dialect and use `${table}` for the table and, on a column
rule, `${column}` for the column:

```yaml
quality:
  - id: no-negative-amounts
    type: sql
    query: SELECT COUNT(*) FROM ${table} WHERE amount < 0
    mustBe: 0
    severity: error
```

Engine rules (`type: custom`) name an `engine` and pass its `implementation`
through; only providers that support that engine enforce them. `check` validates
the shape of SQL offline (one read-only statement, no comments); the platform
compiles it when the check runs.

Each provider and connector declares how it enforces each rule: while loading,
after loading, or not at all. `check` and `build` report this for every flow, for example
`Quality rules: 4 (0 at load, 0 after load, 4 not enforced by the target)`, and
the build writes the full list to `ingestron-project.json`. An error-severity
rule that the target cannot enforce stops the build. To accept that and only
report it, set:

```yaml
defaults:
  quality:
    unsupported: report
```

Rules implied by keys are reported but never stop the build.

### Local snapshots

The local connectors (Files 1.3.0, SQL Server 1.3.0, Azure Blob 1.2.0 and GitHub
1.34.0) check library rules and key rules on the staged snapshot before it is
committed, so `check` counts them as enforced at load. If an error-severity rule
fails, the run stops and nothing is committed:

```text
Error: Contract quality rules failed; nothing was committed: orders.key-unique (2).
Fix the source data or review the rule severity, then retry with the same run ID.
```

Other rules are recorded in the snapshot receipt, and `ingestron run status`
shows them, for example `Quality rules: 3 checked before commit; 1 warning(s):
orders-volume.` Messages name rules and counts, never row values. Invalid rows are
not removed or quarantined: a failed run is fixed at the source and retried. SQL
and engine rules are not checked locally.

### Databricks and ADF

The [Databricks](/docs/reference/databricks#contract-quality-rules) and
[ADF](/docs/reference/adf#contract-quality-rules) providers generate native
checks, and what they enforce depends on the ingestion standard. `check` reports
it per flow, so the same contract can be enforced at load on a snapshot and
reported as not enforced on a streaming table.
