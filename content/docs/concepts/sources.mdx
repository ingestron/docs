A connection reads one kind of source, such as SQL Server, Azure Blob Storage or
GitHub. There can be more than one way to read it:

| Route        | What reads the source                                                    |
| ------------ | ------------------------------------------------------------------------ |
| **Portable** | An Ingestron connector package, run by the provider on its compute       |
| **Native**   | The platform's own connector, such as ADF Copy or Databricks Auto Loader |

Native connectors in the ADF and Databricks providers are free to use with
Ingestron; the platform bills its own usage as it normally would.

## Reading the routes in `check`

For each flow that reads a connection, `check` prints the route it uses and, when
another configured provider can read the same source natively, that alternative:

```text
Sources:
  sales: erp (sql-server) portable sql-server@1.5.0 on local [verified, no extra cost]
    Also available: native on adf via snapshot-land@v1 [preview, included in platform pricing]
```

Nothing switches routes for you. A native alternative uses that provider's
ingestion standard, so moving to it is a project change you review. Routes that a
platform bills separately are listed with `--json` but never suggested. When the
route you chose is billed separately and another configured platform can land
the same source, `check` suggests a bridge instead (below).

## Bridges

Sometimes the platform that processes the data cannot reach the source, for
example Databricks and a SQL Server on a private network that only a
self-hosted integration runtime reaches. A bridge lets ADF read the source and
hand each snapshot to Databricks:

```yaml
connections:
  erp:
    kind: sql-server
    route: bridge
    binding: erp_adf # ADF's SQL Server linked service binding
    bridge:
      provider: landing # ADF configuration that reads and lands the source
      publisher: publisher # Databricks configuration that publishes deliveries
      landing:
        { linkedService: landing_adls, fileSystem: landing, path: retail }
      handover: files # storage binding both platforms read
      publication:
        credential:
          {
            secretScope: retail_storage_dev,
            tenantIdKey: tenant-id,
            clientIdKey: client-id,
            clientSecretKey: client-secret,
          }
```

The flow stays an ordinary Databricks `snapshot-with-history@v1` flow with the
connection and one `source: {schema, table}` per table. Ingestron expands it
into three flows, each generated by its own provider: `<flow>_land` (ADF Copy),
`<flow>_publish` (a Databricks job that verifies each landed snapshot and
appends it to a delivery index) and the flow itself (Lakeflow history). `check`
shows it as one route:

```text
  sales: erp (sql-server) bridge: lands on landing, ingests on processing via snapshot-land@v1 → snapshot-publication@v1 → snapshot-with-history@v1 [preview, included in platform pricing]
```

Build with `ingestron build --delivery`. See the
[bridge example](https://github.com/ingestron/provider-adf/tree/main/examples/bridge-to-databricks).
Generation is offline; running it needs the existing factory, linked services,
storage, workspace and permissions.

## Reference records

Every route carries the same record, so you can compare them in one format.
`ingestron check --json` includes it in full.

| Field          | Meaning                                                                                         |
| -------------- | ----------------------------------------------------------------------------------------------- |
| `docs`         | Where the connector or API is documented                                                        |
| `vendorStatus` | The platform's own status: GA, preview or beta; `not-applicable` for Ingestron connectors       |
| `licence`      | Licence of the connector and anything it wraps, or the platform's terms                         |
| `cost`         | `none`, `included` in platform pricing, or `separately-billed`, with a pricing link and note    |
| `access`       | What you need: nothing, free access, a free tier, a trial, a subscription or a platform service |
| `auth`         | Supported sign-in methods                                                                       |
| `network`      | Where the source can be: local, public, private network or on-premises                          |
| `maturity`     | How far Ingestron has tested the route (below)                                                  |
| `verified`     | When the record was last checked; `check` notes records older than 180 days                     |

## Maturity

| Level         | Meaning                                                                                                       |
| ------------- | ------------------------------------------------------------------------------------------------------------- |
| **Preview**   | Tested against mocks, synthetic data or offline generation only; not yet against the live service or platform |
| **Verified**  | Also tested against the real service, using a free, trial or test account                                     |
| **Qualified** | Also run natively on the target platform, or used by an independent user                                      |

The files, GitHub, SQL Server, PostgreSQL, MySQL, Oracle, S3 and SFTP connectors
are verified (against real engines and servers in local containers). Azure Blob,
Google Cloud Storage, Stripe, Salesforce, HubSpot, Jira, SharePoint and OneDrive,
every native ADF and Databricks route, and bridges are in preview.

## Discovering fields

Every route can draft contracts from the source before you write them; see
[discover a source](/docs/guides/discover).

## Requiring capabilities

A flow can state what its source must support. `check` stops if the route cannot
supply it:

```yaml
ingestion:
  connection: erp
  requires: [incremental]
```

Capabilities are `snapshot`, `incremental`, `cdc`, `deletes` and `discovery`.
Current Ingestron connectors read reviewed full snapshots with discovery.
