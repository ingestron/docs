---
title: Standards, packs and methods
description: Separate project policy from platform capabilities and method selection.
---

A **standard** is the project's policy. A **pack** implements capabilities and
builds platform files. A **method** performs one action for a table. Choosing a
pack does not mean every action must run on that platform.

| Action      | Responsibility                                                                 |
| ----------- | ------------------------------------------------------------------------------ |
| `ingest`    | Read a source, producing files or a table                                      |
| `transform` | Compute a result from declared project tables                                  |
| `store`     | Keep the preceding result using a supported storage method                     |
| `serve`     | Make a table's data available somewhere else, such as SQL views over its files |

Methods declare what they accept and produce. Consecutive methods must be
compatible; listing two packs does not make every combination valid. If ingestion
already produces a table, that flow has no separate store step. A serve step is
optional: it follows a table's last step only when something chooses a serve
method, such as `synapse-serve` for a table another pack stores.

## One policy across the project

The standard names its packs, limits methods with `allowed`, supplies defaults
and can fix settings that definitions may not change. Use
[Set your organisation's standard](/docs/how-to/configure-a-standard) to write that policy,
and [Which setting wins](/docs/concepts/settings) to understand overrides.

## Intent: what to keep, not how [#intent]

Besides choosing methods, a standard can say how data is loaded, kept and run
in words that belong to no platform: load only new files, keep the latest row
per key, add a column saying when a row was loaded, try a failed run twice
more. That is **intent**. Each pack turns it into its own platform's terms:
`history: latest` is AUTO CDC on Databricks and `INSERT OR REPLACE` on DuckDB.

Methods are chosen first, as below; intent changes what a chosen method
writes, never which method is chosen, unless a `when` rule matches on it. A
value the chosen pack does not apply is a
[`NOT_APPLIED`](/docs/reference/errors#NOT_APPLIED) warning, with the pack's
reason, so a standard never promises what a project does not build. Each pack's
reference page lists what it does with every value, and the
[intent reference](/docs/reference/intent) lists the words, where each can be
written and which value wins.

A [published standard](/docs/how-to/choose-a-published-standard) is a
standard of this kind for one platform, with a small project that builds.

## How a method is chosen

For each action, the first applicable choice wins:

1. An explicit `uses` in the definition, provided the standard allows it.
2. A matching `when` rule in the standard.
3. A matching rule in a pack. An ingest rule is skipped if it cannot read the
   connector or reachability declared by the connection.
4. The standard's `default`, then the applicable pack default.

Rules can match connector, connectivity, layer and the preceding action's output.
An explicit unsupported choice is reported as a problem; it does not silently
switch to another platform.

An environment in `project.yaml` can name `runs-on`, one of the standard's
packs, to run the tables on that pack alone, such as `runs-on: duckdb` on a
laptop. There, an ingest that lands files with another pack is replaced by the
named pack's method that reads those landed files, and a serve step from
another pack is left out. A store or transform that belongs to another pack is
a [`RUNS_ON`](/docs/reference/errors#RUNS_ON) error, and a table another pack ingests straight into a table is
left out with a warning. [Run a cloud project locally](/docs/platforms/duckdb#run-a-cloud-project-locally)
shows it.

The connection-first builder writes an explicit `ingest.uses` for the chosen
route. You can inspect that choice in the flow without learning the builder's
interface. [Reachability](/docs/start/choose-a-route#reachability) explains the `connectivity` values.

## Combine packs when their actions fit

The first pack in the standard supplies project defaults such as naming,
layers and column types. Rules are considered in pack order. The order is
precedence, not the order things run: list the pack that stores or serves the
tables first, such as `[duckdb@2, adf@2]`, even though ADF copies first. Each resolved action records the
pack that owns it, and each pack generates its own output folder when several
packs are selected.

For the ADF-to-Databricks route, copying produces landing files and the store
method reads them into tables. The ADF pack supplies no store method: alone, it
ends at the landed files (`store: none`), and with Synapse or DuckDB those packs
serve or store them. Other combinations require implemented, compatible methods;
they cannot be enabled by substituting a provider name.

## Keep settings with their owner

Method settings are keyed by method ID: configuring one method does not configure
another. Standards hold shared defaults and policy, Platform holds shared
infrastructure, and flows or tables hold local choices. A missing required
setting is reported before generation, with its expected location.

Use [Plan, apply and review](/docs/how-to/plan-and-generate) to inspect the result.
Tools can explain method selection and setting origins without changing the
underlying definitions.
