title: "GitHub connector"
description: "Source support and limits for connector 1.33.0."
---

The connector uses Meltano's GitHub issue reader with an Ingestron REST repository
lookup and explicit authentication. It runs through the local provider. The qualified walkthrough selects the `issues` stream and projects
`id` as int64 and `title` as string.

```sh
ingestron plugin install github@1.33.0
```

| Setting          | Value in the example                                                   |
| ---------------- | ---------------------------------------------------------------------- |
| `repositories`   | An array containing an authorised `owner/repository`.                  |
| `authentication` | `anonymous` in the public example; `token` for authenticated access.   |
| `auth_token`     | Omitted for anonymous access; a `$secret.env` reference in token mode. |
| Selected stream  | `issues`.                                                              |
| Output           | A full Parquet snapshot with the reviewed projection.                  |

## Behaviour to account for

- The issues API can include pull-request entries. This connector does not filter them out.
- A snapshot is not a transactionally consistent view or a complete issue event history.
- Retries of incomplete work do not restore an incremental cursor.
- API limits, source permissions and the configured flow timeout can stop a run.
- Discovery includes the parent repository schema; only `issues` is accepted as output.
- Other projections have not been individually qualified by this walkthrough.
- GitHub Enterprise and GitHub App authentication are not supported here.

The runtime bounds metadata/catalogue input to 2 MB and individual upstream messages
to 16 MB. Large fields can fail even when a repository has few issues. There is no
published throughput guarantee; use a small source first and measure your own workload.

Use [the tutorial](/docs/tutorials/github-to-parquet) for the complete procedure and
[the source repository](https://github.com/ingestron/connectors) for implementation
and upstream licence details.

## Use a token

Anonymous reads work for public repositories. GitHub allows 60 unauthenticated
REST requests per hour per originating IP. See [GitHub's rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api).
Use a token for private repositories or a higher request allowance.

Create a fine-grained personal access token with the intended resource owner,
selected repository access and read-only Issues permission. Metadata read access
is included by GitHub. Organisation policies can require approval; follow
[GitHub's token guide](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens).

Change the connection's settings to:

```yaml
settings:
  authentication: token
  auth_token:
    $secret:
      env: INGESTRON_GITHUB_TOKEN
  repositories:
    - your-owner/your-repository
```

Put `INGESTRON_GITHUB_TOKEN=your_token` in an untracked `.env` file. Build into a new
directory and repeat discovery, review and approval as described in
[change a project](/docs/guides/update-project). Add `--secrets-file .env` to discovery
and extraction commands. Keep the same `--from` directory throughout.

A rejected token fails; the connector never retries anonymously. Anonymous mode
rejects an `auth_token` setting. If `authentication` is omitted, the presence of
`auth_token` selects token mode; otherwise it selects anonymous mode. Ambient
`GITHUB_TOKEN` values are not used.
