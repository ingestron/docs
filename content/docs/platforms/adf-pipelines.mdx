Your standard decides how the generated pipelines look in ADF Studio. Every
setting on this page is optional: without them, each pipeline has one Copy
activity per table. This page applies to every route that starts with ADF; set
up the copies first with [Azure Data Factory](/docs/platforms/adf).

## Settings that shape it [#settings]

Write the pipeline settings under the method's settings in the standard, as
the Northwind example does; a flow can override them with
`ingest: { with: … }`, except where a pipeline's tables must agree.

<ExampleDownload name="northwind" />

<Example name="northwind" file="standard.yaml" pick="ingest" />

Run `ingestron apply` and open the pipeline in ADF Studio, or read the files
above, to see the result. Every value of these settings is in the
[ADF pack reference](/docs/reference/packs/adf#adf-copy-pattern).

### Copy every table with one ForEach

`pattern: foreach` gives each connection's pipeline one ForEach activity,
`for_each_table`, with one parameterised Copy inside, `copy_table`. The
pipeline's `tables` parameter lists the tables to copy. Its default value is
the generated list, so each table's query and landing folder are in the
pipeline's JSON and in Git. Nothing is read at run time, and no control table is
needed.

To copy only some tables again, trigger the pipeline with a shorter `tables`
value: copy the entries you need from the parameter's default, with all of each
entry's keys (`table`, `object`, `connection`, `query`, `watermark`, `folder`
and `file`), because the copy reads them from each item and a missing key fails
the run.

The pipeline also has `windowStart` and `windowEnd` parameters with no default.
The tumbling window trigger fills them. A rerun you start by hand must give
both, as the start and end of the window to copy again, in UTC; with an empty
value the copies may fail.

<Screenshot
  src="/images/platforms/adf-pipelines/adf-04-foreach-settings.png"
  label="Azure Data Factory"
  checked="2026-11-02"
  alt="The ForEach's Settings tab: Sequential off, Batch count 4, Items @pipeline().parameters.tables."
  caption="The demo's for_each_table in ADF Studio: four tables at a time, over the pipeline's tables parameter."
/>

`parallel` sets how many tables are copied at once; its range and default are
in the [`parallel`](/docs/reference/packs/adf#adf-copy-parallel) reference. The
pattern is offered for `adf-copy` sources (the SQL Server family).
Incremental tables carry their watermark column, and the Copy adds the window
filter when it runs. A `path` with date or `{run}` tokens needs one Copy
activity per table: use `pattern: activities`.

The tables of one pipeline share `pattern`, `parallel`, `activity` and
`audit_columns`. When a flow changes one of them for a single table,
`ingestron plan` names the tables that differ.

### Retry a failed copy

`activity` is the Copy activity's policy, for every ADF method:

<SettingsSections pack="adf" method="adf-copy" include={["activity"]} level={4} />

<Screenshot
  src="/images/platforms/adf-pipelines/adf-05-copy-general.png"
  label="Azure Data Factory"
  checked="2026-11-02"
  alt="The Copy activity copy_table's General tab: its description, Timeout 0.01:00:00, Retry 2, Retry interval 60 seconds."
  caption="The demo's copy_table in ADF Studio: its description, a one-hour timeout and two retries a minute apart, from activity."
/>

No generated file holds a value ADF would refuse: a `timeout` under ADF's own
minimum is reported as a settings problem. These retries happen inside the
run; `retries` at the method's top level still retries the whole window from
the trigger (see [Retry and pause](/docs/platforms/adf#retry-and-pause)). With
[`after_copy`](/docs/platforms/duckdb-in-azure#start-it-after-the-copies),
window retries move onto the copies, and your `activity` values
win.

### Add audit columns

`audit_columns` adds columns to every landed row, by name. A value is one of the
run values ADF fills in when it runs, or text:

<SettingsSections pack="adf" method="adf-copy" include={["audit_columns"]} level={4} />

<Screenshot
  src="/images/platforms/adf-pipelines/adf-06-copy-audit-columns.png"
  label="Azure Data Factory"
  checked="2026-11-02"
  alt="Additional columns on the copy's source: _loaded_at from @pipeline().TriggerTime, _run_id from @pipeline().RunId, _source from @item().object."
  caption="The demo's audit columns on the copy's source in ADF Studio, each an expression ADF fills in when it runs."
/>

The `run.` and `source.` names are matched in any case, so `RUN.ID` means
`run.id`, and the pipeline uses the lower-case form. Text that starts with
`run.` or `source.` but is not one of these names is refused, and so is text
that starts with `@` or holds `@{`, which ADF would read as an expression.

`run.window_start` and `run.window_end` come from the `windowStart` and
`windowEnd` parameters. A manual run that leaves either empty lands an empty
text in that column, which the packs that read the files cannot cast to a
timestamp. Give both when you start a run by hand.

Names start with a letter or underscore, must not repeat a contract column or
each other in another case, and must not be `_ingestron_file` or
`_rescued_data`, which the packs that read the files use.
The packs that read the files keep the columns after the contract's: Synapse
views, DuckDB tables and Databricks tables, with timestamps typed. Each data
product passport lists them with its columns, typed as the contract's are.

<Screenshot
  src="/images/platforms/adf-pipelines/synapse-02-customers-audit-columns.png"
  label="Azure Synapse"
  checked="2026-11-02"
  alt="The _run_id and _source columns of bronze.customers in Synapse: every row has the same run ID and northwind.dbo.Customers."
  caption="Where they land: rows of the demo's bronze.customers view in Synapse, each with the load's _run_id and _source."
/>

Audit columns are offered for `adf-copy` and for native table copies that read
columns by name. Files copied as they are have no rows to add to, and sources
read by path, or Microsoft 365, are refused for now.

### File resources in the factory

`folder` puts the project's pipelines and datasets in a factory folder, such as
`ingestron/erp`; every ADF table in a project uses the same folder.
`annotations` adds tags to a pipeline, after Ingestron's own. The tables of one
pipeline share them, so each flow can tag its pipeline with its source system.

<Screenshot
  src="/images/platforms/adf-pipelines/adf-08-pipeline-properties.png"
  label="Azure Data Factory"
  checked="2026-11-02"
  alt="The pipeline's properties: name pl_northwind_northwind, a description of the four copies, and the annotations Generated by Ingestron and northwind."
  caption="The demo's pl_northwind_northwind in ADF Studio: its generated description, and the annotations Generated by Ingestron and northwind."
/>

Under `pattern: foreach`, each run of `copy_table` carries its table's name as
a user property, so the run's monitoring view shows which table each copy was.

<Screenshot
  src="/images/platforms/adf-pipelines/adf-10-activity-runs-table.png"
  label="Azure Data Factory"
  checked="2026-11-02"
  alt="The User properties column of a run's activities, with the table values customers, products, order_details and orders."
  caption="The User properties of one run's copies in ADF's monitoring view: the table each copy_table copied."
/>

Every generated pipeline and Copy activity has a description, so the factory
explains itself without opening the definitions.
