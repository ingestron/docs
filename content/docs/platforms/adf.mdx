title: Azure Data Factory
description: Copy a source into landing storage with ADF, from one factory for every environment, and deploy it as an ARM template with a parameter file per environment.
---

When Databricks cannot reach the source, for example a database on a private
network, Azure Data Factory copies it. ADF reaches the source through an
integration runtime and copies each table into ADLS Gen2 landing storage on a
schedule. Ingestron writes one factory for every environment, its linked
services, datasets, Copy pipelines, triggers and integration runtimes, and a
parameter file for each environment; on this route, the Databricks pack writes
the pipelines that read the landed files into tables.

<RouteFacts id="adf-databricks" />

ADF feeds the other routes too. Everything on this page, from the runtime and
Key Vault to the schedules and deployment, applies to them as well; their own
pages cover what reads the files:

- [Synapse serverless views](/docs/platforms/synapse) (`adf-synapse`): views
  over the landed files.
- [Run DuckDB in Azure](/docs/platforms/duckdb-in-azure) (`adf-duckdb`): DuckDB
  tables rebuilt after each load.
- [Land files only](/docs/platforms/landing-only) (`adf-landing`): the landed
  files are the result.

## Settings that shape it [#settings]

Each setting has an owner: the connection holds the source's address and
credentials, the platform the shared infrastructure, the standard the shared
schedule, and the flow each table's choices; see
[Keep settings with their owner](/docs/concepts/standards-and-packs#keep-settings-with-their-owner).
The examples use `adf-copy`, for SQL-family tables; `adf-table` (native full
selections) and `adf-files` (file copies) take the same settings.

### Runtime and Key Vault [#runtime-and-key-vault]

<SettingsSections
  pack="adf"
  method="adf-copy"
  include={["integration_runtime", "runtime_kind", "landing", "key_vault"]}
/>

The factory gets each runtime its linked services use, as
`factory/integrationRuntime/<name>.json`, so a deployment never drops a
linked service's runtime. An ARM deployment sets a runtime's whole resource,
so describe a runtime linked to a shared one, or an Azure runtime's region
and compute, with the method's `runtime` setting; see the
[ADF pack reference](/docs/reference/packs/adf). Before the first deployment to
a factory that already has its runtimes, run `az deployment group what-if`
with the template and that environment's parameter file, as the notice says.
Windows SQL authentication, File System and HDFS need a self-hosted runtime;
other sources' needs are on their connector pages.

### Choose the source and its tables [#choose-the-source-and-its-tables]

The [connector page](/docs/connectors) for your source lists the connection's
fields, each authentication mode's, and the settings it takes in
`ingest.with.source_options`, such as
[REST's pagination](/docs/connectors/rest#adf-settings). Secrets use
`${secret:name}`: put the value in Key Vault under that name. The `object`
selects the native table, collection, dataset or relative path; give each
source its own landing folder.

Native table copies write a full selection each window. On the
`adf-databricks` route, repeated snapshots append repeated rows with the
default store; choose [upsert or history](/docs/how-to/keep-a-table-current)
for current rows or change history. SQL-family copies, as in this starter,
can copy only the rows changed in each window (`mode: incremental`). An
unknown setting stops generation with a diagnostic, and the standard's fixed
settings still win.

### Define the time windows [#define-the-time-windows]

The pipelines run from tumbling window triggers, which divide time into
consecutive, non-overlapping windows. `start` is the first window's start, in
UTC, and `every` sets each window's length. A full selection copies again each
window; an incremental copy filters the watermark column by the window's
bounds; file copies in `new` mode select the files changed in it.

<SettingsSections pack="adf" method="adf-copy" include={["every", "start"]} />

### Retry and pause [#retry-and-pause]

A retry repeats a failed window; it does not move that window's bounds.
Triggers start only in `prod` or `production`; in every other environment
they stay stopped. `paused` keeps a trigger stopped there too, and
`paused: false` starts one elsewhere. Without it, the trigger follows the
platform's `schedule.paused`; see the
[platform defaults](/docs/reference/packs/adf#platform-configuration).

<SettingsSections pack="adf" method="adf-copy" include={["retries", "paused"]} />

To stop only the copies, for example while the source database is down for
maintenance, set `paused` for the copy method in the platform, beside the
other `adf-copy` settings:

```yaml
settings:
  adf-copy:
    paused: true
```

`paused: true` in the platform's `schedule` stops the Databricks refresh job
and the triggers together; see
[Refresh on a schedule](/docs/platforms/databricks#schedule). On the
`adf-databricks` route, ADF and Databricks run on their own schedules. On
`adf-duckdb`, ADF can start the DuckDB job after the copies; see
[Run DuckDB in Azure](/docs/platforms/duckdb-in-azure).

### Tables that share a schedule

SQL-family tables in one connection and source database share their runtime,
encryption, schedule, retries and paused state. File tables in one connection
share their runtime and schedule. Give tables that need their own settings
separate connections. Native full-copy sources get a pipeline per table.

### Names and pipeline shape [#set-policy-and-names]

Resource names are the same in every environment, because one template is
deployed to each factory. [ADF resource names](/docs/how-to/name-things-your-way#adf-resource-names)
covers where each name goes, sharing rules and safe renames, and
[Shape ADF pipelines](/docs/platforms/adf-pipelines) covers ForEach, retries
inside a run, audit columns and factory folders.

## Before you deploy [#prerequisites]

<OldAnchor id="platform-prerequisites" />

Ingestron creates nothing in Azure and does not test credentials, run queries
or inspect the factory. These must exist before the pipelines can run:

- **An integration runtime that reaches the source.** A self-hosted runtime
  runs on infrastructure you manage, with the source's drivers and network
  access; register a node on it where the deployment creates it.
- **Key Vault**, holding the source's secrets, with access for the factory's
  identity.
- **ADLS Gen2 landing storage**, with write access for the factory's identity.
  Microsoft 365 uses its configured application instead.
- **Source access:** the permissions, drivers, versions and authentication in
  the source's vendor prerequisites, linked from its connector page.

`ingestron request --env prod`, or **Ingestron: Prepare platform request** in
VS Code, lists them with this project's values:

request.

## Deploy [#deploy]

<OldAnchor id="publish" />

One factory serves one project. Microsoft's post-deployment script deletes
every pipeline, dataset, linked service, trigger and integration runtime in
the factory that the template does not hold, so give each project, and each
environment, a factory of its own. Leave the test and production factories
unconnected to Git, as Microsoft recommends.

Build the ARM template once with Microsoft's
[`@microsoft/azure-data-factory-utilities`](https://www.npmjs.com/package/@microsoft/azure-data-factory-utilities),
on Node.js 20 or 22, from the project folder. It validates every resource and
writes `arm/ARMTemplateForFactory.json` and `arm/PrePostDeploymentScript.ps1`.
The factory ID only names the template's resources; the build downloads its
tool from `adf.azure.com` and changes nothing in Azure:

```sh
npm install --prefix .adf @microsoft/azure-data-factory-utilities@1.0.3
node .adf/node_modules/@microsoft/azure-data-factory-utilities/lib/index export build/adf/factory <dev factory resource ID> arm
```

Replace `<dev factory resource ID>` with the development factory's resource ID,
`/subscriptions/<id>/resourceGroups/<group>/providers/Microsoft.DataFactory/factories/<factory>`.
Keep `.adf/` and `arm/` out of Git: they are rebuilt for each deployment.

Then, for each environment in turn, signed in to its subscription, stop the
triggers, deploy the template with the environment's parameter file, and run
the script again to delete what the template no longer holds and start the
triggers whose state is `Started`. Here for `prod`:

```powershell
./arm/PrePostDeploymentScript.ps1 -ArmTemplate arm/ARMTemplateForFactory.json -ArmTemplateParameters build/adf/parameters/prod.json -ResourceGroupName <group> -DataFactoryName <factory> -PreDeployment $true -DeleteDeployment $false
az deployment group create --resource-group <group> --mode Incremental --template-file arm/ARMTemplateForFactory.json --parameters "@build/adf/parameters/prod.json" factoryName=<factory>
./arm/PrePostDeploymentScript.ps1 -ArmTemplate arm/ARMTemplateForFactory.json -ArmTemplateParameters build/adf/parameters/prod.json -ResourceGroupName <group> -DataFactoryName <factory> -PreDeployment $false -DeleteDeployment $true
```

Replace `<group>` and `<factory>` with the environment's resource group and
factory. The script needs PowerShell 7 and the Az modules. Always give it
`-ArmTemplateParameters`: without the environment's file it cannot tell that
`prod`'s triggers start. Keep `--mode Incremental`; Microsoft warns that
`Complete` deletes the resource group's other resources. When
`ingestron request` lists values to provide, add `<name>=<value>` after
`factoryName` for each.

What reads the files is deployed beside the factory, from its own folder:
[Databricks](/docs/platforms/databricks#deploy),
[Synapse](/docs/platforms/synapse#deploy) or
[DuckDB in Azure](/docs/platforms/duckdb-in-azure#deploy).

### From CI [#deploy-from-ci]

In a pipeline, the build runs once and each environment's stage deploys the
same template. From the GitHub Actions template, the build:

<Template
  file="github-actions/deploy.yml"
  from='- name: "Data Factory: build the template"'
  to='node "$adf" export'
/>

and each environment's deployment, between the two runs of the script:

<Template
  file="github-actions/deploy-environment.yml"
  from='- name: "Data Factory: deploy the template"'
  to='--parameters "@build/adf/parameters/$ENVIRONMENT.json"'
/>

Microsoft's three Data Factory GitHub Actions are archived, so the template
calls the npm package and the script directly. In Azure DevOps it uses
`AzurePowerShell@5` and `AzureResourceManagerTemplateDeployment@3`.
[Deploy through environments](/docs/how-to/deploy-through-environments) gives
the whole pipeline for both, with approvals between the stages.

## Limits [#limits]

- **Environments may differ only in values.** Resource names, integration
  runtime names and kinds, and resources built in some environments only are
  [`ENVIRONMENTS_DIFFER`](/docs/reference/errors#ENVIRONMENTS_DIFFER), and more
  than 256 template parameters is
  [`ARM_PARAMETERS`](/docs/reference/errors#ARM_PARAMETERS).
- **A value supplied when deploying is a whole value.** `${envvar:…}` inside a
  longer value, in the landing folder or in a name is
  [`DEPLOY_VALUE`](/docs/reference/errors#DEPLOY_VALUE): write it in
  `project.yaml` for each environment.
- **One project per factory.** A factory shared by several projects, or by
  resources you make in Studio, loses them on the next deployment.
- **Only the ARM template.** Deploying the factory's JSON directly, through the
  REST API or `az datafactory`, is not supported: the JSON holds the first
  environment's values.
- **A Git-connected development factory** writes files of its own into the
  folder, which `ingestron check` reports; leave it unconnected, or run
  `ingestron check --allow-extra`.
- **What has been tried.** The screenshots show the demo deployed with
  ingestron 1.8, which wrote a factory per environment. The 2.0 factory passes
  Microsoft's build for every connector, but has not yet been deployed as an
  ARM template to a live factory.
