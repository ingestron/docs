DuckDB runs SQL on one machine, with nothing to set up but its command line.
The DuckDB pack loads files into tables in a local database, runs transforms,
and publishes each table as Parquet that Power BI and other tools read as
files.

<RouteFacts id="duckdb" />

To try it, [run your first project on your laptop](/docs/start/first-project):
it creates a project from the **DuckDB on a laptop** starter, generates its
SQL and builds its tables. Each table is published to the `published/` folder
that `platform.yaml` names, as `<schema>.<table>.parquet`. Keep `ingestron.duckdb` and
`published/*.parquet` out of version control: they are data, built from the
files.

The same pack also runs a cloud project's tables on a laptop, so a failed load
can be tried again there; see [Run a cloud project locally](#run-a-cloud-project-locally).

## Read files where they are

`duckdb-files` reads a files connection's `path` and each table's `object`, a
file or a pattern. Name the format in the standard; CSV files have a header row
and commas unless `csv` says otherwise:

```yaml
# standard.yaml
packs: [duckdb@1]
ingest:
  settings:
    duckdb-files: { format: csv }
```

`duckdb-table` keeps each table by `mode`: `replace` (the default), `append`
(each file's rows once) or `upsert` (by the contract's primary key). The
`published` folder comes from the platform and must exist.

A CSV without a header (`csv.header: false`) binds its columns in the
contract's order, so the file's columns must be in that order. With a header,
columns are matched by name.

`append` reads each file name once, so a file re-exported under the same name is
skipped and its new rows are not loaded. Give a re-export a new name, or delete
`ingestron.duckdb` and run again to reload every file. In Azure each run starts
with an empty database, so every file is read.

A transform's columns are cast to the contract's types, and a cast can change a
value: a timestamp with a time zone loses its offset when the contract says
`timestamp`, and a `timestamptz` shows the time in the session's time zone; a
decimal rounds when the contract says `integer`. Give the
contract the type you want to keep.

`runs-on: duckdb` runs the same tables on a laptop:

In `local`, ADF's copy becomes `duckdb-landed`, which reads each table's files
from `<landing>/<object>/*.parquet`. Name the local folder in the standard:

<Example name="duckdb-local" file="standard.yaml" />

The tables' store and transforms must be DuckDB's in every environment, so the
local run is the cloud run with local paths: `run.sql` differs only in where
files are read and published. A serve step from another pack, such as
`synapse-serve`, is left out locally, since the tables can be queried in
`ingestron.duckdb`.

## Bring a load's files down

ADF writes a table's files to `<landing>/<object>/` in the landing storage,
with the contract's column names: one file, replaced by each load, with
`layout: snapshot` (as in the example), or a file per load with `increments`.
Download that folder's files to `samples/<object>/`, with Azure Storage
Explorer, or with AzCopy after `azcopy login`:

```sh
azcopy copy "https://saleslakedev.dfs.core.windows.net/landing/erp/erp.dbo.Invoices/*" \
  "samples/erp.dbo.Invoices/"
```

Then generate and run the local environment from the project folder:

```sh
ingestron apply
duckdb -bail ingestron.duckdb -c ".read build/local/duckdb/run.sql"
```

With increments and `upsert` or `append`, keep the loads' file names: they
start with the load's time, so a later load's rows win.

## Run the same tables in Azure

To rebuild the tables in Azure after each load, ADF can start a Container Apps
job: see [Run DuckDB in Azure](/docs/platforms/duckdb-in-azure).

## What a local run cannot catch

A local run starts after the files land. It finds mistakes in contracts, types,
modes and transforms, but not failures inside ADF: connectors, credentials,
networking, the self-hosted integration runtime, or the source itself. Tables
ADF lands in other ways find no files locally: Microsoft 365 data (JSON), files
`adf-files` copies as they are, and custom `path` layouts.
