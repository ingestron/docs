DuckDB runs SQL on one machine, with nothing to set up but its command line.
The DuckDB pack loads files into tables in a local database, runs transforms,
and publishes each table as Parquet that Power BI and other tools read as
files. The same pack runs a cloud project's tables on a laptop, so a failed
load can be tried again there.

<RouteFacts id="duckdb" />

## What it looks like in DuckDB [#on-the-platform]

After a run, the tables are in `ingestron.duckdb` in the project folder, and
their Parquet files in `published/`. From the starter's folder:

```sh
duckdb ingestron.duckdb -c "SELECT 'bronze.orders' AS name, count(*) AS row_count FROM bronze.orders UNION ALL SELECT 'silver.customer_totals', count(*) FROM silver.customer_totals ORDER BY name"
```

```text
┌────────────────────────┬───────────┐
│          name          │ row_count │
│        varchar         │   int64   │
├────────────────────────┼───────────┤
│ bronze.orders          │         5 │
│ silver.customer_totals │         3 │
└────────────────────────┴───────────┘
```

## Settings that shape it [#settings]

<OldAnchor id="read-files-where-they-are" />

`duckdb-files` reads a files connection's `path` and each table's `object`, a
file or a pattern. Name the format in the standard; CSV files have a header row
and commas unless `csv` says otherwise:

<SettingsSections pack="duckdb" method="duckdb-files" include={["format", "csv"]} />

A CSV without a header (`csv.header: false`) binds its columns in the
contract's order, so the file's columns must be in that order. With a header,
columns are matched by name.

`duckdb-table` keeps each table by `mode`: `replace`, `append` or `upsert`;
see [Keep a table current](/docs/how-to/keep-a-table-current#on-duckdb).
The `published` folder comes from the platform and must exist. What a cast to
the contract's type can change is in
[What each engine makes of it](/docs/how-to/write-a-transform#what-each-engine-makes-of-it).
Every method and setting is in the
[DuckDB pack reference](/docs/reference/packs/duckdb).

## Run and operate [#operate]

Run `run.sql` from the project folder, as the generated `README.md` says:

```sh
duckdb -bail ingestron.duckdb -c ".read build/duckdb/dev/run.sql"
```

`-bail` stops at the first error, so a run that fails while building
publishes nothing. Running again is safe: it rebuilds the tables and replaces
their files. Keep `ingestron.duckdb` and `published/*.parquet` out of version
control: they are data, built from the files. When a run fails, see [DuckDB](/docs/troubleshooting#duckdb) in
Troubleshooting.

### Run a cloud project locally

When ADF lands the files and DuckDB builds the tables, an environment that names
`runs-on: duckdb` runs the same tables on a laptop:

<ExampleDownload name="duckdb-local" />

<Example name="duckdb-local" file="project.yaml" />

In `local`, ADF's copy becomes `duckdb-landed`, which reads each table's files
from `<landing>/<object>/*.parquet`. Name the local folder in the standard:

<Example name="duckdb-local" file="standard.yaml" />

The tables' store and transforms must be DuckDB's in every environment, so the
local run is the cloud run with local paths: `run.sql` differs only in where
files are read and published. A serve step from another pack, such as
`synapse-serve`, is left out locally, since the tables can be queried in
`ingestron.duckdb`.

### Bring a load's files down

ADF writes a table's files to `<landing>/<object>/` in the landing storage,
with the contract's column names: one file, replaced by each load, with
`layout: snapshot` (as in the example), or a file per load with `increments`.
Download that folder's files to `samples/<object>/`, with Azure Storage
Explorer, or with AzCopy after `azcopy login`:

```sh
azcopy copy "https://salesdev.dfs.core.windows.net/landing/erp/erp.dbo.Invoices/*" \
  "samples/erp.dbo.Invoices/"
```

Then generate and run the local environment from the project folder:

```sh
ingestron apply
duckdb -bail ingestron.duckdb -c ".read build/duckdb/local/run.sql"
```

With increments and `upsert` or `append`, keep the loads' file names: they
start with the load's time, so a later load's rows win.

### Run the same tables in Azure

To rebuild the tables in Azure after each load, ADF can start a Container Apps

## Limits [#limits]

<OldAnchor id="what-a-local-run-cannot-catch" />

- **Rows are checked only where a layer says so.** DuckDB checks rows only in
  a layer whose `does` lists `check`. In any other layer a flow's
  `expectations` are an error, and each contract rule is
  [`NOT_APPLIED`](/docs/reference/errors#NOT_APPLIED); see
  [Check data quality](/docs/how-to/add-quality-checks).
- **A local run starts after the files land.** It finds mistakes in contracts,
  types, modes and transforms, but not failures inside ADF: connectors,
  credentials, networking, the self-hosted integration runtime, or the source
  itself.
- **Some landed tables find no files locally:** Microsoft 365 data (JSON),
  files `adf-files` copies as they are, and custom `path` layouts.
