---
title: Run DuckDB in Azure
description: Rebuild a project's DuckDB tables in Azure after each ADF load, with a Container Apps job and a public image.
---

When ADF lands the files and DuckDB builds the tables, an Azure Container Apps
job can rebuild them after each load. ADF runs a schedule's copies, starts the
job and waits for it. The job pulls the public image
`ghcr.io/ingestron/duckdb-runner:1`, so you need no container registry and no
registry credentials.

Each run starts with an empty database, reads every landed file, rebuilds
every table, and publishes each one to storage as Parquet. Nothing is kept
between runs, so running again is always safe.

## Settings that shape it [#settings]

<OldAnchor id="start-it-after-the-copies" />

With `after_copy`, each schedule has one parent pipeline,
`pl_<project>_every_<interval>_<unit>`, and one trigger in place of the
connection pipelines' triggers. The parent runs the schedule's copies, starts
the job once, reads the run's status every 30 seconds, and fails unless the run
succeeded.

<SettingsSections pack="adf" method="adf-copy" include={["after_copy"]} />

When you turn `after_copy` on in an environment that already runs:

- set `start` to the next window, because the new trigger runs every window
  since `start`;
- delete the connection pipelines' old triggers from the factory, because an
  incremental publish leaves them running, which would copy everything twice.

The tables' modes are as on [DuckDB](/docs/platforms/duckdb#settings), and the
copies' schedule and runtime as on
[Azure Data Factory](/docs/platforms/adf#runtime-and-key-vault).
`after_copy.job` names a resource in one environment, so give each environment
its job's ID in `project.yaml`: where the IDs differ, the factory takes the
job as a template parameter.

### Create the job

The job runs in a Container Apps environment on the consumption plan. Create
one if you have none:

```sh
az containerapp env create --name cae-data --resource-group rg-data --location <region>
```

Replace `<region>` with the Azure region that holds your storage.

Then deploy the job from the template,
[`duckdb-job.bicep`](https://github.com/ingestron/docs/blob/main/ci-templates/azure/duckdb-job.bicep):

```sh
az deployment group create --resource-group rg-data \
  --template-file duckdb-job.bicep \
  --parameters name=sales-dev-duckdb \
    environmentId=$(az containerapp env show -n cae-data -g rg-data --query id -o tsv) \
    sqlUrl=abfss://deploy@salesdev.dfs.core.windows.net/sales/dev/run.sql \
    storageAccountName=salesdev \
    factoryPrincipalId=$(az datafactory show -n adf-sales-dev -g rg-data --query identity.principalId -o tsv)
```

Its parameters:

<Template file="azure/duckdb-job.bicep" from="param name" to="param memory" />

The template creates the job with:

- **Identity:** its own managed identity, with Storage Blob Data Contributor on
  the storage account, to read the landed files and `run.sql` and to publish
  tables.
- **Resources and limits:** 0.5 vCPU and 1 GiB per run, a replica timeout of
  1800 seconds, and one retry. Raise the CPU and memory for larger tables, up
  to the consumption plan's limits.
- **Starting and stopping:** the Container Apps Jobs Operator role on the job
  for your data factory, so ADF can start runs, read them and stop them. The
  role also lets the factory change a run's container, so the job holds no
  secrets.
- **Image:** the public image, pulled anonymously. `:1` moves to each new 1.x
  release of the runner; to choose when it changes, pass `image=` with a full
  version tag or a digest (`ghcr.io/ingestron/duckdb-runner@sha256:…`). If your
  organisation only allows its own registry, copy the image there and pass
  `image=`; the template shows where the registry's settings go. A private
  registry adds its own cost.

The template outputs the job's resource ID, `jobId`, for `after_copy`.

## Deploy [#deploy]

<OldAnchor id="deploy-the-sql" />

Run `ingestron apply`, deploy the factory as in
[Azure Data Factory](/docs/platforms/adf-deploy#deploy), then copy the environment's
DuckDB folder to the folder `sqlUrl` names, here for `dev`:

```sh
az storage fs directory upload --account-name salesdev --file-system deploy \
  --source "build/duckdb/dev/*" --destination-path sales/dev --recursive --auth-mode login
```

The cloud environment's `run.sql` must read and write `abfss://` paths: the job
refuses one that names local folders. A local environment, such as `local`
here, is never deployed.

## Run and operate [#operate]

<OldAnchor id="hangs-failures-and-cost" />

The schedule's trigger starts the parent pipeline each window; outside
production it is stopped, as the
[platform defaults](/docs/reference/packs/adf#platform-configuration) say. Each
job run shows in the job's execution history:

<Screenshot
  src="/images/platforms/duckdb-in-azure/duckdb-03-job-runs.png"
  label="Azure portal"
  checked="2026-11-02"
  alt="The status and duration of the Container Apps job's three recent executions: each Succeeded, in 29 to 32 seconds."
  caption="The demo job's three most recent executions: each succeeded in about 30 seconds."
/>

- **A run that never finishes** is stopped at
  [`after_copy.timeout`](/docs/reference/packs/adf#adf-copy-after-copy-timeout),
  and the pipeline fails, saying whether the run stopped. The job's
  own replica timeout is half of that, so a retried run also ends in time.
- **A failed run** is retried once by the job. Retries are safe because each
  run rebuilds everything. ADF never starts the job twice for one load: a
  failed copy is retried in place, and the schedule's trigger does not retry.
- **Cost:** consumption-plan jobs bill per second only while a run goes. The
  first 180,000 vCPU-seconds and 360,000 GiB-seconds per subscription each
  month are free
  ([Container Apps pricing](https://azure.microsoft.com/en-us/pricing/details/container-apps/),
  checked 4 November 2026), so a small daily job may cost nothing. ADF bills
  each activity run: the wait reads the run's status every 30 seconds, about
  three activity runs a poll.
- **Every run reads every landed file.** With `layout: snapshot` that is one
  file per table. With increments, each run reads them all; keep them bounded,
  knowing that deleting old files removes their rows from `append` tables.
- **Two schedules** may start the job at once. Each run rebuilds everything,
  and the later run's files win.

When the parent pipeline fails, see
[The job after the copies fails or times out](/docs/troubleshooting#the-job-after-the-copies-fails-or-times-out).

DuckDB tables check no rows yet, so a flow's `expectations` are an error; see

### What has run in Azure

<OldAnchor id="checked-against-live-azure-not-yet" />

This route ran end to end with ingestron 1.8 on 2 November 2026, in one demo
subscription, on Microsoft's Northwind sample, before ingestron 2.0 put every
environment's factory into one ARM template: ADF copied four tables, started
the job and waited for it, and DuckDB built five tables, twice in a row. The
runs confirmed what the pipeline and the job rely on:

- **Starting the job:** the start call, with its empty body, is accepted, and
  the pipeline reads the run's name from Azure's response, then reads the
  run's status until it ends.
- **Signing in:** DuckDB signs in to storage with the job's managed identity,
  reads the landed files and `run.sql` from `abfss://` paths, and publishes
  each table there.
- **Running again:** a second run replaces each published file in place.

The demo did some steps differently from this page. It created the job with an
equivalent Terraform module, not `duckdb-job.bicep`; put the factory's
resources through the REST API rather than publishing them; copied the SQL file
by file; and started each run by hand, with the triggers stopped. A scheduled
run, a hung run, the job's own retry, a private registry and two schedules
starting the job at once have not been tried.
