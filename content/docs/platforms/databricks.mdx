When Databricks can reach the source, Databricks reads it and writes the
tables. The Databricks pack writes one
[Databricks bundle](https://docs.databricks.com/aws/en/dev-tools/bundles/) per
environment: Lakeflow pipelines with their SQL and Python files, Lakeflow
Connect ingestion for databases, and a refresh job when the platform has a
schedule or a contract task (tags, column comments or table checks) runs after
the refresh. The same bundle reads the files ADF lands on the `adf-databricks`
route; [Azure Data Factory](/docs/platforms/adf) covers the copies.

## Work through the retail project

In this example you read a complete Databricks project, generate it for its `dev`
and `prod` environments, and break it once on purpose to see how Ingestron reports a
problem. It builds on
[Run your first project on your laptop](/docs/start/first-project).

Create it from the `retail` starter, from a parent folder:

```sh
ingestron init retail --template retail --yes
cd retail
```

`--yes` keeps the example's workspace and storage; leave it out to answer
those questions. You can also <ExampleDownload name="retail" /> and unzip it.
Either way the project holds the definitions only: you generate `build/`
yourself in the fifth step.

### 1. The organisation's standard

<Example name="retail" file="standard.yaml" />

Every catalog is named `<environment>_sales`, rows missing a required value
are dropped, and every streaming table is clustered automatically, which no
project can change because it is `fixed`.

### 2. Dev and prod environments

<Example name="retail" file="project.yaml" />

`dev` and `prod` use different workspaces and storage accounts. The rest of
the definitions read these values, so nothing else changes between them.

### 3. Where things go

<Example name="retail" file="platform.yaml" />

The pipelines run as a service principal, engineers can manage them and
analysts can view them. The refresh job runs daily at 5 am London time
(`Europe/London`), paused in `dev`, and failures are emailed.

### 4. The tables

<Example name="retail" file="flows/shop.yaml" />

`orders` arrives as change records, so it is kept current by key
([Keep a table current](/docs/how-to/keep-a-table-current)) and checked for
negative totals. `customers` arrives as CSV with a header.

<Example name="retail" file="transforms/daily_sales.yaml" />

`daily_sales` reads both tables and lands in `silver`.

### 5. Generate


```text

```

</Tool>
<Tool name="VS Code">

Run **Ingestron: Plan** from the Command Palette (⇧⌘P on macOS, Ctrl+Shift+P elsewhere). The output is in the Ingestron output panel. Problems show in the Problems panel as you type, before you plan.

</Tool>
</ToolSteps>

Run `ingestron apply` to write both environments. Compare
`build/dev/databricks.yml` with `build/prod/databricks.yml`: the workspace
and the mode differ. In each folder's `resources/retail_refresh.job.yml`, the
`dev` schedule is paused and the `prod` one is not.

### 6. Break it on purpose

Change the transform's `id` to `orders` in `transforms/daily_sales.yaml` and
plan again:

```text
dev: the definitions have problems
transforms/daily_sales.yaml:3:5  error  DUPLICATE_TABLE
  Another flow or transform already produces a table named "orders".
```

Transforms refer to tables by name, so each name has one producer. Change
the `id` back to `daily_sales`; nothing was written while the problem
existed.

## Let the bundle create the schemas [#create-the-schemas]

By default Ingestron assumes the schemas already exist, created by your
platform team. When this project owns its schemas, say so in the platform and
give grants per layer:

<Example name="platform-setup" file="platform.yaml" />

The bundle then creates each schema the tables use, with the layer's grants,
and the pipelines refer to them so Databricks creates the schemas first:

<Example name="platform-setup" file="build/prod/resources/schemas.yml" />

The bundle also gets a `prerequisites.sql`, with the catalog grants to run once
as an administrator before the first deploy; see
[platform prerequisites](/docs/reference/packs/databricks#platform-prerequisites).

Only set `manage.schemas` when no other project uses the schemas: deploying
the bundle can change them, and `databricks bundle destroy` deletes them.

## Refresh on a schedule [#schedule]

Add a `schedule` to the platform, with a
[Quartz cron expression](https://www.quartz-scheduler.org/documentation/quartz-2.3.0/tutorials/crontrigger.html)
and, if not UTC, a time zone, as the retail platform above does. Ingestron
generates a job that refreshes the pipelines in order: Lakeflow Connect
ingestion first, then your own pipeline. The job, and its file under
`resources/`, are named `<project>_refresh` by default, after the project's
`id`; `naming.job` in the standard changes that (see
[Name tables and resources](/docs/how-to/name-things-your-way)). The
`sql-server` starter reads its database through Lakeflow Connect, so its job
has both tasks. The starter's own files use the id `erp`:

<Example name="sql-server" file="build/dev/resources/erp_refresh.job.yml" />

A project you create from it takes its folder's name as its id, so
`ingestron init sql-server --template sql-server` writes
`resources/sql_server_refresh.job.yml`.

Outside production the job is created paused, as the
[platform defaults](/docs/reference/packs/databricks#platform-configuration)
say; set `paused: false` in the `schedule` to change that.
`ingestron request` lists the state of each schedule, so the platform team
sees the same thing the files say.

On the `adf-databricks` route, the ADF copies have their own windows, but the
same switch stops them: `paused: true` in the platform's `schedule` stops both
the job and the Data Factory triggers. To stop only the copies, see
[Retry and pause](/docs/platforms/adf#retry-and-pause).

## Deploy the bundle [#deploy]

The generated folder is an ordinary Databricks bundle. You need the
[Databricks CLI](https://docs.databricks.com/aws/en/dev-tools/cli/) and to be
signed in to the workspace. Generate and review the files first, and arrange
the permissions and source access listed in the
[platform request](/docs/how-to/ask-the-platform-team).

### Deploy an environment

From the project folder, open the output folder containing `databricks.yml`:

- With only the Databricks pack: `build/dev/`.
- With ADF as well (the `adf-databricks` route): `build/dev/databricks/`.

Use the environment you intend to deploy in place of `dev`. Run these commands
from that bundle folder:

```sh
databricks bundle validate
databricks bundle deploy
```

On the `adf-databricks` route, publish the ADF resources separately, as in
[Publish the factory](/docs/platforms/adf#publish). The bundle does not start
the ADF copies; the landed files must be there before the pipelines read them.

### Deploy from a CI/CD pipeline [#deploy-from-ci]

Each environment's bundle is its own folder, `build/<environment>/`
(`build/<environment>/databricks/` on the `adf-databricks` route). Its
`databricks.yml` has one target, named after the environment and set as the
default: `build/prod/databricks.yml` holds the target `prod`. The target's
`mode` is `production` for an environment named `prod` or `production`, and
`development` otherwise, unless the platform sets `mode` itself.

Commit `build/` with the definitions, so one commit holds every environment's
bundle. A pipeline that already deploys Databricks bundles promotes that commit
stage by stage: each stage signs in to its environment's workspace, as it does
for any bundle, and runs this from that environment's folder, here for `prod`:

```sh
databricks bundle deploy -t prod
```

The deploy stages need the Databricks CLI only, not Ingestron: they deploy the
committed files. Keep `ingestron check` on pull requests, so the committed
bundles are what the definitions generate; the GitHub Actions and Azure DevOps
templates are in [Check generated files in CI](/docs/how-to/check-in-ci).

### Run the complete refresh

Inspect the generated files under `resources/`. If a refresh job is generated,
run that job so its ingestion, refresh and any contract tasks run in the
declared order. From the retail project's `build/dev/` folder:

```sh
databricks bundle run retail_refresh
```

For your project, use the key under `resources.jobs` in its generated job
file. If no job is generated, run the pipeline key under `resources.pipelines`
instead:

```sh
databricks bundle run <pipeline-key>
```

Replace `<pipeline-key>` with that YAML key, not the display `name` or a
filename. Read the run output and inspect the run in Databricks to confirm
that its tasks succeeded. See the
[bundle run instructions](https://docs.databricks.com/aws/en/dev-tools/bundles/work-tasks)
for the platform command (checked 28 October 2026).
