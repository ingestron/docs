When Databricks can reach the source, Databricks reads it and writes the
tables. The Databricks pack writes one
[Databricks bundle](https://docs.databricks.com/aws/en/dev-tools/bundles/) for
every environment, with a target per environment: Lakeflow pipelines with
their SQL and Python files, Lakeflow Connect ingestion for databases, and a
refresh job when the platform has a schedule or a contract task (tags, column
comments or table checks) runs after the refresh. The same bundle reads the
files ADF lands on the `adf-databricks` route;
[Azure Data Factory](/docs/platforms/adf) covers the copies.

The pipeline reads the catalog from `${var.catalog}`, and passes the landing

Everything the same in every environment, such as the schema and the tags, is
written as it is:

<Example name="retail" file="build/databricks/resources/retail.pipeline.yml" />

The table's SQL names tables with two parts, in the pipeline's catalog, and
reads its files from `${ingestron.shop_path}`. Its expectations come from the
contract, and `CLUSTER BY AUTO` from the standard's fixed setting:

<Example name="retail" file="build/databricks/src/retail/bronze/customers.sql" />

A value only the deploying pipeline knows, written as `${envvar:NAME}`, is a
variable that the targets leave unset; see
[Supplied when deploying](/docs/concepts/yaml-references#supplied-when-deploying).

`dev` and `prod` use different workspaces and storage accounts. The rest of

Then generate both environments:

```sh
ingestron plan --no-diff
```

```text
databricks → build/databricks (dev, prod)
create    databricks.yml
create    resources/retail.pipeline.yml
create    resources/retail_refresh.job.yml
create    src/retail/bronze/customers.sql

create    src/retail/silver/daily_sales.sql

6 files: 6 create. Ready to apply.
```

Run `ingestron apply` to write them. If plan reports a problem instead, each
one names its file, line and fix; see
[Troubleshooting](/docs/troubleshooting#databricks).

## Settings that shape it [#settings]

The platform document decides the targets: `workspace`, `run_as`,
`permissions` and `mode` go into each target, and `tags` that differ become
the target's preset tags. The defaults:

<PlatformDefaults pack="databricks" />

Only an environment named `dev` is in development mode, which prefixes
resource names with the deploying user and pauses schedules; every other
environment is in production mode. Each setting is explained in the
[Databricks pack reference](/docs/reference/packs/databricks#platform-configuration).

### Let the bundle create the schemas [#create-the-schemas]

By default Ingestron assumes the schemas already exist, created by your
platform team. When this project owns its schemas, say so in the platform and
give grants per layer, as the `platform-setup` example does:

<Example name="platform-setup" file="platform.yaml" />

The bundle then creates each schema the tables use, with the layer's grants,
in each target's catalog:

<Example name="platform-setup" file="build/databricks/resources/schemas.yml" />

Each environment also gets the catalog grants an administrator runs once
before the first deploy. They are not deployed:

<Example name="platform-setup" file="build/databricks/prerequisites/prod.sql" />

Only set `manage.schemas` when no other project uses the schemas: deploying
the bundle can change them, and `databricks bundle destroy` deletes them.

### Refresh on a schedule [#schedule]

A `schedule` in the platform, with a
[Quartz cron expression](https://www.quartz-scheduler.org/documentation/quartz-2.3.0/tutorials/crontrigger.html)
and a time zone, adds a job that refreshes the pipelines in order: Lakeflow
Connect ingestion first, then your own pipeline. It is named
`<project>_refresh` by default; `naming.job` in the standard changes that (see
[Name tables and resources](/docs/how-to/name-things-your-way)). The
`sql-server` starter reads its database through Lakeflow Connect, so its job
has both tasks:

<Example
  name="sql-server"
  file="build/databricks/resources/erp_refresh.job.yml"
  pick="resources.jobs.erp_refresh.tasks"
/>

The schedule runs only in `prod` or `production`; set `paused` in the
`schedule` to change that. On the `adf-databricks` route, `paused: true` in the
platform's `schedule` stops both the job and the Data Factory triggers; to
stop only the copies, see
[Retry and pause](/docs/platforms/adf-pipelines#retry-and-pause).

The tables themselves are shaped by the flows and the standard:
[Keep a table current](/docs/how-to/keep-a-table-current),
[Write a transform](/docs/how-to/write-a-transform) and
[Check data quality](/docs/how-to/add-quality-checks).

## Deploy and run [#deploy]

<OldAnchor id="prerequisites" />
<OldAnchor id="deploy-from-ci" />

Deploy the bundle with the Databricks CLI, one environment's target at a time,
from `build/databricks`: `databricks bundle deploy -t <environment>`.
[Deploy the Databricks bundle](/docs/platforms/databricks-deploy) lists what
must exist first, deploys by hand or [from CI](/docs/platforms/databricks-deploy#deploy-from-ci)
as one identity, and runs the refresh.

## Limits [#limits]

- **Environments may differ only in values.** A table built in some
  environments only, or code that differs in more than a value, is
  [`ENVIRONMENTS_DIFFER`](/docs/reference/errors#ENVIRONMENTS_DIFFER). A
  PySpark transform's own code cannot hold a value that differs yet, and a
  Kafka connection's `continuous` must be the same in every environment.
- **Values supplied when deploying** must be values, not names: a flow's
  `source` read from `${envvar:…}` is
  [`DEPLOY_VALUE`](/docs/reference/errors#DEPLOY_VALUE).
- **What has been tried.** The screenshots show the demo deployed with
  ingestron 1.8, which wrote a bundle per environment. The 2.0 bundle, one for
  every environment, validates against the Databricks CLI's bundle schema
  (v1.23.0), but has not yet been deployed to a live workspace.
