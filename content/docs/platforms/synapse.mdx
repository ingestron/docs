---
title: Synapse serverless views
description: Show the files ADF lands to reports as Synapse serverless SQL views, with transforms as views too.
---

When reports need SQL tables, but nothing should run or be stored after each
load, Synapse serverless SQL can show the files ADF lands as views. A transform
becomes a view over other views, and Synapse reads the files each time a report
queries a view.

<RouteFacts id="adf-synapse" />

## What Ingestron writes [#what-you-get]

The ADF pack writes the factory, as on
[Azure Data Factory](/docs/platforms/adf#what-you-get), and the Synapse pack
writes one script of views for every environment, with a short script for each
environment that sets its values:

<BuildTree name="synapse-views" folder="build/synapse" />

`views.sql` starts by switching to the environment's database, a sqlcmd
variable, because the databases differ between environments; everything the
same in every environment is written as it is:

<Example name="synapse-views" file="build/synapse/views.sql" from="USE [" to="GO" />

Each copied table becomes a view over the file ADF lands, read through the
external data source `landing`, with the contract's column types:

<Example
  name="synapse-views"
  file="build/synapse/views.sql"
  from="CREATE OR ALTER VIEW [bronze].[customers]"
  to="GO"
/>

A transform becomes a view over its inputs' views, with its SQL inside:

<Example
  name="synapse-views"
  file="build/synapse/views.sql"
  from="CREATE OR ALTER VIEW [silver].[customer_totals]"
  to="GO"
/>

Each environment's script sets the variables and includes `views.sql`. It
stops at the first error:

<Example name="synapse-views" file="build/synapse/environments/prod.sql" />

A value only the deploying pipeline knows, written as `${envvar:NAME}`, is a
variable that the script leaves unset, and the pipeline sets as an
environment variable `NAME`; see
[Supplied when deploying](/docs/concepts/yaml-references#supplied-when-deploying).

## Settings that shape it [#settings]

<OldAnchor id="list-synapse-first-and-keep-tables-as-views" />
<OldAnchor id="name-the-external-data-source" />
<OldAnchor id="write-a-transform-as-a-view" />

`store: { default: synapse-view }` keeps every table as a view over the files
ADF lands. The database is named by the standard's `naming.catalog`, here the
Synapse pack's default, `{{ project }}_{{ environment }}`; see
[Name tables and resources](/docs/how-to/name-things-your-way).

`data_source` and `data_source_location` name the external data source in
every view, and every file a view reads must be under the location:

<SettingsSections
  pack="synapse"
  method="synapse-view"
  include={["data_source", "data_source_location"]}
/>

`layout: snapshot` lands one file per table, so each view shows the current
data; a view over files that each load adds shows every load's rows. ADF's
schedule, runtime and landing settings are on
[Azure Data Factory](/docs/platforms/adf#runtime-and-key-vault). What a view's
SQL can do is in
[What each engine makes of it](/docs/how-to/write-a-transform#what-each-engine-makes-of-it).

### Views or tables

A view cannot merge changes or keep history. For that, keep the table with a
store pack and serve it with `synapse-serve`; see
[Keep a table current](/docs/how-to/keep-a-table-current#on-synapse).

|                             | Views (Synapse)                              | Tables (a store pack, served with `synapse-serve`) |
| --------------------------- | -------------------------------------------- | -------------------------------------------------- |
| Runs after each load        | Nothing                                      | The store pack's job                               |
| Cost                        | Data scanned each time a report reads a view | The job's run time, plus data scanned when read    |
| Merge, history              | No: the files as they are                    | Yes                                                |
| Heavy joins over large data | Recomputed on every read                     | Computed once per load                             |

Ingestron creates nothing in Synapse. `ingestron request --env dev` lists what
the team that owns the workspace creates first, with this project's names: the
serverless database, the external data source with a managed-identity
credential, the workspace's read access to the storage, and report users'
permissions.

<Request
  name="synapse-views"

/>

The same request lists what ADF needs first, as in
[Before you deploy](/docs/platforms/adf-deploy#prerequisites). Run the views with
sqlcmd (Go), which signs in with Microsoft Entra ID; install it with
`winget install sqlcmd` or `brew install sqlcmd`, or from its

## Deploy [#deploy]

<OldAnchor id="generate-then-run-the-views" />

Run `ingestron apply`, then deploy the factory as in
[Azure Data Factory](/docs/platforms/adf-deploy#deploy). Then run the environment's
script with sqlcmd (Go), from `build/synapse`, signed in with `az login`, here
for `dev`:

```sh
cd build/synapse
sqlcmd -S <workspace>-ondemand.sql.azuresynapse.net --authentication-method ActiveDirectoryDefault -i environments/dev.sql
```

Replace `<workspace>` with your Synapse workspace's name. Start sqlcmd in
`build/synapse`: it reads `views.sql` from the folder it starts in, not from
the script's folder. `views.sql` holds sqlcmd variables, so Synapse Studio,
which has no SQLCMD mode, cannot run it. See
[Authenticate with Microsoft Entra ID in sqlcmd](https://learn.microsoft.com/en-us/sql/tools/sqlcmd/sqlcmd-authentication)
for the other ways to sign in (checked 5 November 2026).

### From CI [#deploy-from-ci]

GitHub's Ubuntu runners and Azure DevOps' Ubuntu agents have no sqlcmd, so
each environment's stage installs sqlcmd (Go) at a pinned version, checked by
its SHA-256, then runs the environment's script. From the GitHub Actions
template:

<Template
  file="github-actions/deploy-environment.yml"
  from='- name: "Synapse: install sqlcmd"'
  to='-i "environments/$ENVIRONMENT.sql"'
/>

Do not pass `-X`, which stops sqlcmd reading environment variables, or `-x`,
which stops it replacing variables.
[Deploy through environments](/docs/how-to/deploy-through-environments) gives
the whole pipeline, for GitHub Actions and Azure DevOps.

## Run and operate [#operate]

Loads need nothing more: ADF replaces the files on its schedule, and each query
reads the files as they are then. Run the environment's script again whenever
the definitions change, such as a new table or column. It creates or alters
every view, so running it again is safe; it drops nothing, so a view for a
table you removed stays until you drop it.

When a table's layer checks its rows, `ingestron apply` also writes
`checks.sql`, with `checks/<environment>.sql` for each environment. It counts
every check's failing rows, returns one row per check, and raises an error
when a `fail` check fails. A view reads the files each time it is queried, so
nothing runs the checks by itself: run the script after each landing, from
`build/synapse`, here for `dev`:

```sh
sqlcmd -S <workspace>-ondemand.sql.azuresynapse.net --authentication-method ActiveDirectoryDefault -i checks/dev.sql
```

or from a pipeline's Script activity, with each `$(…)` replaced by the
environment's value, or as a step in CI. See
[Check data quality](/docs/how-to/add-quality-checks#synapse).

When a view fails to create or to read its files, see
[Synapse serverless views](/docs/troubleshooting#synapse-serverless-views) in
Troubleshooting.

## Limits [#limits]

- **Checks only where a layer checks, and no `fail`.** In a layer whose `does`
  lists `check`, the view leaves out the rows a `drop` check fails, and
  `checks.sql` counts every check, but only when something runs it. A view
  cannot stop a load, keep the rows it leaves out, or keep results, and
  serverless T-SQL has no regular expressions: each is
  [not applied here](/docs/concepts/not-applied). See
  [Check data quality](/docs/how-to/add-quality-checks#synapse).
- **No merge or history.** A view shows the files as they are; see
  [Views or tables](#views-or-tables).
- **Environments may differ only in values.** A table built in some
  environments only, or a transform whose code differs in more than a value,
  is [`ENVIRONMENTS_DIFFER`](/docs/reference/errors#ENVIRONMENTS_DIFFER). A
  value that differs cannot hold `'`, `]` or a line break, and a value
  supplied when deploying must be a whole value.
- **What has been tried.** The screenshots show the demo deployed with
  ingestron 1.8. The 2.0 scripts have been run with sqlcmd (Go) v1.10.0 and the
  ODBC sqlcmd against a local SQL engine, not yet against a Synapse workspace.
