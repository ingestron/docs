A contract says what a table holds: its columns, their types, which columns
make the key and which must always have a value. Ingestron reads it to type
the table's columns, to keep rows by their key and to check them. Contracts
use the [Open Data Contract Standard](https://bitol-io.github.io/open-data-contract-standard/)
(ODCS) v3.1.0 unchanged, so other tools can read them too.

The contract's `schema` entry whose `name` is the table's name is used, or the
only entry when there is one. A contract with several entries and none named
like the table is an error
([`CONTRACT_TABLE`](/docs/reference/errors#CONTRACT_TABLE)).

## What Ingestron reads

Ingestron reads:

- for each column: `name`, `logicalType`, `physicalType`, `physicalName`,
  `required`, `primaryKey`, `primaryKeyPosition` and `description`;
- for each column's values: `logicalTypeOptions`, such as `minLength`,
  `pattern` or `minimum`, `unique`, and its `quality` rules;
- for the table: the schema entry's `description`, for the table's comment,
  and its `quality` rules;
- the table's and each column's `tags`, and each column's `classification`,
  which it keeps for packs that tag tables.

[Data contract](/docs/reference/documents#data-contract) lists every ODCS
field.

What each pack does with a field, or why it does not yet, is on its page:
[Databricks](/docs/reference/packs/databricks#contract-fields),
[Azure Data Factory](/docs/reference/packs/adf#contract-fields),
[Synapse](/docs/reference/packs/synapse#contract-fields) and
[DuckDB](/docs/reference/packs/duckdb#contract-fields). A contract field that
no pack of your standard uses yet is a
[warning](/docs/reference/errors#CONTRACT_FIELD_UNUSED) at that field.

## Keys and required columns

- `primaryKey: true` marks the table's key. With several key columns,
  `primaryKeyPosition` orders them. The key is what `upsert` and `history`
  keep the current row by; see [Keep a table current](/docs/how-to/keep-a-table-current).
- `required: true` says the column always has a value. Where the pack checks
  rows, a required column gets a check that it is not null, with the
  standard's `quality.required` action; see
  [Add quality checks](/docs/how-to/add-quality-checks).

## Rules about the data

Where the pack checks rows, these become checks on each row, with the
standard's `quality.default` action:

- A column's `logicalTypeOptions`: `minLength` and `maxLength`, `pattern`,
  `minimum`, `maximum`, `exclusiveMinimum` and `exclusiveMaximum`,
  `multipleOf`, `minItems`, `maxItems` and `uniqueItems`. Each check is named
  `<column>_<option>`, such as `customer_id_minimum`, and a null value passes.
  `format` and the other options only document the column.
- A column's `quality` rules that allow no failing row: `nullValues`,
  `missingValues` and `invalidValues` (with `validValues` or `pattern`) when
  they must be 0.

Other rules compare a count over all rows, such as a row count or a share of
nulls, which a check of one row cannot. So does `unique: true`, which says no
value repeats. These run after each refresh when the platform turns on
`manage.checks`. Otherwise each `quality` rule is a
[warning](/docs/reference/errors#QUALITY_RULE_NOT_CHECKED) and stays as
documentation.

## Tags and classification

A contract's `tags`, a column's `tags` and its `classification` are kept for
packs that tag tables. Databricks sets them as Unity Catalog tags after each
refresh when the platform turns on `manage.tags`; see
[Databricks contract fields](/docs/reference/packs/databricks#contract-fields).

## Draft from a sample [#draft-from-a-sample]

When a source sends files, start its contract from a sample instead of typing
every column:

```sh
ingestron contract exports/orders.csv --name shop.orders
```

In VS Code, right-click the file in the Explorer and choose
**Ingestron: Draft contract from sample**, or run it from the Command Palette
with the file open.

Ingestron reads the header and up to 1,000 rows of a CSV file (comma,
semicolon or tab separated) or a JSON file (an array of objects, or one
object per line), and writes `contracts/<name>.yaml` with each column's name
and the narrowest logical type every value fits: `integer`, `number`,
`boolean`, `date`, `timestamp`, `array`, `object`, else `string`. A value
with a leading zero, such as the code `00123`, stays a `string`, because as a
number it would lose its zeros. It never overwrites a contract, and the draft
holds no values from the sample.

A sample cannot prove which columns are keys or always present, so the draft
is `status: draft` with neither. Review the types, then add `primaryKey`,
`required` and descriptions, and link it from a table with `contract`.
[Add a source and its tables](/docs/how-to/add-a-source#add-a-table-from-a-source-you-already-read)
drafts one and links it.
