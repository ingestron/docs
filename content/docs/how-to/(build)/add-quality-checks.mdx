---
title: Check data quality
description: Count, drop or stop on rows that break a rule.
---

Checks run where the platform builds the table, and not every platform checks
rows yet:

| Where the table is built                                  | What happens to the checks                                                                                                                                                                            |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Databricks](/docs/platforms/databricks)                  | Runs them, as this guide describes.                                                                                                                                                                   |
| [DuckDB](/docs/platforms/duckdb), on a laptop or in Azure | Runs them in a layer whose `does` lists `check`. In any other layer, a flow's `expectations` entry is an error (`METHOD_CHECK`) and each contract rule is not applied (`NOT_APPLIED`).                |
| [Synapse serverless views](/docs/platforms/synapse)       | In a layer whose `does` lists `check`, the view leaves out the rows a `drop` check fails, and `checks.sql` counts every check. In any other layer, each contract rule is not applied (`NOT_APPLIED`). |
| [Land files only](/docs/platforms/landing-only)           | Nothing reads the files, so each expectation and contract rule is not applied (`NOT_APPLIED`).                                                                                                        |

The rest of this guide is about Databricks.

Every column the contract marks `required: true` gets a check that it is not
null. You add your own checks on the table with `expectations`:

<Example name="quality" file="flows/readings.yaml" />

Each check is a SQL condition rows must meet. `action` says what happens to
rows that fail:

| `action` | Effect                             |
| -------- | ---------------------------------- |
| `warn`   | keep the row and count the failure |
| `drop`   | leave the row out and count it     |
| `fail`   | stop the update                    |

Without an `action`, the standard decides. Its `quality` sets the action for
required columns and the default for your own checks:

<Example name="quality" file="standard.yaml" />

`quality: { results: true }` in the standard also keeps the results of the
checks as a table you can query: on Databricks, the pipeline's event log. It is
[intent](/docs/reference/intent), so a pack that cannot keep them says so with
[`NOT_APPLIED`](/docs/reference/errors#NOT_APPLIED).
