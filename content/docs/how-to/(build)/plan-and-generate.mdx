---
title: Plan, apply and review
description: Validate definitions, inspect proposed file changes and write the reviewed output.
---

Run this workflow after creating or changing a project. Work from the folder
containing `project.yaml`, with your definitions and standard saved. The selected
packs determine which files appear; the workflow is the same across routes.

## 1. Inspect the plan

<ToolSteps>
<Tool name="CLI">

```sh
ingestron plan
```

Every environment is planned together, into one output folder per platform.
Add `--no-diff` for the file list without line-by-line differences.

</Tool>
<Tool name="VS Code">

Save the definitions and run **Ingestron: Plan**. Inspect the output panel and
resolve any Problems entries; the Problems panel shows the environment selected
in the status bar.

The plan lists each output folder, such as `databricks → build/databricks
(dev, prod)`, with the environments it holds, and its proposed creates, updates
and deletions. It resolves every environment and validates definition links,
method compatibility, required settings and standard policy before writing
anything: a problem in any environment stops the plan, so a bundle or factory is
never written with an environment missing. A diagnostic includes the file and
location to fix. A conflict means a generated file was changed by hand.

Review unexpected deletions and names as well as new files. Generation checks
configuration; it does not test source credentials, networks or cloud permissions.

## 2. Generate the files

<ToolSteps>
<Tool name="CLI">

```sh
ingestron apply
```

</Tool>
<Tool name="VS Code">

Run **Ingestron: Apply**, which writes every environment, and read the result
in the output panel. If it reports a problem, some folders may not have been
written.

</Tool>
</ToolSteps>

Apply writes the planned output and reports what it applied. It does not deploy
resources or move source data. If a generated file has a manual edit, move the
change into the definitions or restore that file before generating again.
See [generated-file ownership](/docs/concepts/generated-files) for recovery rules.

## 3. Review and commit

Inspect the definition changes alongside the generated diff. Check the source
objects, names, secret references, target locations and schedules relevant to
your packs. Commit both definitions and generated output so reviewers can see
the platform effect.

Use [CI checking](/docs/how-to/check-in-ci) to detect drift without rewriting files.
Applying writes files; deploying them is a separate step, with your platform's
own tools, one environment after another; see
[Deploy through environments](/docs/how-to/deploy-through-environments). Each
route's guide says how:
