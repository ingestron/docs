title: Create a project
description: Start from a connection and a supported route, or from a starter or a downloaded example, then make the definitions yours.

A project is a folder of YAML definitions with a `project.yaml` at its root.
Create one in any of three ways:

- **From a connection:** choose the source, how it can be reached, and the
  route its data takes. The project holds only that connection, its example
  flows and contracts, and any transforms they need.
- **From a starter:** copy a complete project for a common situation, such as
  [the DuckDB starter](/docs/start/first-project), or one your organisation
  shares as a template.
- **From a published standard:** copy a dated standard for your platform,
  which says how every table is loaded, kept and run, with a small project
  that builds; see
  [Start from a published standard](/docs/how-to/start-from-a-published-standard).

Each way, the result is ordinary definitions you edit, then plan and apply.

## Start from a connection

Ingestron offers only the routes the source supports, for how it can be
reached; [Choose where your data goes](/docs/start/choose-a-route) shows the
platform combinations for each source.

<ToolSteps>
<Tool name="CLI">

From the parent folder where you want the project, run:

```sh
ingestron init sales
```

Choose the source category, connector, network reachability and route.
When only one route is supported, Ingestron selects it. Nothing else is asked:
the project's id is the folder's name, its environments are `dev` and `prod`,
and its standard is the route's own.

To choose them with flags (`--via` is `databricks`, `adf-databricks`,
`adf-synapse`, `adf-duckdb` or `adf-landing`; see
[Choose where your data goes](/docs/start/choose-a-route)), as a script would:

```sh
ingestron init sales --connector postgresql --connectivity private --via adf-databricks --yes
```

`--yes` takes the default of each choice not given as a flag. `--env` gives
other environments, `--name` another id, and
`--standard ../platform/standard.yaml` your organisation's standard, or
`--kit` a [published one](/docs/how-to/start-from-a-published-standard#with-a-connection).

</Tool>
<Tool name="VS Code">

Run **Ingestron: New project** from the Command Palette and choose **From a
connection**. Choose a category, or **All sources**, then type to search
connectors. Choose source reachability and a supported ingestion route, then
the folder to create the project in: its name becomes the project's id.
Cancelling a choice creates no files.

The new `README.md` opens in a preview, and a message says how many values
are still to write. The generation plan appears in the Ingestron output
panel.

</Tool>
</ToolSteps>

The project holds the connection, its example flows and contracts, and the
platform settings the route needs. What Ingestron cannot know, such as the
source's server, the tables to copy, the storage account or the integration
runtime, is written as `REPLACE_ME`, with a comment above it saying what it
is; see [Write the values it cannot know](#write-the-values).

## Start from a starter [#start-from-a-starter]

A starter is a complete project, often with several tables and a transform.
[Starters and templates](/docs/reference/templates#built-in-templates) lists the starters
and what each sets up.

<ToolSteps>
<Tool name="CLI">

Name a starter, a folder or a Git URL with `--template`:

```sh
ingestron init sales --template retail
ingestron init sales --template ../templates/lakehouse
ingestron init sales --template https://github.com/acme/data-templates.git#lakehouse
```

`--template` cannot be combined with `--connector`, `--connectivity` or
`--via`. After `#` comes the folder inside the repository. Git uses your
own credentials. The environments are the starter's own; `--env`,
`--standard` and `--set` work as they do from a connection.

</Tool>
<Tool name="VS Code">

Run **Ingestron: New project** and choose **From a starter**, then the
starter, then the folder to create it in.

</Tool>
</ToolSteps>

To make a template of your own, see [Share templates and standards](/docs/how-to/share-a-template).

### From a downloaded example

The **Examples** section of a connector's page offers project ZIPs. Extract
one into an empty folder, and open the folder that holds `project.yaml`. The
archive contains the synthetic definitions and contracts, without generated files,
so you can generate it locally without access to the source. A starter's
download is what `init` writes from it, with `REPLACE_ME` where a value is
yours and a `README.md` that lists them. Code blocks there name the project and
the relative path of each file shown.

A multi-connector project demonstrates several sources together. To start
with only one connection, [start from a connection](#start-from-a-connection)
instead.

## Use your standard

A project has one standard, including when it uses several packs.
Creation validates every environment before writing files. See
[Set your organisation's standard](/docs/how-to/configure-a-standard) for
allowed methods, settings ownership and fixed policies.

## Write the values it cannot know [#write-the-values]

<OldAnchor id="make-it-yours" />

`init` writes `README.md`, which lists each value still `REPLACE_ME`, with its
file and line, what it is, where to find it and the environments it is for,
then the Key Vault secrets to create, how to deploy each output folder, and
how to ask the platform team. It is yours: Ingestron never writes it again.
`init` ends by saying how many there are, such as:

```text
7 values are still REPLACE_ME: README.md lists each one and where to find it.
```

Write each value in place, where the comment above it says. A value that
differs between environments, such as the storage account, is already under
`environments.<name>.values` in `project.yaml`. Or give the values when you
create the project, each by the name README.md shows, with `--set`, and
`--set <environment>.<name>` for one environment:

```sh
ingestron init sales --connector postgresql --connectivity private --via adf-databricks --yes \
  --set source_server=pg.example.invalid --set prod.storage_account=salesprod
```

A name the project does not have is refused, with the names it has. Until
every value is written, `ingestron plan` and `apply` warn about each, with
[`REPLACE_ME`](/docs/reference/errors#REPLACE_ME), and still write the files;
`ingestron check` fails, so nothing with a `REPLACE_ME` passes CI, and
`ingestron request` lists them first. `plan` counts each place a value is
written, where `init` counts names, so a value such as the storage account,
written for `dev` and for `prod`, counts once for `init` and twice for `plan`.
For the project above, plan ends:

```text
9 values are still REPLACE_ME; ingestron check fails until each is written.
```

Then make the rest yours:

1. Keep secrets out of the YAML. A connection's password is already a
   `${secret:name}` reference, such as `${secret:sales-postgresql-password}`;
   create the secret in Key Vault under that name, as README.md says. See
   [YAML references and placeholders](/docs/concepts/yaml-references).
2. Adapt each contract to the columns and keys of its object; the tables and
   contracts README.md names are examples. See
   [Describe a table with a contract](/docs/how-to/write-a-contract), and the
   **Read with …** section of the connector's page for its reading options.
3. Check the environments, platform and standard. Use the connector reference
   and [Azure Data Factory](/docs/platforms/adf) for ADF infrastructure, and
   [ADF resource names](/docs/how-to/name-things-your-way#adf-resource-names)
   for name defaults and overrides.
4. Arrange the source credentials and platform permissions the route needs.
   Local generation does not need them.

`init` never replaces an existing file. If any target file already exists,
it lists the clashes and writes nothing. Two files are exceptions. An existing
`README.md` is kept, and `init` prints the values to replace instead. An
existing `.gitignore` gains only the lines it lacks: those that keep `.env`
files out of Git, and on a route through Data Factory, the folders
Microsoft's build writes. See
[Environment files](/docs/concepts/yaml-references#use-environment-files)
for what those files are for.

To grow the project later, see [Add a source and its tables](/docs/how-to/add-a-source).

## Review and generate

From the project folder, run `ingestron plan --no-diff`, or use
**Ingestron: Plan** in VS Code. A new project or an unchanged download has no
generated files yet, so the plan lists every file as one to create, after a
warning for each value still `REPLACE_ME`. After reviewing the plan, run Apply to write the files; see
[Plan, apply and review](/docs/how-to/plan-and-generate).

Inspect the source objects, credential references, landing paths and
destination names in the generated files. Generation validates the
definitions; neither creation nor Apply connects to the source or deploys
anything.
