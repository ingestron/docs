---
title: Write a transform
description: Build a table from other tables with SQL on DuckDB, Synapse or Databricks, or with PySpark on Databricks.
---

A transform builds one table from tables your flows or other transforms
produce. It lands in the [second layer](/docs/concepts/layers), `silver` by default,
unless it sets `layer`. Its code runs on the engine that keeps the table, so you write that
engine's SQL: DuckDB's with [`duckdb-sql`](/docs/reference/packs/duckdb#duckdb-sql),
T-SQL with [`synapse-sql`](/docs/reference/packs/synapse#synapse-sql), and
Databricks SQL with [`sql`](/docs/reference/packs/databricks#sql), or Python
with [`pyspark`](/docs/reference/packs/databricks#pyspark). A transform names
its method with `transform.uses`. Without it, the first of these that applies
chooses: a matching rule of the standard, a matching rule of a pack, the
standard's default, then the default of the first pack that has one.

## Leave out the code [#without-code]

A transform with one input can leave out `code`. It then reads every column of
its input, `SELECT * FROM {{ tables.<input> }}`, and keeps the columns its
contract names. Use it for a table that only cleanses, checks or keeps
another, such as a silver copy of the first project's orders, saved as
`transforms/orders_clean.yaml`:

```yaml
apiVersion: ingestron.io/v1
kind: Transform
id: orders_clean
inputs: [orders]
contract: shop.orders
cleanse:
  columns:
    customer: { trim: true, empty: null }
```

A transform with any other number of inputs needs its code
([`TRANSFORM_CODE`](/docs/reference/errors#TRANSFORM_CODE)).
[Cleanse data in the right layer](/docs/how-to/cleanse-data) builds this table
and runs it.

## What each engine makes of it

On DuckDB, the transform is a table, built again each run from its query,
with each column cast to the contract's type, and published as Parquet:

<Example name="duckdb" file="build/duckdb/dev/tables/silver.customer_totals.sql" />

A cast can change a value: a timestamp with a time zone loses its offset when
the contract says `timestamp`, and a `timestamptz` shows the time in the
session's time zone; a decimal rounds when the contract says `integer`. Give
the contract the type you want to keep.

On Databricks, it is a materialised view:

<Example name="layers-and-transforms" file="build/databricks/src/sales/silver/store_sales.sql" />

On Synapse, it is a view over its inputs' views, in `synapse/views.sql`. A view
keeps no rows and reads its inputs each time a report queries it. Its SQL sits
inside the view, so it cannot start with `WITH` (write a common table
expression as a subquery in `FROM`) or end with `ORDER BY`, and it names only
tables listed in `inputs`. A view cannot merge changes or keep history; see
[Keep a table current](/docs/how-to/keep-a-table-current#on-synapse).

## Read a table another team owns

`inputs` are tables the project builds. To read a table that already exists,
such as reference data another team keeps, write its name as a value in the
code. Give the value in `project.yaml`, with a different name per environment
where it differs:

<Example name="existing-tables" file="project.yaml" />

<Example name="existing-tables" file="transforms/store_sales.sql" />

Ingestron never creates or changes that table. On Databricks, the part of the
name that differs between environments is read from the pipeline's
configuration, and each target of the bundle sets it:

<Example name="existing-tables" file="build/databricks/src/sales/silver/store_sales.sql" />

<Example name="existing-tables" file="build/databricks/databricks.yml" pick="targets" />

A value that `project.yaml` does not have is an error
([`UNKNOWN_CODE_VALUE`](/docs/reference/errors#UNKNOWN_CODE_VALUE)), so a
misspelt name never reaches the generated files. Other `${…}` in the code,
such as a SQL parameter, stay as written.

## In PySpark

On Databricks, set `transform: { uses: pyspark }` and define a function
`transform(tables)`. `tables` is a dictionary of DataFrames keyed by input
name, such as `tables["invoices"]`; the function returns one DataFrame:

<Example name="pyspark" file="transforms/monthly_revenue.py" />

<Example name="pyspark" file="transforms/monthly_revenue.yaml" />

Ingestron resolves `${values.…}` references in the code, then wraps it as a
materialised view with
the table's name, comment, clustering and checks. A name the wrapper writes
that differs between environments, such as a schema, is read from the
pipeline's configuration with `spark.conf.get`; a value in the transform's own
code must be the same in every environment for now
([`ENVIRONMENTS_DIFFER`](/docs/reference/errors#ENVIRONMENTS_DIFFER)):

A transform that reads itself, directly or through others, is an error
([`INPUT_CYCLE`](/docs/reference/errors#INPUT_CYCLE)). When the query's outer
`SELECT` names its columns, they are compared with the contract's, and a
column one has and the other lacks is a warning
([`TRANSFORM_COLUMNS`](/docs/reference/errors#TRANSFORM_COLUMNS)).
