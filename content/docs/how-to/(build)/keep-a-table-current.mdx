---
title: Keep a table current
description: Keep the current row for each key, or every version, from loads of changed rows on DuckDB or Databricks.
---

Use this when each load brings rows that change rows the table already has:
a key, a column that orders the changes, and sometimes a condition that says
which rows are deletions. Three words of [intent](/docs/reference/intent) say
what the table keeps:

- `history: latest` keeps the current row per key, and `history: full`
  every version;
- `sequence` names the column that orders a key's changes;
- `load: { deletes: { when } }` is a SQL condition that is true for a row
  deleted at the source.

Write them on a flow for every table of the flow, on a table for that table
alone, or `history` on a layer of the standard for every table in it. They
need the contract to mark the key with `primaryKey: true`; see
[Describe a table with a contract](/docs/how-to/write-a-contract#keys-and-required-columns).

## On DuckDB

`duckdb-table` replaces the table with the files' rows each run, unless the
table keeps history. To keep one row per order, the latest by `ordered_at`,
give the orders table in the [DuckDB starter](/docs/start/first-project)'s
`flows/orders.yaml` this intent:

```yaml
# flows/orders.yaml
tables:
  orders:
    object: orders.csv
    contract: shop.orders
    history: latest
    sequence: ordered_at
```

Each run then inserts each key's latest row, by `sequence` and then by file
name, and replaces the row the table had for that key: the method's
`mode: upsert`. Set `sequence` when one file can hold a key twice. Running
again is safe in every mode. A changed primary key or column type needs the
table built again: delete `ingestron.duckdb` and run again, which reloads
everything from the files. Every setting is listed under
[`duckdb-table`](/docs/reference/packs/duckdb#duckdb-table).

The method also has a `mode` that no intent stands for, `append`.
`append` adds each file's rows once: it reads each file name once, so a file
re-exported under the same name is skipped and its new rows are not loaded.
Give a re-export a new name, or delete `ingestron.duckdb` and run again to
reload every file. In Azure each run starts with an empty database, so every
file is read. A copy that replaces its file under the same name each load
cannot be appended; see
[Append would miss later loads](/docs/troubleshooting#append-would-miss-later-loads).

## On Synapse

A Synapse view reads the landed files each time a report queries it, so it
shows them as they are: it cannot merge changes or keep history. To keep
current rows, keep the table with DuckDB, whose tables are published as files,
and serve it with `synapse-serve`; see [Views or tables](/docs/platforms/synapse#views-or-tables).

## When ADF lands the rows

ADF copies the rows; the pack that stores the table keeps it current. A
native table copy lands the whole selection each window, so a row missing
from a later copy does not mean it was deleted. See
[Choose the source and its tables](/docs/platforms/adf#choose-the-source-and-its-tables).
