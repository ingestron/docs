---
title: Check generated files in CI
description: Fail a pull request when someone changed the definitions without generating, with GitHub Actions or Azure DevOps.
---

Commit the `build/` folder with your definitions. In CI, run `ingestron check`
from the definitions project folder on every pull request: it fails when
someone changed the definitions without generating, so the files you deploy
are always what the definitions say. It needs only Node.js 22.13 or later:
each template installs an exact version of the command from npm,
`npm install -g ingestron@2.1.0`, then runs it. Change the version when you
upgrade, as
[Upgrade Ingestron and its packs](/docs/how-to/upgrade#choose-the-version-you-run)
shows, so a new release never fails a pull request that changed nothing.

To deploy what the check passed, one environment after another, see
[Deploy through environments](/docs/how-to/deploy-through-environments): its
pipelines run this check first.

## GitHub Actions

Save as `.github/workflows/ingestron-check.yml`:

<Template
  file="github-actions/ingestron-check.yml"
  from="# Fails the build"
  to="- run: ingestron check"
/>

## Azure DevOps

Save as `ingestron-check.yml` and add it as a pipeline:

<Template
  file="azure-devops/ingestron-check.yml"
  from="# Fails the build"
  to="displayName: ingestron check"
/>

## Give the check its variables

The check needs no deployment values: for Databricks, Data Factory and
Synapse, a value written as `${envvar:NAME}` is supplied when deploying, not
read when generating. Only DuckDB and data product passports read such values
when generating. If they do, set `NAME` in the pipeline's variables and pass
it to the step that runs `ingestron check`. A value in the process environment
wins over `.env` files, and `.env` files are not committed, so CI has none.
See [Environment files](/docs/concepts/yaml-references#use-environment-files).

## Run it locally

Both files, and the deploy pipelines, are in the
[`ci-templates/`](https://github.com/ingestron/docs/tree/main/ci-templates)
folder of this site's repository. Locally, after
[installation](/docs/start/install), use the equivalent command:

<ToolSteps>
<Tool name="CLI">

```sh
ingestron check
```

</Tool>
<Tool name="VS Code">

Run **Ingestron: Check** from the Command Palette (⇧⌘P on macOS, Ctrl+Shift+P elsewhere) before you commit. The result is in the Ingestron output panel. Use the command in CI itself.

/>

</Tool>
</ToolSteps>

It writes nothing. It prints `up to date` for each output folder, such as
`databricks: up to date`, and exits with `0`. It exits with `1` when:

- a value is still `REPLACE_ME`, as `ingestron init` writes it where it cannot
  know the value. `plan` and `apply` only warn about it; `check` reports it as
  [`REPLACE_ME`](/docs/reference/errors#REPLACE_ME), an error, so nothing
  deploys with one. Write it, as the project's `README.md` says.
- the output differs from what the definitions generate today. It lists
  what differs; run `ingestron apply` locally and commit the result.
- a file in an output folder was not generated, such as a SQL file someone
  added beside the generated ones. A pipeline that reads the whole folder
  would deploy it too:

  ```text
  databricks: not generated  src/retail/bronze/extra.sql
  ```

  Move the file out of `build/`, or put what it does into the definitions.
  Run `ingestron check --allow-extra` only if you keep your own files there
  on purpose.

- a folder under `build/` was generated before but is not any more, for
  example after you remove a platform's last table, or after upgrading from
  the folder per environment of version 1:

  ```text
  build/prod: no longer generated. Delete the folder, or delete its .generated.json to keep it as your own.
  ```

  Ingestron never deletes it for you. Stop anything that deploys from it,
  then delete it.

A project with a self-hosted integration runtime also prints its
[`PACK_NOTICE`](/docs/reference/errors#PACK_NOTICE) warning on every check,
under `adf: warnings`; it does not fail the check.

`check` compares files. It does not say that the platform accepts them or
that anyone approved them; keep code review for that.
