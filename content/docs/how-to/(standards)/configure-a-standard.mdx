---
title: Set your organisation's standard
description: Write one standard every project follows, start each project from it, and keep projects to it.
---

A standard is one file, `standard.yaml`, that says how your organisation
builds data projects: the packs, names, layers and column types, default
settings, the settings no project may change, and what every data product
must declare. Each project holds a copy. VS Code marks a definition that
breaks it as you type, `ingestron plan` reports it, `ingestron check` fails
in CI, and nothing is generated until it is fixed.

To make every project follow your rules:

1. Write the standard and try it on a project.
2. Start each project from it, from a file or a Git repository.
3. Keep projects to it: `ingestron check` in each project's CI, and a review
   of changes to the copy.
4. Answer each project's [platform request](/docs/how-to/ask-the-platform-team),
   and [upgrade](/docs/how-to/upgrade) on purpose.

## What a standard holds [#what-a-standard-holds]

This is Acme's standard. Its naming, types and storage choices belong to
Acme; the way defaults and fixed settings work is the same for every pack.

<Example name="standards-and-conventions" file="standard.yaml" />

From top to bottom:

- **Packs:** the packs every project uses, each with its major version. The
  first gives the defaults. See
  [Standards, packs and methods](/docs/concepts/standards-and-packs).
- **Naming:** one `acme` catalog; a schema per environment and layer, such
  as `prod_raw`; flow tables prefixed with their source, such as
  `web__visits`; the pipeline keeps the pack's name, the project's id. See
  [Name tables and resources](/docs/how-to/name-things-your-way).
- **Layers:** `raw`, `curated` and `published` instead of the default ones.
  See [Layers](/docs/concepts/layers).
- **Types:** numbers become `DECIMAL(38,6)` unless a contract says
  otherwise. See [Give each column a type](/docs/how-to/write-a-contract#give-each-column-a-type).
- **Ingest settings:** unexpected columns in files are kept aside in a
  rescue column instead of changing the table.
- **Store:** only streaming tables are allowed (`allowed`); each one gets two
  table properties (`settings`); clustering is fixed to automatic (`fixed`).

A standard can also choose methods with `when` rules (see
[How a method is chosen](/docs/concepts/standards-and-packs#how-a-method-is-chosen)),
set what happens to rows that fail a check (`quality`), and require
[governance of data products](#require-governance-of-data-products).
[Which setting wins](/docs/concepts/settings) explains what happens when a project
sets one too.

## One standard for several packs

A project has exactly one standard, even when it uses several packs. Each
method's settings stay under the method's id, so configuring one method does
not configure another. This standard copies with Azure Data Factory and
stores with Databricks:

`ingest.allowed` permits the selected copy method; `ingest.settings.adf-table`
supplies its schedule. `store.allowed` and `store.fixed.streaming-table` control
the downstream table. `naming` controls its Databricks names; ADF methods use
[resource names](/docs/how-to/name-things-your-way#adf-resource-names) instead. Check

route uses.

## Put settings with their owner

| Responsibility                  | Definition location                            |
| ------------------------------- | ---------------------------------------------- |
| Shared policy and defaults      | Standard, under the relevant action and method |
| Shared infrastructure           | Platform, under `settings.<method>`            |
| Source access                   | Connection `settings`                          |
| Extraction choices              | Flow `ingest.with`                             |
| One table's overrides           | The table's `ingest.with` or `store.with`      |
| Reusable and environment values | Project `values` and environment overrides     |

The [YAML reference syntax](/docs/concepts/yaml-references) connects reusable
values to these settings. The method reference identifies required fields and
their intended location.

### Generate


</Tool>
<Tool name="VS Code">

Run **Ingestron: Apply** from the Command Palette (⇧⌘P on macOS, Ctrl+Shift+P elsewhere). The output is in the Ingestron output panel. Problems show in the Problems panel as you type, before you plan.

</Tool>

Open a generated table in `build/databricks/src/` and find each rule from the
standard in it: the names, the types, the properties and the clustering. The
schema differs between environments, so the table names it as a value each
target of `build/databricks/databricks.yml` sets.

### Break a rule

At the end of `flows/web.yaml`, add a store setting the standard fixes, as
in the download's `exercises/fixed-setting.yaml`:

<Example name="standards-and-conventions" file="exercises/fixed-setting.yaml" />

Plan again:

```sh
ingestron plan
```

```text
dev, prod: the definitions have problems
flows/web.yaml:10:23  error  FIXED_SETTING
  The standard fixes "cluster_by" to "auto".
  Remove this setting, or change the standard.
  Fix: Remove this setting.
```

Each environment is checked and reported. The line and column point at the
value you added. Remove it; in VS Code, the quick fix **Remove this setting**
does it for you. See [`FIXED_SETTING`](/docs/reference/errors#FIXED_SETTING).

## Start each project from it

A new project takes your standard in place of the one its starter or route
comes with. `init` copies it into the project as `standard.yaml`, with a first
line saying where it came from, and checks every environment before it writes
anything.

<ToolSteps>
<Tool name="CLI">

Pass `--standard` with a path or a Git URL. A relative path is resolved from
your shell's current folder:

```sh
ingestron init sales --connector postgresql --connectivity private --via adf-databricks \
  --standard ../platform/standard.yaml --yes
```

The new `sales/standard.yaml` starts with `# From ../platform/standard.yaml`.
To take it from a Git repository instead, see
[Share templates and standards](/docs/how-to/share-a-template#share-a-standard).

</Tool>
<Tool name="VS Code">

**Ingestron: New project** keeps the starter's or route's own standard. To
start from yours, run `ingestron init` with `--standard` in a terminal, or
replace the new project's `standard.yaml` with your standard and plan.

</Tool>
</ToolSteps>

The copy does not follow the original. To give a project a newer version,
replace its `standard.yaml` in a pull request and plan: the plan shows every
generated file the change affects.

## Keep projects to it

- **In CI.** A definition that breaks the standard, such as a fixed setting
  changed or a method it does not allow, stops `ingestron check`, so the pull
  request fails. Add the check to every project as in
  [Check generated files in CI](/docs/how-to/check-in-ci).
- **In review.** The copy is a file in the project's repository, so a project
  can change it, and its `platform.yaml` can
  [change its names](/docs/how-to/name-things-your-way#one-project-names).
  Ask for the platform team's review of changes to both files, for example
  with your Git host's code owners.

## Require governance of data products

A `governance` section makes every data product state its owner and purpose,
classify each column it publishes, and say who may use sensitive data. A
product that breaks a rule stops generation, so the pull request fails. See
[Define a data product](/docs/how-to/define-a-data-product).
