Ingestron names each table, and on Databricks the pipeline and the refresh
job, from patterns. The packs have default patterns; the standard's `naming`
replaces them with your organisation's. ADF's linked services, datasets,
pipelines and triggers have names of their own, set with `resource_names`. The names are in the generated
files, so `plan` shows them for review before anything is deployed.

## What each pack names

Without `naming`, the standard's first pack gives these patterns. A standard
that sets only some of them keeps the pack's for the others.

<PackNaming />

- **Databricks** uses all five: `catalog.schema.table` for each table, the
  pipeline that builds them, and the refresh job.
- **Synapse serverless** creates each view in the catalog, which is the
  serverless database, under its schema and table name.
- **DuckDB** uses the schema and table name for each table, and for the
  Parquet file it publishes, `<schema>.<table>.parquet`.

Azure Data Factory names its own resources differently; see
[ADF resource names](#adf-resource-names).

## Keep names valid

Every name must be lowercase letters, digits and underscores, and start with
a letter or underscore
([`BAD_NAME`](/docs/reference/errors#BAD_NAME)). Use a filter such as
`downcase` when a value might not be. A pattern with an unknown variable is
an error ([`BAD_PATTERN`](/docs/reference/errors#BAD_PATTERN)), so a typo
cannot quietly give a valid but wrong name. Two tables with the same full
name are an error too
([`DUPLICATE_NAME`](/docs/reference/errors#DUPLICATE_NAME)).

## One project's names [#one-project-names]

A project's platform document can have its own `naming`. Each pattern it
sets replaces the standard's for that project; the others still come from
the standard. `fixed` holds only method settings, so a standard cannot stop
this. If every project must keep your names, review changes to
`platform.yaml` as you review changes to `standard.yaml`.

## ADF resource names

ADF linked services, datasets, pipelines, triggers and activities are named by
the copy method's `resource_names` setting, not by the patterns above. They
have their own defaults and validation rules. Set `resource_names` under the
selected method's settings. Leave a role out to keep its default; override only
the names you need.

ADF resource names use resolved YAML values such as `${project.id}`,
`${environment.name}` and `${values.resource_prefix}`; the table variables
above are not available there. Changing `naming.pipeline` does not rename an
ADF pipeline.

### Choose where the name belongs

| Scope                                          | Where to put `resource_names`                              |
| ---------------------------------------------- | ---------------------------------------------------------- |
| Organisation default for one method            | `standard.yaml`: `ingest.settings.<method>.resource_names` |
| Shared project resources                       | `platform.yaml`: `settings.<method>.resource_names`        |
| A source's pipeline, trigger or linked service | A flow's `ingest.with.resource_names`                      |
| A per-table resource or Copy activity          | The table's `ingest.with.resource_names`                   |

Use the actual method ID: `adf-copy`, `adf-table` or `adf-files`. A preset for
one method is not applied to the others. See the
[resource-name roles and defaults](/docs/reference/packs/adf#adf-table-resource-names)
for the complete list and each resource's sharing rules.

Tables sharing a generated resource must resolve to the same name, even
when settings come from different flows or methods. Source linked services
and pipelines also have grouping rules: a table-level override cannot split
a resource that is shared per connection or database.

### Give the pipeline an environment-specific name

The project sets `values.resource_prefix` to `sales`. Its PostgreSQL flow
uses that value and the selected environment:

<Example name="connection-first-adf" file="flows/postgresql.yaml" />

Plan produces `pl_sales_orders_dev` and `pl_sales_orders_prod`, with matching
trigger references. `copy_orders` names the Copy activity inside the pipeline.
The flow leaves out the source linked service and dataset roles, so they keep
their default names.

Separate `build/dev/` and `build/prod/` folders do not by themselves make the
ADF resource names different. If environments share a factory, use
`${environment.name}` for resources that must be separate and choose shared
names deliberately.

Known roles for resources a source does not generate are accepted but unused.
A Snowflake staging name does not create staging for another source. Unknown
roles, invalid names, conflicting shared names and case-insensitive collisions
stop generation. The reference lists the accepted characters and length limit.

### Review a rename before applying

<ToolSteps>
<Tool name="CLI">

```sh
ingestron plan --env dev --no-diff
ingestron apply --env dev --no-diff
ingestron check --env dev
```

</Tool>
<Tool name="VS Code">

Select **dev** with **Ingestron: Select environment**, then run
**Ingestron: Plan**. Review the changes before **Ingestron: Apply** and
**Ingestron: Check**.

</Tool>
</ToolSteps>

Open `build/dev/adf/pipeline/pl_sales_orders_dev.json`. The matching trigger
is `build/dev/adf/trigger/tr_sales_orders_dev.json`; its pipeline reference
uses the chosen name. Linked services and datasets follow their chosen names
in the same way.

For a safe rename exercise, change `values.resource_prefix` in `project.yaml`
from `sales` to `sales_v2` and run Plan. Expect new pipeline and trigger files
and removal of the previously generated ones. Apply uses the existing
ownership manifest and refuses to overwrite hand edits.

Removing an owned local file does not delete a resource already published to
the factory: review that change when you [publish](/docs/platforms/adf#publish),
and choose the destination factory then. The integration runtime and
credential references come from the method and connection settings;
`resource_names` names only the resources this pack generates.

## Check a change of names

Change a pattern, then plan. For example, add `_ingest` to the pipeline's
name in the standard:

```yaml
naming:
  pipeline: "{{ project }}_{{ environment }}_ingest"
```

<ToolSteps>
<Tool name="CLI">

```sh
ingestron plan --env prod --no-diff
```

</Tool>
<Tool name="VS Code">

Select `prod` in the status bar and run **Ingestron: Plan** from the Command Palette (⇧⌘P on macOS, Ctrl+Shift+P elsewhere). The output is in the Ingestron output panel.

</Tool>
</ToolSteps>

The pipeline's files are named after it, so they move:

```text
prod → build/prod
delete    resources/marketing_prod.pipeline.yml
create    resources/marketing_prod_ingest.pipeline.yml
delete    src/marketing_prod/raw/campaigns.sql
delete    src/marketing_prod/raw/visits.sql
create    src/marketing_prod_ingest/raw/campaigns.sql
create    src/marketing_prod_ingest/raw/visits.sql

7 files: 3 create, 3 delete, 1 unchanged. Ready to apply.
```

Ingestron renames files, not data. When a table's or pipeline's name changes,
what happens to the old one on the platform depends on how you deploy, so
review the deletes before you apply.
