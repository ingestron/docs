title: Name tables and resources
description: Set the catalog, schema, table, pipeline and job names every project gets, name ADF's resources, and see the names before anything is deployed.

Ingestron names each table, and on Databricks the pipeline and the refresh
job, from patterns. The packs have default patterns; the standard's `naming`
replaces them with your organisation's. ADF's linked services, datasets,
pipelines and triggers have names of their own, set with `resource_names`. The names are in the generated
files, so `plan` shows them for review before anything is deployed.

Catalogs, schemas and tables may be named differently in each environment.
The pipeline and the job may not: the bundle's files and resource keys are
named after them, so a `pipeline` or `job` pattern that uses
`{{ environment }}` is
[`ENVIRONMENTS_DIFFER`](/docs/reference/errors#ENVIRONMENTS_DIFFER).

Patterns use [Liquid](https://shopify.github.io/liquid/) and these
variables:

<NamingVariables />

`{% if source %}` works because a variable a table does not have is empty: a
transform's table has no source, so it keeps its own name. These
`{{ … }}` patterns are not the `${…}` references used everywhere else in the
YAML; see [YAML references](/docs/concepts/yaml-references).

## What each pack names

Without `naming`, the standard's first pack gives these patterns. A standard
that sets only some of them keeps the pack's for the others.

<PackNaming />

- **Databricks** uses all five: `catalog.schema.table` for each table, the
  pipeline that builds them, and the refresh job.
- **Synapse serverless** creates each view in the catalog, which is the
  serverless database, under its schema and table name.
- **DuckDB** uses the schema and table name for each table, and for the
  Parquet file it publishes, `<schema>.<table>.parquet`.

Azure Data Factory names its own resources differently; see
[ADF resource names](#adf-resource-names).

## Keep names valid

Every name must be lowercase letters, digits and underscores, and start with
a letter or underscore
([`BAD_NAME`](/docs/reference/errors#BAD_NAME)). Use a filter such as
`downcase` when a value might not be. A pattern with an unknown variable is
an error ([`BAD_PATTERN`](/docs/reference/errors#BAD_PATTERN)), so a typo
cannot quietly give a valid but wrong name. Two tables with the same full
name are an error too
([`DUPLICATE_NAME`](/docs/reference/errors#DUPLICATE_NAME)).

## One project's names [#one-project-names]

A project's platform document can have its own `naming`. Each pattern it
sets replaces the standard's for that project; the others still come from
the standard. `fixed` holds only method settings, so a standard cannot stop
this. If every project must keep your names, review changes to
`platform.yaml` as you review changes to `standard.yaml`.

## ADF resource names

ADF linked services, datasets, pipelines, triggers and activities are named by
the copy method's `resource_names` setting, not by the patterns above. They
have their own defaults and validation rules. Set `resource_names` under the
selected method's settings. Leave a role out to keep its default; override only
the names you need.

ADF resource names use resolved YAML values such as `${project.id}` and
`${values.resource_prefix}`; the table variables above are not available
there. Changing `naming.pipeline` does not rename an ADF pipeline. Each name
must be the same in every environment, because one ARM template is deployed
to each environment's factory: a name holding `${environment.name}`, or a
value that differs, is
[`ENVIRONMENTS_DIFFER`](/docs/reference/errors#ENVIRONMENTS_DIFFER).

### Choose where the name belongs

| Scope                                          | Where to put `resource_names`                              |
| ---------------------------------------------- | ---------------------------------------------------------- |
| Organisation default for one method            | `standard.yaml`: `ingest.settings.<method>.resource_names` |
| Shared project resources                       | `platform.yaml`: `settings.<method>.resource_names`        |
| A source's pipeline, trigger or linked service | A flow's `ingest.with.resource_names`                      |
| A per-table resource or Copy activity          | The table's `ingest.with.resource_names`                   |

Use the actual method ID: `adf-copy`, `adf-table` or `adf-files`. A preset for
one method is not applied to the others. See the
[resource-name roles and defaults](/docs/reference/packs/adf#adf-table-resource-names)
for the complete list and each resource's sharing rules.

### Name a source's pipeline [#name-a-sources-pipeline]

<OldAnchor id="give-the-pipeline-an-environment-specific-name" />

The project sets `values.resource_prefix` to `sales`. Its PostgreSQL flow
uses that value for the pipeline and its trigger:

<Example name="connection-first-adf" file="flows/postgresql.yaml" />

Plan produces `pl_sales_orders`, and a trigger that runs it. `copy_orders`
names the Copy activity inside the pipeline. The flow leaves out the source
linked service and dataset roles, so they keep their default names. Each
environment has a factory of its own, so the names need not differ between
environments to keep them apart.

Known roles for resources a source does not generate are accepted but unused.
A Snowflake staging name does not create staging for another source. Unknown
roles, invalid names, conflicting shared names and case-insensitive collisions
stop generation. A name is at most 140 characters, and a Copy activity's 55,
as Microsoft's build accepts; a longer default name is refused with the role
to set. The reference lists the accepted characters.

The integration runtime and credential references come from the method and
connection settings; `resource_names` names only the resources the ADF pack
generates.

## Check a change of names

Change a pattern, then plan. For example, add `_ingest` to the pipeline's
name in the standard:

```yaml
naming:
  pipeline: "{{ project }}_ingest"
```

<ToolSteps>
<Tool name="CLI">

```sh
ingestron plan --no-diff
```

</Tool>
<Tool name="VS Code">

Run **Ingestron: Plan** from the Command Palette (⇧⌘P on macOS, Ctrl+Shift+P elsewhere). The output is in the Ingestron output panel.

</Tool>
</ToolSteps>

The pipeline's files are named after it, so they move:

```text
databricks → build/databricks (dev, prod)
delete    resources/marketing.pipeline.yml
create    resources/marketing_ingest.pipeline.yml
delete    src/marketing/raw/campaigns.sql
delete    src/marketing/raw/visits.sql
create    src/marketing_ingest/raw/campaigns.sql
create    src/marketing_ingest/raw/visits.sql

7 files: 3 create, 3 delete, 1 unchanged. Ready to apply.
```

<OldAnchor id="review-a-rename-before-applying" />

An ADF name changes the same way. In the finished PostgreSQL project, change
`values.resource_prefix` in `project.yaml` from `sales` to `sales_v2` and
plan: Plan deletes `factory/pipeline/pl_sales_orders.json` and
`factory/trigger/tr_sales_orders.json` and creates `pl_sales_v2_orders.json`
and `tr_sales_v2_orders.json` in their place, and the new trigger runs the new
pipeline.

Ingestron renames files, not data, so review the deletes before you apply. On
the platform, a deployment creates the renamed resource and removes the old
one: the bundle's deploy deletes the old pipeline, and Data Factory's
post-deployment script deletes the old pipeline and trigger. A renamed
tumbling window trigger runs its past windows again from `start`, so move
`start` to the next window first; see
[Deploy](/docs/platforms/adf#deploy).
