The packs come inside the `ingestron` command: each release of the command
includes one version of every pack. A newer release can change the files the
packs generate, so upgrade on purpose, in a pull request, where `plan` shows
the change and `check` proves it is complete. Coming from 1.x, read
[Upgrade from 1.x to 2.0](#upgrade-to-2) first.

## What the standard pins

The standard's `packs` names each pack with its major version:

<Example name="duckdb" file="standard.yaml" />

`duckdb@2` accepts every DuckDB pack whose major version is 2. A new major
version is a new name, and the command checks it. When the standard names a
major the command's pack does not have, nothing is generated. In the
[first project](/docs/start/first-project), whose command has DuckDB pack 2,
changing the line to `duckdb@3` makes `ingestron plan` stop at:

```text
dev: the definitions have problems
standard.yaml:4:9  error  WRONG_PACK
  This standard is for "duckdb@3", but the pack is duckdb@2.
```

A standard that names the major before the command's, such as `duckdb@1`,
stops with [`PACK_VERSION`](/docs/reference/errors#PACK_VERSION) instead, with
a fix that changes it; see [Upgrade from 1.x to 2.0](#upgrade-to-2). A release
in the same major keeps the name, so the standard needs no change, but the
files it generates can still differ, for example by a new cast in a table's
SQL.

[Versions](/docs/reference/versions) lists the command and pack versions
these pages describe.

## Choose the version you run

A new release can change the files the packs generate, and then
`ingestron check` fails on a pull request that changed nothing. So install an
exact version, in CI and on each of your computers, and change it when you
choose to upgrade. The [CI templates](/docs/how-to/check-in-ci) and the
[deployment templates](/docs/how-to/deploy-through-environments) do:

```sh
npm install -g ingestron@2.3.0
```

`npm ls -g ingestron` shows the version a computer has installed.

The VS Code extension carries its own copy of the command: the version its
own repository locked when you built it, which need not be the one you pin.
Once you have applied with the command, **Ingestron: Plan** in VS Code should
list no changes; if it does, the two versions differ.

## Upgrade in a pull request

1. On a new branch, change the version in CI and on your computer.
2. Plan with the new version:

   ```sh
   ingestron plan
   ```

   Each file the new version writes differently is an `update`, with its
   line differences, and files it adds or no longer writes are a `create` or
   a `delete`. Review them as you would review a change to the definitions.

3. If the plan reports
   [`PACK_VERSION`](/docs/reference/errors#PACK_VERSION), apply its fix, which
   changes the major version in the standard's `packs`. Fix any other problem
   the plan reports.
4. Apply, and commit the generated files with the version change:

   ```sh
   ingestron apply
   ```

5. Open the pull request. `ingestron check` in CI runs the new version and
   passes, because the committed files are what it generates.

Deploy the changed files as you deploy any other change.

## Upgrade from 1.x to 2.0 [#upgrade-to-2]

Version 1 wrote a complete copy of each platform's files for each environment,
in `build/<environment>/`. Version 2 writes one set of files per platform for
every environment, in `build/<pack>/`, laid out as each platform's CI/CD tools
expect; see [Where the files go](/docs/concepts/generated-files#where-the-files-go).
A deployment pipeline promotes the same files from one environment to the
next; see [Deploy through environments](/docs/how-to/deploy-through-environments).

### The standard and the folders

1. Install `ingestron@2.3.0` and plan. Every pack is version 2, so a standard that
   names `databricks@1`, `adf@1`, `synapse@1` or `duckdb@1` stops with
   `PACK_VERSION`, once for all the environments that have it:

   ```text
   dev: the definitions have problems
   standard.yaml:4:9  error  PACK_VERSION
     This standard is for "duckdb@1", but the pack is duckdb@2.
     Change it to duckdb@2; the upgrade notes say what changes in the generated files.
     Fix: Change to "duckdb@2".
   ```

   Change each to `@2`, or apply the fix in VS Code.

2. Apply. Ingestron writes `build/<pack>/`, and names each 1.x folder it no
   longer generates:

   ```text
   build/dev: no longer generated. Delete the folder, or delete its .generated.json to keep it as your own.
   ```

   `ingestron check` fails until those folders are gone, so CI cannot keep
   deploying them. Change your deployment to the new folders first, then
   delete the old ones in the same pull request. A Databricks project with
   managed schemas needs its 1.x folders for one more step first; see
   [Databricks](#databricks) below.

3. Environments may now differ only in values, such as names, paths and
   hosts. A table built in some environments only, or a resource name that
   differs, is [`ENVIRONMENTS_DIFFER`](/docs/reference/errors#ENVIRONMENTS_DIFFER),
   and every environment must resolve before anything is written. A naming
   pattern that put `{{ environment }}` in a pipeline's or job's name, or an
   ADF `resource_names` value with `${environment.name}`, needs changing.
4. `${envvar:…}` values in a Databricks, Data Factory or Synapse project are
   no longer read when generating: the deploying pipeline supplies them,
   under the names `ingestron request` lists. A variable that decides a name,
   such as a flow's `source`, is
   [`DEPLOY_VALUE`](/docs/reference/errors#DEPLOY_VALUE): write it in
   `project.yaml` for each environment. See
   [Supplied when deploying](/docs/concepts/yaml-references#supplied-when-deploying).
5. Change CI: the check templates install `ingestron@2.3.0`, and the deploy
   pipelines deploy `build/<pack>/` by target, parameter file or script, as
   [Deploy through environments](/docs/how-to/deploy-through-environments)
   shows.

`plan`, `apply` and `check` now always work on every environment together:
given `--env`, they exit with `2`. `compare` and `request` still take `--env`.

### Databricks

- One bundle in `build/databricks/`. The bundle's name, its pipeline and job
  keys, the target names and `root_path` are as in 1.x, so the first
  `databricks bundle deploy -t <environment>` updates that environment's
  resources in place, if the same identity deploys it. Run
  `databricks bundle validate` and `databricks bundle summary` first.
- **Deploy as the identity that deployed 1.x.** Without
  `databricks.workspace.root_path` in the platform, a target's deployment state is in the
  deploying identity's own folder, `~/.bundle/…` in the workspace.
  Another identity, such as the service principal of the new CI templates,
  finds no state there and creates a second copy of every pipeline and job; in
  `prod`, both copies run on schedule. `databricks bundle summary` shows the
  folder a target uses. So run the first 2.0 deploy, and the schema steps
  below, as the identity that deployed 1.x. Before deploys move to CI, set a
  shared `databricks.workspace.root_path` in `platform.yaml`, such as
  `/Workspace/Shared/.bundle/<project>/${environment.name}`, and bind each
  existing resource to it as the CI identity, as
  [Deploy as one identity](/docs/platforms/databricks-deploy#one-identity)
  shows.
- Only an environment named `dev` is in development mode; `test`, `uat`,
  `staging` and every other environment are in production mode, unless the
  platform sets `databricks.mode`. On such an environment's first 2.0 deploy, jobs and
  pipelines lose the `[dev <identity>]` prefix from their names, pipelines
  leave development, the deployment lock comes on, and production mode checks
  the deploying identity's `run_as`, `permissions` and `root_path`. To keep
  development mode there, write `mode: ${values.mode}` in the platform's
  `databricks:` section,
  `mode: production` in `project.yaml`'s `values`, and `mode: development` in
  that environment's `values`.
- With `databricks.manage.schemas`, managed schemas are keyed by layer, such as `bronze`,
  or by schema name when a layer has several, not `<catalog>_<schema>`. Each
  environment's deployment state still holds the old key, so before the first
  2.0 deploy, for each environment and managed schema, as the identity that
  deployed 1.x, and before the 1.x folders are deleted (or from the last 1.x
  commit):
  1. in the 1.x bundle's folder, `build/<environment>/`, or
     `build/<environment>/databricks/` when the standard listed several packs,
     run
     `databricks bundle deployment unbind <catalog>_<schema> -t <environment>`;
  2. in `build/databricks/`, run
     `databricks bundle deployment bind <key> <catalog>.<schema> -t <environment>`,
     with the key from `resources/schemas.yml`;
  3. run `databricks bundle validate` and `databricks bundle summary`, and
     check that the deploy deletes no schema.

  Without this, the deploy plans to delete each schema under its old key.

- `prerequisites.sql` is `prerequisites/<environment>.sql`. The after-refresh
  script moved from `src/<pipeline>/apply_contract.py`, where the pipeline
  also loaded it as its own code, to `tasks/<pipeline>/apply_contract.py`; the
  first deploy removes the old file.
- Pipeline code names tables in the pipeline's catalog with two parts, such as
  `` `bronze`.`orders` ``, and reads values that differ through the pipeline's
  configuration. A PySpark transform's own code cannot hold a value that
  differs yet, and a Kafka connection's `continuous` must be the same in every
  environment.
- Deploy with the Databricks CLI v0.264.0 or later.

### Azure Data Factory

- One factory in `build/adf/`: the factory's files in `factory/`, and
  `parameters/<environment>.json`. Deploy it as an ARM template built with
  Microsoft's npm package, with the pre- and post-deployment script; see
  [Deploy](/docs/platforms/adf-deploy#deploy). Deploying the JSON directly, through
  the REST API, `az datafactory` or a factory's Git publishing of
  `build/<environment>/adf/`, is no longer supported.
- [One factory per project](/docs/platforms/adf-deploy#one-factory-per-project):
  the post-deployment script deletes every resource in the factory that the
  template does not hold.
- Resource names are as in 1.x, so the first deployment updates each
  factory's resources in place.
- The factory now holds each integration runtime its linked services use.
  Describe a runtime linked to a shared one, or an Azure runtime's region and
  compute, with the method's `runtime` setting, and run
  `az deployment group what-if` before the first deployment. Each plan, apply
  and check prints this as a `PACK_NOTICE` warning.
- Triggers start only in `prod` and `production`, decided by the environment's
  name. A platform that set `mode: production` to start another environment's
  triggers sets `paused: false` in the copy method's settings instead.
- The PostgreSQL recipe no longer adds `_<environment>` to its names, so a
  project started from it renames its resources: the deployment creates the
  new ones and the post-deployment script deletes the old ones. A renamed
  tumbling window trigger runs its past windows again from `start`.
- Output that Microsoft's build refused is fixed, so every connector builds:
  - MongoDB, MongoDB Atlas and Azure Cosmos DB for MongoDB datasets write
    `collection`.
  - Microsoft 365 lands through a binary copy into `<object>/`, so its tables
    use `layout: increments`. Before the first 2.0 run, delete or move the
    1.x file, `<object>/<object>.json`, which matches the new location,
    `<object>/*.json`, and point its readers at that location.
  - A connection with a user-assigned managed identity needs `identity`, the
    identity's resource ID; the factory gets a credential of its own, which
    replaces one of the same name made in Data Factory Studio.
  - A resource name is at most 140 characters, and a Copy activity's 55; a
    longer default name is refused with the `resource_names` role to set.
  - `runtime.location` takes the region's display name, such as `UK South`,
    not `uksouth`.

### Synapse serverless

- One `views.sql` in `build/synapse/`, with `environments/<environment>.sql`
  for each environment. Run `sqlcmd -i environments/<environment>.sql` from
  `build/synapse/`; see [Deploy](/docs/platforms/synapse#deploy).
  `views.sql` holds sqlcmd variables, so Synapse Studio cannot run it.
- `views.sql` starts with `USE [<database>]`, also when the views are in one
  database. If you ran a 1.x `views.sql` connected to a database with another
  name than the naming gives, change the naming to that name first.
  Otherwise, view names are as in 1.x, so the first run alters each view in
  place.

### DuckDB

`duckdb@2` writes the same SQL, in `build/duckdb/<environment>/`. Run it with
`.read build/duckdb/<environment>/run.sql`, as its `README.md` now says.

### VS Code

Use version 2 of the extension with 2.0. **Ingestron: Apply** and auto-apply
write every environment, and auto-apply logs a line for each output folder.
The environment in the status bar chooses the problems, the previews and the
platform request; see [VS Code](/docs/tools/vscode).

### If you call the packages from code

The package READMEs describe each interface; these are the changes:

- **`@ingestron/cli` 2.0.0:**
  - `generatedOutputs(files, { envvars?, packs? })` replaces
    `generatedOutputs(model, environment)`. It resolves every environment and
    builds every output folder as `ingestron plan` does, and writes nothing.
    It returns `ok`, `outputs`, `environmentReports`, `packReports`,
    `deployed`, `refused` and `text`; each output has `name`, `folder`,
    `targets`, `byEnvironment`, `files` and, for a pack that builds every
    environment together, `deployValues`, with files at the paths
    `ingestron apply` writes. A pack that cannot be loaded gives `refused`,
    not an exception. The new types are `GeneratedOutput`,
    `GeneratedOutputs`, `GeneratedOutputsOptions` and `Report`.
  - `run(args, io)` returns `2` for a pack that cannot be loaded, and for
    `--env` given to `plan`, `apply` or `check`.
  - `platformRequest` and `compareEnvironments` resolve every environment
    together, and still throw for a pack that cannot be loaded: check
    `packLoadProblem(packs)` first.
  - `packs` are `databricks@2`, `adf@2`, `synapse@2` and `duckdb@2`.
- **`@ingestron/definitions` 1.10.0** adds `packLoadProblem(packs)` and the
  codes [`PACK_LOAD`](/docs/reference/errors#PACK_LOAD) and
  [`PACK_NOTICE`](/docs/reference/errors#PACK_NOTICE). `PACK_VERSION` now
  covers version 1 of every version 2 pack, which 1.9 reported as
  `WRONG_PACK`.
- **`@ingestron/authoring` 2.0.0:** `generatedFiles(project, environment)`
  gives the 2.0 paths, for the output folders that target the environment;
  `problems` adds pack notices and what generating finds, such as
  `DEPLOY_VALUE`.

## Upgrade to 2.1 [#upgrade-to-2-1]

2.1 changes `init`, what `check` finds, and Hive connections on Azure Data
Factory:

- `init` asks only what picks the project: the starter, or the connector,
  connectivity and route. It writes `REPLACE_ME`, with a comment, for each
  value it cannot know, writes `README.md` with where to find each one, and
  `--set <name>=<value>` writes one as the project is created; see
  [Create a project](/docs/how-to/start-from-a-template#write-the-values).
  A script that answered `init`'s questions on standard input gives `--set`
  instead.
- A value still `REPLACE_ME` is a [`REPLACE_ME`](/docs/reference/errors#REPLACE_ME)
  warning in `plan` and `apply`, and an error in `check`. Projects created
  before 2.1 have none.
- `ingestron request` opens with **Values to replace**, and its **Values to
  provide** says the deploying pipeline supplies each value under the name
  given.
- VS Code's **New project** asks no name, environments or standard, and
  opens the new `README.md`.
- On Azure Data Factory, a [Hive](/docs/connectors/hive) connection's
  `transport` now decides how it signs in. `Binary` connects anonymously: the
  linked service is written with `authenticationType: Anonymous` and no user
  or password, and a `Binary` connection that gives `user` or `password` is
  refused. `SASL` and `HTTP` sign in with a user and password, and need both.
  In a 2.0 project, on `Binary`, remove `user` and `password`, or set
  `transport` to the one your server uses; on `SASL` or `HTTP`, give both,
  with the password as a secret such as `${secret:hive-password}`. Then run
  `ingestron plan` to see the linked service change.
- For code that calls the packages: `@ingestron/definitions` 1.11 adds the
  `REPLACE_ME` code and the `replaceMe` resolve option, which `check` sets to
  `error`; and the CLI's `Io` gains an optional `now()`, the day `init`
  writes.

## Upgrade to 2.2 [#upgrade-to-2-2]

2.2 generates, prints and checks exactly what 2.1 does, and the VS Code
extension works as before. Only code that calls the packages changes:

- `@ingestron/core` 1.0 is the API the command is built on.
  `@ingestron/cli` now exports only `run`, `commands` and `flags`. Import
  everything else it exported in 2.1, such as `generatedOutputs`,
  `projectRoutes`, `platformRequest` and `packs`, from `@ingestron/core`,
  under the same names. The
  [`@ingestron/core` README](https://github.com/ingestron/ingestron/tree/main/packages/core)
  describes them.
- In `@ingestron/authoring`, open a project with `ProjectSnapshot.open(folder)`
  in place of `openProject`, and call the snapshot's methods. Each function
  that took the project first is now a method with the same name:
  `problems(project, "dev")` becomes `snapshot.problems("dev")`. Three are
  renamed: `projectSymbols` is `symbols`, `compareEnvironments` is `compare`
  and `platformRequest` is `request`. The
  [`@ingestron/authoring` README](https://github.com/ingestron/ingestron/tree/main/packages/authoring)
  shows an example.

## Upgrade to 2.3 [#upgrade-to-2-3]

2.3 generates the same files as 2.2 for a project that changes nothing,
apart from a data product's passport, whose Quality and Who may use it
sections are rewritten, and one fix on Databricks (below). It adds
[intent](/docs/reference/intent),
[published standards](/docs/how-to/choose-a-published-standard), layers that
say what they do, checks on every engine, cleansing, accepted warnings, and
grants, masks and row filters. It asks for some settings to be written in
their new places, and some warnings have new codes:

- **Settings that are intent.** `streaming-table`'s `mode`, `sequence_by`,
  `delete_when` and `cluster_by`, `duckdb-table`'s `mode` and `sequence_by`,
  and `adf-copy`'s `mode` and `watermark_column` mean the same as
  [intent](/docs/reference/intent#settings-that-are-intent), such as
  `history: latest` for `mode: upsert`. They still work, and `plan` reports
  each as [`SETTING_MOVED`](/docs/reference/errors#SETTING_MOVED), a warning.
  In a flow's or a flow table's `with`, its fix writes the intent and removes
  the setting; anywhere else, such as the standard, write the intent by hand.
- **The `databricks:` section.** The platform's `workspace`, `mode`, `run_as`,
  `compute`, `permissions`, `manage` and `grants` now go under `databricks:`,
  and `notifications.on_failure` becomes an email alert in `alerts`. At the
  top they still work, with a
  [`PLATFORM_FIELD_MOVED`](/docs/reference/errors#PLATFORM_FIELD_MOVED)
  warning whose fix moves each; one written in both places with different
  values is [`BAD_SETTING`](/docs/reference/errors#BAD_SETTING). See
  [the `databricks:` section](/docs/reference/packs/databricks#platform).
- **What each pack applies.** A value of intent the table's pack does not
  apply is [`NOT_APPLIED`](/docs/reference/errors#NOT_APPLIED), and with the
  standard's `features: ga`, one that needs a feature in preview is
  [`PREVIEW_FEATURE`](/docs/reference/errors#PREVIEW_FEATURE). Projects
  written before 2.3 declare no intent, so they get neither.
- **Published standards.** `ingestron init --kit` starts a project from one,
  `ingestron standard install` moves a project to another version, and
  `ingestron standard list` lists them; in VS Code, **New project** offers
  **From a published standard**. Hover a `REPLACE_ME` to see where to find its
  value.
- **Quality and cleansing.** A layer can say what it does with its rows,
  `does`; a table can cleanse its columns, keep one row per key, convert time
  zones, and keep the rows a `drop` check leaves out; and a transform with one
  input can leave out `code`. See
  [What a layer does](/docs/concepts/layers#what-a-layer-does),
  [Check data quality](/docs/how-to/add-quality-checks) and
  [Cleanse data in the right layer](/docs/how-to/cleanse-data). All of it is
  optional.
- **DuckDB and Synapse check rows where a layer says so.** They run a table's
  checks only in a layer whose `does` lists `check`, and count them, each as
  `warn`, in a `raw` one. In a layer without `does` their files are what they
  were, and each contract rule they do not run is a new warning,
  [`NOT_APPLIED`](/docs/reference/errors#NOT_APPLIED), with the hint to add
  `check` to the layer's `does`. Expect these on the first plan with 2.3; see
  [Not applied here](/docs/concepts/not-applied).
- **Table checks on DuckDB and Synapse need nothing turned on.** Where a layer
  checks, they count table checks and `unique` in their own run, whatever
  `manage.checks` says. Only Databricks needs `databricks.manage.checks`.
- **New codes for old warnings.**
  - `CONTRACT_FIELD_UNUSED` is no longer reported. A contract field the pack
    that keeps a table does not apply yet is `NOT_APPLIED` instead, judged for
    each table against that pack, not against every pack of the standard.
  - `QUALITY_RULE_NOT_CHECKED` for a check an engine cannot run, such as one
    on a table that ends at the landed files, is `NOT_APPLIED`. It stays for a
    rule no engine can check as written, such as a `custom` rule.
  - A rule that counts over all rows while `databricks.manage.checks` is off
    was `QUALITY_RULE_NOT_CHECKED`; it is
    [`CAPABILITY_OFF`](/docs/reference/errors#CAPABILITY_OFF), with the fix
    that turns checks on.
  - A flow's `expectations` on a table that Lakeflow Connect writes were an
    error; each is `NOT_APPLIED`, and so is each required column there.

  A script that looks for an old code should look for the new one.

- **Accepted warnings.** A warning you have decided to live with can be
  accepted in `platform.yaml`, with the reason; see
  [Accept a warning](/docs/how-to/accept-a-warning). An entry for
  `CONTRACT_FIELD_UNUSED` is [`ACCEPT_CODE`](/docs/reference/errors#ACCEPT_CODE),
  an error: accept `NOT_APPLIED` instead.
- **Grants, masks and row filters.** A contract's `roles`, and a layer's
  `access`, can be granted on each table; the standard's `governance` can
  make grants exact, mask columns by their classification, and filter rows.
  Databricks applies them after each refresh, with `databricks.manage.grants`,
  `masks` and `filters`; Synapse grants each view, with
  `synapse.manage.grants`. `principals` in `platform.yaml` says who each role
  is. Each switch is off by default, so the files do not change until you
  turn one on. See
  [Grant access, mask columns and filter rows](/docs/how-to/grant-access).
- **New warnings for roles.** A project whose contracts name `roles` gets a
  warning for each role on the first plan with 2.3, and the same files:
  - on Databricks or Synapse,
    [`CAPABILITY_OFF`](/docs/reference/errors#CAPABILITY_OFF), whose fix
    turns on `databricks.manage.grants` or `synapse.manage.grants`;
  - on DuckDB, [`NOT_APPLIED`](/docs/reference/errors#NOT_APPLIED): DuckDB
    has no access control.

  Masks and row filters, which only a standard written for 2.3 can give,
  warn for each classified column they mask and each filter:
  `CAPABILITY_OFF` on Databricks, and `NOT_APPLIED` on Synapse and DuckDB,
  which cannot mask or filter.
  Turn the capability on, or accept the warning with
  `about: { feature: grants }` (or `write`, `exact`, `masks` or `filters`)
  and the reason; see [Accept a gap](/docs/how-to/grant-access#accept-a-gap).
  Either way, the passport's Who may use it says which roles are granted
  and which are not enforced, and why.

- **A role's `access` is checked where it is granted.** A role whose
  `access` is neither `read` nor `write` is
  [`ROLE_ACCESS`](/docs/reference/errors#ROLE_ACCESS), an error, only on a
  table where its grant would be applied. A project that does not turn grants
  on gets no new error.
- **Tag keys Unity Catalog refuses.** With `databricks.manage.tags` on, a
  contract tag key, or the classification's tag key, holding
  `* < > % & ? \`, a control character, or a space at either end is now
  [`PACK_CHECK`](/docs/reference/errors#PACK_CHECK), an error, as `. , - = / :`
  already were. Unity Catalog refused such a key when the task ran; now
  `plan` says so first. Rename the tag.
- **A Databricks `run_as` user name with a dot.** `prerequisites/<environment>.sql`
  wrote a `run_as` `user_name` such as `first.last@example.com` as two names,
  `` `first`.`last@example.com` ``, which is not the user. It is now one
  name, `` `first.last@example.com` ``, so that file changes for such a
  project. A service principal's application ID has no dot, and is written as
  before.
- **A classified column that already has the tag key.** On Databricks, a
  column whose contract `tags` already hold the classification's tag key, and
  that has a `classification` too, was tagged with the key twice. The apply
  task now sets it once, from the `classification`, so that task changes for
  such a project.
- **`ingestron request` lists each pack's switches.** A Synapse switch is read
  from the platform's `synapse:` section and listed as
  `synapse.manage.grants`; Databricks' list is unchanged. A name holding a
  backtick is written as code with two backticks around it.

To move a project to the new places, plan with 2.3.0, apply each fix (in
VS Code, **Fix all** applies one kind at once), and plan again: the plan should
list no change to the generated files, other than the passports. Then read
what it lists under `Not applied on this platform`, and decide for each
whether to give the layer a duty, change the definitions or accept it.

For code that calls the packages:

- `@ingestron/definitions` 1.13 adds intent: `intentPaths`, `intentUseOf` and
  `intentCoverageGaps`; a pack's `intent`, and a method's `intent`,
  `intentDefaults` and `aliases`; each table's `intent` and `intentOrigins`;
  a pack's `platformSection` and `platformSectionReference`; and `find` and
  `suggest` on each `FieldInfo`.
