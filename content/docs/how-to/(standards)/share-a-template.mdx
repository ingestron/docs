A template is a project folder your team starts from, and a standard is the
one file that holds your organisation's rules. Both are plain files, so keep
them in any Git repository the people who start projects can clone.

## Share a template

A template is an ordinary project folder with one extra file,
`template.yaml`, that names it.

1. Start from a project that works: `ingestron plan` shows no problems.
2. Write `REPLACE_ME` for each value the people who start from it must give,
   with one comment line above it that says what it is. Put a value read in
   several places in `project.yaml`, and read it with `${values.…}`:

`init` asks nothing about those values: the new project's `README.md` lists each `REPLACE_ME`
with its comment, `ingestron plan` warns about each, and `ingestron check`
fails until each is written. `--set landing=<value>` writes one as the
project is created.

3. Add `template.yaml`, with the title and summary people choose it by:

<Example name="minimal" file="template.yaml" />

4. Put the folder in a Git repository your team can read. They start from it
   with its URL and the folder after `#`:

```sh
ingestron init orders --template https://github.com/acme/data-templates.git#files-to-bronze
```

`init` copies every regular file except `template.yaml`, `README.md`,
`build/`, `.generated.json`, `.git` and `.ingestron`, and refuses a template
that holds a symbolic link. Every field of `template.yaml` is in
[Starters and templates](/docs/reference/templates).

## Share a standard [#share-a-standard]

Keep your organisation's standard in its own repository, so every template
and every project takes the same one. Give `--standard` the repository's URL
and the file's path after `#`. It replaces the template's own standard:

```sh
ingestron init orders --template https://github.com/acme/data-templates.git#files-to-bronze \
  --standard https://github.com/acme/data-platform.git#standards/standard.yaml
```

The new `orders/standard.yaml` starts with a `# From` line naming that URL. It
is a copy: a later change to the repository does not reach projects already
created. [Set your organisation's standard](/docs/how-to/configure-a-standard#start-each-project-from-it)
says how to give a project a newer version, and how to keep projects to it.

**Ingestron: New project** in VS Code keeps the template's own standard; use
the command for `--standard`.

## Share a published standard [#share-a-published-standard]

To give teams a dated standard with an example that builds, as Ingestron's own
[published standards](/docs/how-to/choose-a-published-standard) are, make a
folder `<platform>/<name>/<version>/` that holds a project, and a `kit.yaml`
beside its files:

- `standard.yaml`, with `origin: { standard: <platform>/<name>, version: <version> }`
  and the same `packs` as `kit.yaml`;
- `platform.yaml` and `project.yaml`, with `REPLACE_ME` and a comment for
  each value that is the team's;
- `README.md`, which explains each choice, and becomes the project's
  `STANDARD.md`;
- the connections, flows, contracts and transforms of a small example.

`id` is `<platform>/<name>`, its platform the first pack's id; `version` is
the date it was checked, `YYYY-MM-DD`, or `YYYY-MM-DD-preview` with
`features: preview`. `requires` names the `ingestron` versions it needs, as
`>=`, `^` or `~` and a version; `replaces` names the version before it, and
`notes` says what changed, which `standard install` prints. Any other key is
refused, so a mistake shows at once.

Commit the folder, and tag the commit `<platform>/<name>@<version>`. Teams
start from it with the repository's URL, the folder after `#`, and the tag
after `@`:

```sh
ingestron init orders \
  --kit https://github.com/acme/data-platform.git#kits/databricks/acme-lakehouse/2026-11-10@databricks/acme-lakehouse@2026-11-10
```

`ingestron standard install` takes the same form. A version never changes once
tagged: publish a change as a new version, in a new folder. A published
standard from a Git URL is never listed by `standard list`.

## What Ingestron does with a Git URL

Fetching a template, a standard or a published standard is the only time
Ingestron uses the network, besides reading the catalogue's tags for
`ingestron standard list` and for a published standard named without its
version.

- Cloning uses your own `git`, so your Git credentials and settings apply. It
  takes only the latest commit of the default branch, or of the tag for a
  published standard, and runs none of the repository's hooks or
  submodules; filters from your own git settings, such as Git LFS, still
  apply. For a published standard, neither Git nor SSH asks for a password:
  they use the credentials Git and your SSH agent already have. Reading the
  catalogue's tags stops after 15 seconds, and a clone after 60 seconds.
- The part after `#` must stay inside the repository, and must be a folder
  for a template or a published standard, or a regular file for a standard.
- It never runs anything from a template, a standard or a published standard.
- A user name or token in a URL is never printed or written into the
  project.
