title: Ask the platform team
description: Write one request per environment with what the project needs from whoever runs the data platform, including the values still to provide.
---

Some features need someone who administers the data platform: grants for the
identity pipelines run as, tag policies, shared storage and runtimes, and the
values only they know. Write the request from the definitions, so it matches
what will be deployed:

```sh
ingestron request --env prod > platform-request.md
```

Without `--env`, it writes one request for each environment. In VS Code,
**Ingestron: Prepare platform request** opens the same text for the
environment in the status bar, unsaved, to review and send.

## What the request holds

Each section appears only when it has something to say, in this order:

- **Values to provide:** each environment variable the definitions read,
  where it is used, whether it is set, and the name the deploying pipeline
  supplies it as; never its value. See [Values to provide](#values-to-provide).
- The identity pipelines and jobs run as, and the workspace.
- **Switched on:** each `manage` switch the platform turns on, what it does
  and what it needs on the platform, from the pack's
  [platform prerequisites](/docs/reference/packs/databricks#platform-prerequisites).
- **Used by the definitions, but switched off:** features the definitions use
  while their switch is off, such as a contract's `unique: true` without
  `manage.checks`.
- **Shared infrastructure:** the platform's settings for the methods the
  environment uses, with this environment's values. A secret reads "a
  secret"; its value is never shown.
- Each pack's own sections, such as what must exist before deploying, the
  schedules and whether each is paused, and what Azure Data Factory, the
  Synapse database or the DuckDB job needs. Ingestron lists these from the
  definitions; it has not checked that they exist.
- **SQL to run once (review first):** the generated
  `prerequisites/<environment>.sql`.

Nothing is sent anywhere: send the request the way your team takes requests.

## Values to provide [#values-to-provide]

A value only the platform team knows, or one each stage of a deployment
supplies, such as a storage path, can come from an environment variable with
`${envvar:…}`. A variable that is not set yet does not stop the request: the
request opens by asking for it.

In the `shop` project above, read the landing folder from a variable in
`project.yaml`:

```yaml
values:
  landing: ${envvar:LANDING_PATH}
```

With `LANDING_PATH` set nowhere, `ingestron request --env dev` prints:

```text
# Platform request: shop (dev)

## Values to provide

These values come from environment variables. Set them in the pipeline that runs Ingestron for this environment, or in `.env.dev` on your own computer, kept out of Git.

The files of the packs that build every environment together take these values when deploying: the pipeline that deploys them supplies each value for each environment, under the names given.

- `LANDING_PATH`, used for `values.landing` in `project.yaml`: not set yet. The deploying pipeline supplies it as `BUNDLE_VAR_landing_path` (databricks).

Until a variable is set, this request shows it as `${envvar:NAME}`, and leaves out what cannot be worked out without it.

Until every variable is set, some checks may not have run: each pack's checks of the whole project, and each method's checks of a table that holds a variable not set. Once the values are set, run `ingestron check` to run them.

Pipelines and jobs run as the identity that deploys the bundle.

## Must exist before deploying

Ingestron has not checked these; the generated files expect them.

- Catalog `dev`, which the deploying identity can use.
- Schema `dev.bronze`, in which it can create tables and views.
- Files at `${envvar:LANDING_PATH}`, which the pipeline can read.
- Serverless compute for pipelines and jobs, turned on in the workspace.
- No workspace host is set, so `databricks bundle deploy` uses the workspace of the Databricks CLI profile that runs it.

## Schedules

- No schedule: the pipelines run only when someone starts them.
```

For Databricks, Azure Data Factory and Synapse, the generated files take such
a value when deploying, not when generating: the line names what the
deploying pipeline sets, here the bundle variable `BUNDLE_VAR_landing_path`.
For Data Factory it is the ARM template parameter to pass, and for Synapse the
sqlcmd variable. [Deploy through environments](/docs/how-to/deploy-through-environments#values-supplied-when-deploying)
shows where each goes in the pipeline.

- Each variable is listed once, with each field it feeds and its file.
- Once it is set, the line says where from: the environment Ingestron runs
  in, `.env.dev` or `.env`. This section never shows a variable's value; the
  rest of the request shows values as they resolve, as the generated files
  will.
- When a flow's `source` holds a variable that is not set, the flow's
  connection is not known, so the request names the flow and lists nothing
  its tables need, and leaves out the SQL to run once.
- A table whose contract or method holds such a variable is left out, and
  the request names it.
- Only values can wait until deploying. A variable that decides what is
  generated or what it is called, such as a flow's `source`, is refused by
  `ingestron plan` as [`DEPLOY_VALUE`](/docs/reference/errors#DEPLOY_VALUE)
  for Databricks, Data Factory and Synapse; write it in `project.yaml` for
  each environment. The request then leaves out the deploy names and says to
  run `ingestron plan`.

[Environment files](/docs/concepts/yaml-references#use-environment-files)
says how to set the variables on your computer, and
[Deploy through environments](/docs/how-to/deploy-through-environments#values-supplied-when-deploying)
how to supply them in CI.

## When the definitions have problems

Any other error stops the request. The request is then only its title and
one line, and the command exits with `1`:

```text
# Platform request (dev)

The definitions have problems; fix them first.
```

Run `ingestron plan` to see the problems. Unset variables alone never do
this: with nothing else wrong, the command exits with `0`.
