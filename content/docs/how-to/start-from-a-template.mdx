title: Create a project

A project is a folder of YAML definitions with a `project.yaml` at its root.
Create one in either of two ways:

- **From a connection:** choose the source, how it can be reached, and the
  route its data takes. The project holds only that connection, its example
  flows and contracts, and any transforms they need.
- **From a starter:** copy a complete project for a common situation, such as
  [the DuckDB starter](/docs/start/first-project), or one your organisation
  shares as a template.

Either way, the result is ordinary definitions you edit, then plan and apply.

## Start from a connection

<ToolSteps>
<Tool name="CLI">

From the parent folder where you want the project, run:

```sh
ingestron init sales
```

Choose the source category, connector, network reachability and route.
When only one route is supported, Ingestron selects it. Then enter the
project name, environments, standard and connection settings. Press Enter
to accept the default shown beside a question.

To select the connection and route with flags (`--via` is `databricks`, `adf-databricks`,
`adf-synapse`, `adf-duckdb` or `adf-landing`; see
[Choose where your data goes](/docs/start/choose-a-route)):

```sh
ingestron init sales --connector postgresql --connectivity private --via adf-databricks \
  --env dev --env prod --yes
```

This creates a project using example settings and shows its generation
plan. `--yes` accepts defaults for unanswered questions. Without a terminal
or `--yes`, a missing answer produces an error naming the flag to pass.

Use `--standard ../platform/standard.yaml` to choose your organisation's
standard. Use `--set source_server=postgres.example.invalid` to answer a
configuration question by its value key. The keys for the selected recipe
are visible under `values` in the resulting `project.yaml`; an unknown key
is rejected with the available keys.

</Tool>
<Tool name="VS Code">

Run **Ingestron: New project** from the Command Palette and choose **From a
connection**. Choose a category,
or **All sources**, then type to search connectors. Choose source
reachability and a supported ingestion route, then answer the project,
standard and configuration questions. The destination folder comes last.
Cancelling a question creates no files.

The new `project.yaml` opens when creation succeeds. The generation plan
appears in the Ingestron output panel.

</Tool>
</ToolSteps>

The questions cover the recipe's string connection, object and infrastructure
values. Nested settings, alternative authentication modes, schedules and
resource names stay editable in YAML; see [Make it yours](#make-it-yours).

## Start from a starter [#start-from-a-starter]

A starter is a complete project, often with several tables and a transform.
[Templates](/docs/reference/templates#built-in-templates) lists the starters
and what each one asks.

<ToolSteps>
<Tool name="CLI">

Name a starter, a folder or a Git URL with `--template`:

```sh
ingestron init sales --template retail
ingestron init sales --template ../templates/lakehouse
ingestron init sales --template https://github.com/acme/data-templates.git#lakehouse
```

`--template` cannot be combined with `--connector`, `--connectivity` or
`--via`. After `#` comes the folder inside the repository. Git uses your
own credentials. `--standard` and `--set` work as they do from a connection.

</Tool>
<Tool name="VS Code">

Run **Ingestron: New project** and choose **From a starter**, then the
starter. Enter the project name and environments, then a path or Git URL for
your organisation's standard, or leave it empty to keep the starter's own.
The destination folder comes last.

</Tool>
</ToolSteps>

To make a template of your own, see [Share a template](/docs/how-to/share-a-template).

### From a downloaded example

A connector's **Examples** page offers project ZIPs. Extract one into an empty
folder, and open the folder that holds `project.yaml`. The archive contains
the synthetic definitions and contracts, without generated files. Code blocks
on that page name the project and the relative path of each file shown.

A multi-connector project demonstrates several sources together. To start
with only one connection, [start from a connection](#start-from-a-connection)
instead.

You can generate an unchanged example locally without access to the source.

## Use your standard

A project has one standard, including when it uses several packs.
Creation validates every environment before writing files. See
[Configure the project standard](/docs/how-to/configure-a-standard) for
allowed methods, settings ownership and fixed policies.

## Make it yours

A new project, or an example you downloaded, holds synthetic values. Before
you deploy:

1. Replace the example hosts, accounts, objects and platform paths with yours.
   Answers to the creation questions are `values` in `project.yaml`, which the
   definition files read with `${values.…}`.
2. Keep secrets out of the YAML. Secret questions take `${secret:name}`
   references, not credentials. For ADF connections these name Key Vault
   secrets; follow the selected connector's requirements for its secret
   mechanism. See [YAML references and placeholders](/docs/concepts/yaml-references)
   for values, files and secrets.
3. Set the source objects in the flows, and adapt each contract to the columns
   and keys of its object. See [Describe a table with a contract](/docs/how-to/write-a-contract).
4. Check the environments, platform and standard. Use the connector reference
   and [Azure Data Factory](/docs/platforms/adf) for ADF infrastructure, and
   [Name resources](/docs/platforms/adf-pipelines#name-resources) for name
   defaults and overrides.
5. Arrange the source credentials and platform permissions the route needs.
   Local generation does not need them.

`init` never replaces an existing file. If any target file already exists,
it lists the clashes and writes nothing. The one exception is `.gitignore`:
`init` adds the lines that keep `.env` files out of Git, where they are missing,
and says so. See [Environment files](/docs/concepts/yaml-references#use-environment-files)
for what those files are for.

To grow the project later, see [Add a source and its tables](/docs/how-to/add-a-source).

## Review and generate

From the project folder, run `ingestron plan --no-diff`, or use
**Ingestron: Plan** in VS Code, and select `dev`. A new project or an unchanged
download has no generated files yet, so the plan lists every file as one to
create. After reviewing the plan, run Apply to write the files; see
[Plan, apply and review](/docs/how-to/plan-and-generate).

Inspect the source objects, credential references, landing paths and
destination names in the generated files. Generation validates the
definitions; neither creation nor Apply connects to the source or deploys
anything.

Continue with your route:

- [DuckDB](/docs/platforms/duckdb): build the tables on one machine.
- [Databricks](/docs/platforms/databricks): schemas, the refresh job and deploying the bundle.
- [Azure Data Factory](/docs/platforms/adf): source, runtime, schedules and
  [the generated factory](/docs/platforms/adf#generate-and-inspect).
- [Shape ADF pipelines and names](/docs/platforms/adf-pipelines): pipeline design, defaults and name overrides.
- [Browse connectors](/docs/connectors): fields and supported routes by category.
