The `ingestron` command reads a project folder and writes each platform's
files, for every environment. [Install it](/docs/start/install) first. `ingestron init` creates a
project; see [Create a project](/docs/how-to/start-from-a-template), or
[Published standards](#standard) below. Then
`ingestron plan` and `ingestron apply` are the everyday loop; see
[Plan, apply and review](/docs/how-to/plan-and-generate). In CI, run
`ingestron check`; see [Check generated files in CI](/docs/how-to/check-in-ci).

## Choose the project and the output [#choose-the-project-and-the-output]

Run the command from the folder that holds `project.yaml`. It reads the
project there and writes to `build` there. Four options adjust the run:

- `--env dev` limits `compare` and `request` to one environment; repeat it
  for more. `source` and `contract --from-metadata` take it once.
  `plan`, `apply` and `check` always work on every environment together, and
  refuse it.
- `--definitions <folder>` reads a project that is not the current folder.
- `--out <folder>` writes somewhere other than `build`.
- `--no-diff` lists changed files without their line differences.

Relative `--definitions` and `--out` paths are resolved from your current
folder, and changing `--definitions` does not move the output folder. To work
on a project from outside it, set both. From the folder above `shop`:

```sh
ingestron apply --definitions shop --out shop/build
ingestron check --definitions shop --out shop/build
```

With `--definitions shop` alone, `apply` would write `build` in the folder you
ran it from, not in `shop`.

## Published standards [#standard]

`ingestron init <folder> --kit <name>@<version>` creates a project from a
[published standard](/docs/how-to/choose-a-published-standard). `--kit` takes
the name and version, such as `duckdb/local-medallion@2026-11-10`; the name
alone, for the newest version that is not a preview among the installed
versions and the catalogue's tags (the newest installed one, with a note,
when the catalogue cannot be reached); or
`<git-url>#<folder>@<tag>`, for one kept in a Git repository. It is not
combined with `--template` or `--standard`. See
[Start from a published standard](/docs/how-to/start-from-a-published-standard).

`ingestron standard` takes one of two commands:

- `ingestron standard install <kit>` replaces the project's standard with the
  published standard's, keeping its path and `id`, and lists the published
  standard's other files that changed; it refuses a standard file with
  changes that are not committed. It exits `0` once the file is written, and
  `1` when it writes nothing. See
  [Move to a newer published standard](/docs/how-to/upgrade-a-standard).
- `ingestron standard list` lists the versions installed with the command,
  then those only the public catalogue has. `--platform <id>` keeps one
  platform's. It always exits `0`. See
  [List them](/docs/how-to/choose-a-published-standard#list-them).

## Source metadata [#source-metadata]

Ingestron never connects to a source. `ingestron source` takes one of two
commands, and each works on the project in `--definitions`:

- `ingestron source request` prints what to ask of whoever can reach each
  source: for every connection a flow reads, the query to run or the call to
  make, who can do it, the access it needs and where to save the result. It
  writes nothing. `--connection <id>` limits it to one connection. The recipe
  for each kind of source is in
  [Source metadata recipes](/docs/reference/recipes).
- `ingestron source import <connection> <file>` reads `<file>`, a path from
  the current folder, and writes `sources/<connection>.yaml`, and adds that to
  the imports of `project.yaml` when it is not there. It keeps names and
  types, and never a value from a row. `--dry-run` prints what the file would
  change and writes nothing, and `--object <text>` names the table a file of
  one table describes, when its path does not name it.

Both take `--env <name>` once. Without it they use the first environment
`project.yaml` declares, and `default` when it declares none. An import with
`--env` also records the environment as the document's `environment`; without
it none is recorded.

`ingestron contract --from-metadata <flow>.<table>` drafts a contract for each
table named from the imported metadata, and with `--needed`, for every table
that needs a contract and names none. It resolves for the environment `--env`
names, or the first one. It writes `contracts/<connection>.<table>.yaml`,
never replaces a file that is there, and prints the `contract:` line to add to
the flow. A draft says what to review: its types, which columns are required
and its key.

The document an import writes is in [Documents](/docs/reference/documents#source-metadata),
and the codes `plan` reports about it are in
[Errors](/docs/reference/errors), as the ones that start `SOURCE_`.

## Project guide [#project-guide]

`ingestron init --assistant <names>` and `ingestron assistant add <names>`
write a project guide for coding assistants. Every name writes `AGENTS.md`,
which holds the guide, and `copilot` and `claude` write one more file that
points to it:

| Name                           | Files                                          |
| ------------------------------ | ---------------------------------------------- |
| `copilot`                      | `AGENTS.md`, `.github/copilot-instructions.md` |
| `claude`                       | `AGENTS.md`, `CLAUDE.md`                       |
| `codex`, `cursor` and `agents` | `AGENTS.md`                                    |

`none` is the default and writes nothing. Without `--assistant` and without
`--yes`, `init` asks last, in a terminal: an empty answer is `none`. Without a
terminal, or with `--yes`, it asks nothing and writes nothing.

The guide is written from the project's own files, and `plan` and `apply` keep
its Ingestron section current. `check` never looks at it.
`assistant add` takes `--definitions`, the project's folder, and `--out`, its
output folder, and needs `project.yaml` there. It exits `1` when there is no
guide to write or a file could not be written.

## Output

`plan` and `apply` print one block for each output folder under `--out`, such
as `databricks → build/databricks (dev, prod)`; see
[Where the files go](/docs/concepts/generated-files#where-the-files-go).

## Exit codes

| Code | Means                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0`  | Success. Warnings, such as a pack's notice, do not change it. A `source import --dry-run` that would write, and breaking changes in source metadata, also exit `0`.                                                                                                                                                                                                                                                                                   |
| `1`  | Problems in the definitions, or output that is not up to date or in conflict. `check` also fails while a value is `REPLACE_ME`. `source` and `contract --from-metadata` also exit `1` on a refused file, an unknown connection, flow table or recipe, a recipe that breaks a rule (even one no connection uses), or definitions that cannot be loaded or have errors that stop the command.                                                           |
| `2`  | A mistake in the command, such as an unknown option or `--env` given to `plan`, or a pack that cannot be loaded (`PACK_LOAD`). `source` without `request` or `import`, `source import` without a connection and a file, or with more, `--env` more than once on `source` or on `contract --from-metadata`, `--from-metadata` with neither a table nor `--needed`, or with both, and a flag given to a command it does not belong to are mistakes too. |

## Editor schemas

`ingestron schemas` writes JSON schemas to `.ingestron/schemas` and prints the
`yaml.schemas` setting that points the YAML extension at them. See
[Check files with the YAML extension](/docs/tools/vscode#check-files-with-the-yaml-extension).

## Use the command from code

The CLI package is also a library: `run` takes the same arguments as the
command. The
[`@ingestron/cli` README](https://github.com/ingestron/ingestron/tree/main/packages/cli#in-code)
describes it.

The command is built on `@ingestron/core`, which your code can use too:
`generatedOutputs` gives every output folder's files as `plan` would write
them, and `projectSources`, `projectRoutes` and `projectRecipe` return the
sources, routes and recipes that `init` and **Ingestron: New project** offer.
The
[`@ingestron/core` README](https://github.com/ingestron/ingestron/tree/main/packages/core)
describes them.
