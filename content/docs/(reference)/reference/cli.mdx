The `ingestron` command reads a project folder and writes each platform's
files, for every environment. [Install it](/docs/start/install) first. `ingestron init` creates a
project; see [Create a project](/docs/how-to/start-from-a-template), or
[Published standards](#standard) below. Then
`ingestron plan` and `ingestron apply` are the everyday loop; see
[Plan, apply and review](/docs/how-to/plan-and-generate). In CI, run
`ingestron check`; see [Check generated files in CI](/docs/how-to/check-in-ci).

## Choose the project and the output [#choose-the-project-and-the-output]

Run the command from the folder that holds `project.yaml`. It reads the
project there and writes to `build` there. Four options adjust the run:

- `--env dev` limits `compare` and `request` to one environment; repeat it
  for more. `plan`, `apply` and `check` always work on every environment
  together, and refuse it.
- `--definitions <folder>` reads a project that is not the current folder.
- `--out <folder>` writes somewhere other than `build`.
- `--no-diff` lists changed files without their line differences.

Relative `--definitions` and `--out` paths are resolved from your current
folder, and changing `--definitions` does not move the output folder. To work
on a project from outside it, set both. From the folder above `shop`:

```sh
ingestron apply --definitions shop --out shop/build
ingestron check --definitions shop --out shop/build
```

With `--definitions shop` alone, `apply` would write `build` in the folder you
ran it from, not in `shop`.

## Published standards [#standard]

`ingestron init <folder> --kit <name>@<version>` creates a project from a
[published standard](/docs/how-to/choose-a-published-standard). `--kit` takes
the name and version, such as `duckdb/local-medallion@2026-11-10`; the name
alone, for the newest version that is not a preview among the installed
versions and the catalogue's tags (the newest installed one, with a note,
when the catalogue cannot be reached); or
`<git-url>#<folder>@<tag>`, for one kept in a Git repository. It is not
combined with `--template` or `--standard`. See
[Start from a published standard](/docs/how-to/start-from-a-published-standard).

`ingestron standard` takes one of two commands:

- `ingestron standard install <kit>` replaces the project's standard with the
  published standard's, keeping its path and `id`, and lists the published
  standard's other files that changed; it refuses a standard file with
  changes that are not committed. It exits `0` once the file is written, and
  `1` when it writes nothing. See
  [Move to a newer published standard](/docs/how-to/upgrade-a-standard).
- `ingestron standard list` lists the versions installed with the command,
  then those only the public catalogue has. `--platform <id>` keeps one
  platform's. It always exits `0`. See
  [List them](/docs/how-to/choose-a-published-standard#list-them).

## Output

`plan` and `apply` print one block for each output folder under `--out`, such
as `databricks → build/databricks (dev, prod)`; see
[Where the files go](/docs/concepts/generated-files#where-the-files-go).

## Exit codes

| Code | Means                                                                                                                           |
| ---- | ------------------------------------------------------------------------------------------------------------------------------- |
| `0`  | Success. Warnings, such as a pack's notice, do not change it.                                                                   |
| `1`  | Problems in the definitions, or output that is not up to date or in conflict. `check` also fails while a value is `REPLACE_ME`. |
| `2`  | A mistake in the command, such as an unknown option or `--env` given to `plan`, or a pack that cannot be loaded (`PACK_LOAD`).  |

## Editor schemas

`ingestron schemas` writes JSON schemas to `.ingestron/schemas` and prints the
`yaml.schemas` setting that points the YAML extension at them. See
[Check files with the YAML extension](/docs/tools/vscode#check-files-with-the-yaml-extension).

## Use the command from code

The CLI package is also a library: `run` takes the same arguments as the
command. The
[`@ingestron/cli` README](https://github.com/ingestron/ingestron/tree/main/packages/cli#in-code)
describes it.

The command is built on `@ingestron/core`, which your code can use too:
`generatedOutputs` gives every output folder's files as `plan` would write
them, and `projectSources`, `projectRoutes` and `projectRecipe` return the
sources, routes and recipes that `init` and **Ingestron: New project** offer.
The
[`@ingestron/core` README](https://github.com/ingestron/ingestron/tree/main/packages/core)
describes them.
