`duckdb@2` loads files into tables in a DuckDB database, runs transforms, and
publishes each table as Parquet, with SQL that DuckDB runs on a laptop or
wherever DuckDB runs. List it first, as in `packs: [duckdb@2, adf@2]` when
ADF lands the files; see [Combine packs](/docs/concepts/standards-and-packs#combine-packs-when-their-actions-fit). The settings below come from the pack itself.

For a task walkthrough, use [DuckDB](/docs/platforms/duckdb); the modes are
explained in [Keep a table current](/docs/how-to/keep-a-table-current#on-duckdb).
The pack writes `run.sql`, every table in
order, and `tables/`, each table's SQL alone, in a folder for each
environment, `build/duckdb/<environment>/`. Run `run.sql` from the project
folder with the DuckDB command line; generation itself runs nothing.

## Quality and cleansing [#quality-and-cleansing]

What this pack does with each check, action and cleansing operation, from the
pack itself. Each row links the DuckDB page it was checked against, with the
date; the pack's
[sources](https://github.com/ingestron/pack-duckdb/blob/main/spec/references.md)
list every page it writes SQL from.

<IntentSupport pack="duckdb" part="quality" />

- **Where checks run.** `run.sql` checks a table's rows only in a layer whose
  `does` lists `check`, and in a `raw` layer counts them, each as `warn`. In
  any other layer it runs none, and its SQL is what it was before checks; each
  rule is [not applied here](/docs/concepts/not-applied).
- **When.** Each table's rows are cast and cleansed, then counted against
  every check before the table is built, in the run's one transaction. The
  DuckDB command line prints each check with its failing rows. A failing
  `fail` check calls `error()`, so `-bail` stops the run and nothing is
  published. Table checks are counted once the table is built, with nothing to
  turn on in the platform: the pack has no `checks` capability, so
  `manage.checks` changes nothing here.
- **Quarantine and results** stay in the database and are not published:
  `<schema>.<table>_quarantine`, rebuilt each run (or added to, for `append`),
  and `<schema>._ingestron_checks`, one row per check and run. In Azure each
  run starts with an empty database, so they last only for that run, and the
  job's log shows the counts.
- **Deduplicate** applies to a table replaced each run. An `upsert` table, or
  one kept at `history: latest`, already keeps one row per key, so
  `deduplicate` there is a
  [`DEDUPLICATE_MODE`](/docs/reference/errors#DEDUPLICATE_MODE) warning, and
  on an `append` table it is an error.
- **Time zones** come from DuckDB's ICU extension, which its command line
  includes. A column typed with a time zone, such as `TIMESTAMPTZ`, cannot be
  converted. Around a clock change, a wall time in the hour skipped in spring
  is read in the offset before the change, and one in the hour repeated in
  autumn is read as the later of the two: in London on 25 October 2026,
  `01:30` is `01:30` UTC.

## Access [#access]

DuckDB has no users, roles or permissions, so the pack applies no grant, mask
or row filter, and its files are what they would be without them. Each role,
grant mode, mask and row filter on a table DuckDB keeps is
[not applied here](/docs/concepts/not-applied). When the files DuckDB
publishes are protected another way, such as on the storage account,
[accept the warning](/docs/how-to/grant-access#accept-a-gap).
