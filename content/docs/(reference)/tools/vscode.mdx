title: VS Code
description: Write Ingestron projects in VS Code with problems as you type, navigation, completion and previews.

The Ingestron extension works on any folder with a `project.yaml`. It uses the
same definition and generation packages as the `ingestron` command. Editor
analysis uses the open files and the selected environment; Plan, Apply and
Check work on every environment together, as the command does.

## Install

Install [Ingestron from the Visual Studio Marketplace](https://marketplace.visualstudio.com/items?itemName=ingestron.ingestron-vscode).
You need VS Code 1.104 or later. See
[Install the command and the extension](/docs/start/install) for installation
steps and how to check that it is ready.

Open a folder that holds an Ingestron project. The selected environment
appears in the status bar, such as `Ingestron: dev`; click it to choose
another. It decides what the editor shows: the problems, the previews of
generated files, what each line becomes, and the platform request. Plan,
Apply and Check do not use it: every environment is generated together, into
one set of files per platform. VS Code remembers the choice for each project
in the workspace.

## Get started

**Help: Welcome** lists **Get started with Ingestron**: six steps from a new
project to generated files and a request for your platform team. Each step
is ticked when you do it, such as when the workspace has a flow, or after
**Ingestron: Apply** runs.

## Problems as you type

Definition problems appear in the Problems panel at their file and line,
while you type and before you save: a broken link, a setting
the standard fixes, a method that cannot read a source, a name that is not
valid. Problems are for the environment in the status bar; click it, or run
**Ingestron: Select environment**, to choose another. Problems that generating
finds, such as a value supplied when deploying that cannot be a name
(`DEPLOY_VALUE`), show too, and a pack's notice (`PACK_NOTICE`) is a warning
on the first line of `project.yaml` in every environment. A feature the engine
that keeps a table cannot apply is a warning at the line that asks for it
(`NOT_APPLIED`; see [Not applied here](/docs/concepts/not-applied)). A warning
that the platform's `accept` list accepts is not shown; see
[Accept a warning](/docs/how-to/accept-a-warning).

A definition that uses `${envvar:NAME}` reads the variable from `.env.<environment>`
and `.env` in the project folder, and from the environment VS Code was started
with. A variable exported later in a terminal is not seen here; put it in
`.env`. When the variable is set nowhere, the editor shows a blue information
mark, not an error. For Databricks, Data Factory and Synapse, which take the
value when deploying, it names what the deploying pipeline sets, such as
`BUNDLE_VAR_landing_path`; for DuckDB it names the file to add it to, such as
`.env.dev`. The rest of the project is still checked, and a value that depends
on the missing one is not judged until it is set. A line in an `.env` file that
Ingestron cannot read is a warning (`ENV_FILE_LINE`) at that line. See
[Environment files](/docs/concepts/yaml-references#use-environment-files).

A definitions file that no import in `project.yaml` matches, such as a new
transform in `transforms/` when the project imports only `flows/*.yaml`, is
not part of the project: nothing is generated from it. The editor warns on
the file (`NOT_IMPORTED`), and its quick fix adds the folder to `imports`.

A file in `build/` that was changed by hand gets a warning: the next apply
reports it as a conflict.

## Fix a problem

When a problem has an obvious remedy, the light bulb beside it, or **⌘.**
(**Ctrl+.**), offers it:

- the closest id for a broken link, and the near name for a misspelt field;
- for settings a method needs and nobody set, every one of them at once, each
  empty in the file it belongs in: shared infrastructure in `platform.yaml`,
  a schedule in the standard, facts about the source in the flow;
- for a link to a contract or connection that does not exist yet, a new file
  for it, from the same skeleton as a new file; and `standard.yaml` for a
  project without a standard;
- each allowed value, and a missing field with its usual value;
- for a method that cannot read a source, each method that can: for this
  flow, for every such source in the standard, or from a pack the standard
  does not name yet, which adds the pack too.

A fix may change several files; one undo reverts it. You choose the fix: each
one means something different, such as one flow or the whole standard. The
CLI prints the first fix under the problem, as `Fix: …`.

When the same problem has a fix in several places, the menu also offers
**Fix all N … problems**, which applies each one's first fix in one change; an
edit several of them share, such as turning on `databricks.manage.checks`, is
made once.

A method's setting written outside the file its method says it belongs in,
such as a table's `properties` in a flow or `integration_runtime` in a
standard, offers **Move … to standard.yaml** or **to platform.yaml**, with the
cursor on its key or value. The move removes it where it was, and any `with`
it leaves empty, and says when it replaces a value already there. It also
names the tables the setting will then apply to, such as
`it applies to every adf-copy table: customers, invoices`, because a value in
the standard or platform reaches every table that uses the method.

## Move between files

- **Go to Definition** (F12) on a flow's `source`, a table's `contract`, a
  transform's `inputs`, `{{ tables.orders }}` in transform code,
  `${values.host}` or `${file:daily_sales.sql}` opens what it names.
- **Go to References** (⇧F12) lists every use of an id.
- **Rename Symbol** (F2) renames a connection, contract, table or value
  everywhere it is used, and nowhere else. In a PySpark transform's code
  file, `tables["orders"]` is renamed with the table; comments and other
  Python files are left as they are. A name that another table or document
  of the same kind already has is refused, with the reason.
- **Go to Symbol in Workspace** (⌘T on macOS, Ctrl+T elsewhere) finds any
  table, connection, contract, flow, transform or value in the workspace's
  projects. The **Outline** lists those a file defines.
- **Renaming or moving a file or folder** in Explorer changes each
  `${file:…}` that points into it, so a transform still finds its code. VS
  Code leaves the changed YAML unsaved for you to review, and one undo puts
  the move back.

## Completion

Completion offers what fits where you type: fields from the document's
schema, allowed values and examples, the ids of connections and contracts,
table names in `inputs`, the forms a reference
takes after `${` and value names after `${values.`, the names a naming pattern can use inside `{{ }}`, the methods
for `uses`, and, under `with`, the settings of the method that table uses
in the environment in the status bar, with their defaults. This works in a
new file too, before it has ever been valid.

In a transform's code, after `{{ tables.` in SQL or `tables["` in Python,
completion offers the transform's inputs first. Other tables follow, marked
**not an input yet**; choosing one also adds it to the transform's `inputs`.
The transform itself, and tables that already read it, are never offered,
as either would make a loop.

Where the standard fixes a setting, completion offers the value fixed for
that environment first, even when the standard writes it as `${values.…}`,
marked **fixed by the standard**, and marks the others **not allowed**. If a
definition sets a fixed value anyway, the `FIXED_SETTING` problem has a quick
fix, **Remove this setting**, so the standard's value applies.

It also fills in what the project already decides:

- **A new, empty file** offers a document to start from: the project
  manifest in `project.yaml`, a standard in `standard.yaml`, and the kind its
  folder holds in `flows/`, `connections/` (one per connector, with the
  settings it needs), `contracts/` or `transforms/`. The id comes from the file
  name, and **Tab** moves through the parts to fill.
- **Under a flow's `tables`**, each contract no table uses yet is offered as
  a table, with its object and contract filled in.
- **A table's `contract`** offers `<source>.<object>` first.
- **A flow's `ingest.uses`** offers the methods that can read the source
  first; the others say why they cannot.

Hover a pattern under `naming` to see the names it gives in the selected
environment.

## What each line becomes

For the environment in the status bar, the editor shows beside each line what
it resolves to:

- after a flow table or a transform, the table's full name;
- above it, the methods that build it, with how each was chosen on hover, and
  each file generated for it, which opens that file read-only. A contract
  object shows the same files;
- after a value with `${…}`, the value it resolves to. Secrets and environment
  variables are never shown.

Turn these off with VS Code's `editor.inlayHints.enabled` and
`editor.codeLens` settings.

## Why is this value what it is?

Hover a flow table or a transform to see its full name, the method for each
step, and every setting with the layer that set it: the pack's default, the
standard, the platform, a rule, the flow or transform, the table itself, or a
setting the standard fixes, with the file and line. Hover a setting under
`with` for that one value. The same hover lists the table's
[intent](/docs/reference/intent), each value with where it came from, such as
`history`: `latest`, from the table's layer in the standard
(`standard.yaml:18`).

Hover a value that is still `REPLACE_ME` to see the field it fills, what the
field is, where to find the value, and a suggestion of what it looks like,
such as `<application id>`. A value in `project.yaml`'s `values` is explained
by the field that reads it.

Hover any field or setting to see what it is, what each allowed value means,
its default, an example and where it is usually set; hover a value for that
value's meaning. Each ends with a **Reference** link to its entry in these
docs, and each problem's code in the Problems panel links to its entry in
[Errors](/docs/reference/errors). Links open the address in the
`ingestron.docs.url` setting; set it to a local build, such as
`http://localhost:3000`, to read the docs offline.

## Project view

The **Ingestron** tab in the secondary side bar, on the right, opens with a
**Project** section. For a workspace with one project it lists:

- **Environments**, each with a circle, or a check and **selected** on the one
  problems, previews and the platform request show. Click an environment to
  select it, as in the status bar.
- **Check**, **Plan**, **Apply**, **Compare environments**, **Prepare platform
  request** and **Show generated files**. Click one to run it for the project.
  Check, Plan and Apply work on every environment together; Prepare platform
  request and Show generated files use the selected one. Each item's tooltip
  says which.

With several projects, each has a row, named by its `id` and showing its folder
in the workspace, that holds the same lists. Every row starts folded except
the project of the file in the main editor, which opens by itself. Moving to a
file of another project opens that project and folds the one before; a row you
fold or open by hand stays as you left it until the active project changes. A
workspace with no project shows **New project**. The view follows the environments in `project.yaml`, so adding
one to the file adds it to the list.

## Reference beside the editor

The **Reference** section below the Project view, in the same **Ingestron** tab,
explains what the cursor is on as you move it: the problems on that line with
their meaning, fix and quick fixes; then the field or value, with each allowed
value, the one written marked, its default, an example and where it is usually
set; on the document's header, the document and its fields. Open it with
**Ingestron: Show reference**, or drag the tab to another side.

It shows what the installed extension knows, so it matches its packs and
works offline; **Reference** links open the full entry in these docs.

In editors built on VS Code without a secondary side bar, the tab is a
**Reference** section at the bottom of the side bar on the left, under the
Explorer.

## See what will be generated

- **Ingestron: Show generated files** opens what would be generated for the
  table at the cursor, in the selected environment, in a read-only preview,
  without writing anything. It updates as you edit the definitions. Its paths
  are those `ingestron apply` writes, such as
  `build/adf/factory/pipeline/…`; a folder shared by every environment, such
  as a Databricks bundle or a factory with each environment's parameter file,
  shows in each environment that uses it.
- **Ingestron: Compare with build** shows the difference between that and the
  file in `build/`: what the next apply changes.

While plan would stop, nothing is generated, and the preview says why, such
as `Nothing is generated while plan would stop: prod has problems. Run Plan
to see them.`: problems in any environment stop every one, because every
environment is generated together.

Plan, Apply, Check and the other commands work from a preview too, on the
preview's project; Apply from a `dev` preview writes every environment.
Prepare platform request uses the environment the preview shows, and while a
preview is active, the status bar shows that environment.

## Ask the platform team

Some features need someone who administers the data platform: grants for
the identity pipelines run as, tag policies, shared storage and runtimes.
**Ingestron: Prepare platform request** writes, for the environment in the
status bar, one Markdown document to review and send: the environment
variables still to provide, the identity, what each switched-on `manage`
capability needs, the features the definitions use while their switch is off,
the shared infrastructure the methods expect (secrets never shown), what each
pack needs on the platform and the SQL to run once, such as Databricks'
`prerequisites/<environment>.sql`. Nothing is sent or saved until you do so. See
[Ask the platform team](/docs/how-to/ask-the-platform-team).

## Plan, apply and check

**Ingestron: Plan**, **Ingestron: Apply** and **Ingestron: Check** run the
command for the project, after saving open files, for every environment
together: one block for each output folder, such as
`databricks → build/databricks (dev, prod)`. The output is in the Ingestron
output panel.

You can start them from where you are working, as well as from the Command
Palette. Each acts on the project you started it from:

- **Right-click** a project folder, or a YAML file in a project, in the
  Explorer for **Ingestron: Check**, **Plan**, **Apply**, **Compare
  environments** and **Prepare platform request**. The files in `build/` do not
  have the menu.
- **Editor title buttons**: with a YAML file of a project, or a preview of
  generated files, open, **Plan** and **Apply** are buttons in the editor's
  title bar. **Check**, **Compare environments** and **Prepare platform
  request** are under the **…** menu beside them.
- **The Project view** lists the same actions; see [Project view](#project-view).

## Generate on save

To see the generated files change as you edit, click **Auto-apply: off** in
the status bar, or run **Ingestron: Turn auto-apply on or off**. Turning it on
applies every environment straight away, and the switch reads
**Auto-apply: on**. While it is on, saving a YAML, SQL or Python file in the
project applies again. The Ingestron output panel logs each run with a line
for each output folder, such as `databricks (dev, prod): up to date`, with the
files it changed below it, and a line for each folder that is no longer
generated.

It applies nothing while the definitions have problems in any environment,
and says where to see them: for another environment, such as
`not applied: prod has problems (select prod to see them in the Problems panel)`.
A folder with a file changed by hand is not applied either, and its line says
so, as `apply` would. It starts off, and VS Code remembers the choice for each
workspace.

## Start a project

**Ingestron: New project** starts from a connection, a starter or a published
standard.

- **From a connection** asks for a source category, connection, network
  reachability and supported route. You can search across all sources or
  within a category.
- **From a starter** offers the ready-made projects, such as **DuckDB on a
  laptop**, which [runs locally with DuckDB](/docs/platforms/duckdb).
- **From a published standard** offers the dated standards installed with the
  extension, such as **Local medallion on DuckDB**, and makes the same project
  as `ingestron init --kit`; see
  [Start from a published standard](/docs/how-to/start-from-a-published-standard).

Nothing else is asked. The destination folder comes last, and its name is the
project's id; the environments are `dev` and `prod`, or the starter's or the
published standard's, and the standard is the route's, the starter's or the
published one. The new `README.md` opens in a
preview, and a message says how many values are still `REPLACE_ME`: the
README lists each with where to find it. When the folder is outside the
workspace, the message offers to open it or add it to the workspace. See
[Create a project](/docs/how-to/start-from-a-template).

## Check files with the YAML extension [#check-files-with-the-yaml-extension]

Without the Ingestron extension, the
[YAML extension](https://marketplace.visualstudio.com/items?itemName=redhat.vscode-yaml)
can check each definition file's fields and values against Ingestron's schemas.
From the project folder, run:

```sh
ingestron schemas
```

It writes the schemas to `.ingestron/schemas` and prints the setting to add to
`.vscode/settings.json`:

```json
{
  "yaml.schemas": {
    ".ingestron/schemas/definitions.json": "**/*.yaml"
  }
}
```

The glob follows `--definitions` when you pass it. A schema checks one file at
a time: it does not follow the links between files, apply the standard or read
your environments. The Ingestron extension does, as
[Problems as you type](#problems-as-you-type) describes.
