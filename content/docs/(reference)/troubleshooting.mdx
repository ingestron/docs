Find the message or behaviour you see. Each entry gives the cause and the fix,
and a code links to its entry in [Errors](/docs/reference/errors). Messages are
shown as the command prints them; a name or a path in one is the project's own.

## The command

### `ingestron: command not found` [#ingestron-command-not-found]

**Symptom:** the shell cannot find the command. Bash prints
`bash: ingestron: command not found`, zsh prints
`zsh: command not found: ingestron`, and PowerShell says
`The term 'ingestron' is not recognized`.

**Cause:** Ingestron is not installed globally, or npm's folder for global
commands is not on your `PATH`.

**Fix:** install it, then open a new terminal and run `ingestron --help`:

```sh
npm install -g ingestron
```

If the shell still cannot find it, print the folder npm installs into:

```sh
npm prefix -g
```

On macOS and Linux the command is in that folder's `bin` folder; on Windows it
is in the folder itself. Add that folder to your `PATH`, such as in `~/.zshrc`
or in Windows' environment variables, then open a new terminal.

With a Node.js version manager such as nvm or fnm, each Node.js version has its
own global packages: after you switch versions, run `npm install -g ingestron`
again.

If `npm install -g` fails with `EACCES`, npm cannot write to the folder of a
Node.js installed for the whole system. Install Node.js with a version manager
instead, or set npm's prefix to a folder you own, such as
`npm config set prefix ~/.npm-global`, and add its `bin` folder to your `PATH`.

### Plan, apply or check refuse `--env` [#plan-refuses-env]

**Symptom:** the command prints its usage and exits with `2`:

```text
Every environment is generated together, so plan does not take --env. Use compare for two environments, or request for one.
```

**Cause:** each platform's files hold every environment, so `plan`, `apply`
and `check` always work on all of them. Scripts and CI written for version 1
passed `--env`.

**Fix:** remove `--env` from `plan`, `apply` and `check`. To look at one
environment, use `ingestron compare --env dev --env prod` or
`ingestron request --env prod`.

### A pack cannot be loaded

**Symptom:** every command prints one
[`PACK_LOAD`](/docs/reference/errors#PACK_LOAD) error, writes nothing and
exits with `2`.

**Cause:** a pack that came with the command has a mistake of its own, such as
a field it reads that the definitions do not have. Nothing in your project
causes it.

**Fix:** install a version of Ingestron, or of the VS Code extension, that
fixes the pack, as [Upgrade Ingestron and its packs](/docs/how-to/upgrade)
describes.

## Generated files

### Plan reports a conflict

**Symptom:** `plan`, `apply` or `check` lists a file as a conflict and exits
with `1`:

```text
conflict  dev/run.sql
          Changed by hand since it was generated. Move the change into the definitions, or delete the file to generate it again.
```

**Cause:** someone edited a generated file. Ingestron never overwrites it.

**Fix:** move the change into the definitions or the standard, then delete the
file and run `ingestron apply` to generate it again. In VS Code, the file has an
`EDITED` warning before you apply.

### Apply stops because of `.generated.lock`

**Symptom:** `ingestron apply` prints its plan, then stops with `1`:

```text
Another generation is writing to this folder. If none is, delete .generated.lock.
```

`plan` and `check` still work.

**Cause:** `apply` creates `.generated.lock` in the output folder while it
writes, and removes it when it ends, whether it succeeded or not. A lock that
is still there means another apply is writing to the folder, such as VS Code's
**Ingestron: Apply** or auto-apply, or an earlier one was stopped before it
could remove the lock.

**Fix:** wait for a run that is still going. If none is, delete
`.generated.lock` from the output folder the plan names (the line before the
changes, such as `duckdb → build/duckdb (dev)`). Then follow the next entry,
because the folder may hold a mix of old and new files.

### An apply stopped part-way

**Symptom:** one of these:

- With several platforms, `apply` ends with a line such as
  `Applied: adf. Not applied: databricks.` and exits with `1`.
- A write fails, and `apply` ends with
  `Could not write "dev/tables/silver.customer_totals.sql": <reason>. Nothing was changed.`
- The process was stopped, such as a closed terminal or a cancelled CI job. The
  lock stays, and `ingestron check` may also print a file ending in `.tmp`:
  `duckdb: not generated  dev/tables/silver.customer_totals.sql.<id>.tmp`.

**Cause:** `apply` writes one output folder at a time. A folder whose plan has
a conflict is left as it was while the others are written. When a write
fails, Ingestron puts back the files it had already changed in that folder. If
it cannot put one back, it adds `Some files could not be put back.` A process
that is stopped cannot put anything back: the folder holds a mix of old and new
files, and the lock and a temporary file may remain. Each file is whole, never
half-written.

**Fix:**

- `Not applied: databricks`: run `ingestron plan` and resolve what it reports
  for that folder, such as a [conflict](#plan-reports-a-conflict), then apply
  again.
- `Nothing was changed.`: fix what the reason names, such as a folder you cannot
  write to or a full disk, and apply again.
- A stopped process, or `Some files could not be put back.`: delete
  `.generated.lock` and any `.tmp` file if present, in the output folder, then
  run `ingestron plan`. A file already written shows as unchanged, so the plan lists
  only what is left. Run `ingestron apply`, then `ingestron check`. Restoring
  `build/` from version control first works too.

### Check fails in CI

**Symptom:** `ingestron check` prints `not up to date` and exits with `1`.

**Cause:** the definitions changed but the generated files were not
regenerated and committed, or a generated file was edited.

**Fix:** run `ingestron apply` locally, review the changes and commit them.

### Check reports a folder or file that was not generated

**Symptom:** `ingestron check` prints `not generated  <file>` or
`<folder>: no longer generated`, and exits with `1`.

**Cause:** someone added a file inside an output folder, or a folder that
was generated before is still in `build/`: a platform's folder after its last
table went, or the folder per environment, such as `build/dev/`, that version
1 wrote. See [Upgrade from 1.x to 2.0](/docs/how-to/upgrade#upgrade-to-2).

**Fix:** move the extra file out of `build/`. Delete the old folder once
nothing deploys from it. See [Check generated files in CI](/docs/how-to/check-in-ci).

## Definitions

### A setting is not accepted

**Symptom:** [`BAD_SETTING`](/docs/reference/errors#BAD_SETTING), with one of:

```text
Settings for "duckdb-files": "frmat" is not a setting.
Settings: format, csv.
```

```text
"synapse-view" needs settings: data_source.
```

**Cause:** a misspelt setting, a setting of another method, or a required
setting nobody gave.

**Check:** the message's hint lists the method's settings, and
[Packs and methods](/docs/reference/packs) shows them with their defaults.

**Fix:** correct the name at the reported line, or add the missing setting,
usually in the standard or the platform.

### The method cannot read this source

**Symptom:**
[`CONNECTOR_NOT_SUPPORTED`](/docs/reference/errors#CONNECTOR_NOT_SUPPORTED) or
[`CONNECTIVITY_NOT_SUPPORTED`](/docs/reference/errors#CONNECTIVITY_NOT_SUPPORTED),
such as:

```text
"duckdb-files" cannot read the "sqlserver" connector.
Methods that read sqlserver: adf-copy (private, workspace, public).
Fix: Use "adf-copy" for this flow.
```

**Cause:** the chosen method does not read this kind of source, or cannot
reach it.

**Check:** the hint lists the methods that can, with the connectivity each
supports.

**Fix:** remove the flow's `uses` to let the standard choose, add the pack
that reads it to the standard's `packs`, or correct the connection's
`connectivity`.

### Two tables get the same name

**Symptom:** [`DUPLICATE_TABLE`](/docs/reference/errors#DUPLICATE_TABLE) or
[`DUPLICATE_NAME`](/docs/reference/errors#DUPLICATE_NAME), such as:

```text
Another flow or transform already produces a table named "orders".
```

**Cause:** two flows or transforms use the same table name, or the naming
patterns give two tables the same full name.

**Fix:** rename one, or include `{{ flow }}` or `{{ source }}` in the
table pattern. See [Name tables and resources](/docs/how-to/name-things-your-way).

### The standard names an older pack [#pack-version]

**Symptom:** after upgrading to ingestron 2, plan stops with
[`PACK_VERSION`](/docs/reference/errors#PACK_VERSION), once for every
environment:

```text
standard.yaml:4:9  error  PACK_VERSION
  This standard is for "duckdb@1", but the pack is duckdb@2.
  Change it to duckdb@2; the upgrade notes say what changes in the generated files.
  Fix: Change to "duckdb@2".
```

**Cause:** every pack in ingestron 2 is version 2, and the standard still
names version 1.

**Fix:** change each pack in the standard's `packs` to `@2`, or apply the fix
in VS Code, then follow
[Upgrade from 1.x to 2.0](/docs/how-to/upgrade#upgrade-to-2).

### Environments differ in more than values [#environments-differ]

**Symptom:** a pack's plan stops with
[`ENVIRONMENTS_DIFFER`](/docs/reference/errors#ENVIRONMENTS_DIFFER), such as:

```text
databricks: the definitions have problems
project.yaml:1:1  error  ENVIRONMENTS_DIFFER
  The pipeline is named "retail_dev" in dev and "retail_prod" in prod; resource keys and folders are named after it, so it must be the same in every environment.
  Environments may differ only in values, such as names, paths and hosts; make the rest the same in every environment.
```

**Cause:** one bundle, factory or Synapse script serves every environment, so
environments may differ only in values. A pipeline, job or ADF resource name
that differs, a table built in some environments only, or code that differs in
more than a value cannot be written once.

**Fix:** make it the same in every environment: here, remove
`{{ environment }}` from the standard's `naming.pipeline`. Catalogs, schemas,
paths and hosts may still differ. See
[Where the files go](/docs/concepts/generated-files#where-the-files-go).

### A value supplied when deploying is refused [#deploy-value]

**Symptom:** plan stops with
[`DEPLOY_VALUE`](/docs/reference/errors#DEPLOY_VALUE), such as:

```text
flows/orders.yaml:4:9  error  DEPLOY_VALUE
  "${envvar:SOURCE}" is supplied only when deploying, so it cannot decide what is generated or what it is called.
  Write this value in project.yaml, per environment; keep ${envvar:…} for values the deploying pipeline supplies, such as hosts, paths and accounts.
```

**Cause:** for Databricks, Data Factory and Synapse, `${envvar:…}` is a value
the deploying pipeline supplies. It cannot be a flow's `source`, a contract,
a name, or, for Data Factory and Synapse, part of a longer value.

**Fix:** write the value in `project.yaml`, with each environment's value
under `environments`. See
[Supplied when deploying](/docs/concepts/yaml-references#supplied-when-deploying).

### A new file is not generated

**Symptom:** you added a flow, transform or other definition and `plan` lists
nothing for it. In VS Code, the file has a warning:

```text
This file is not part of the project: no import in project.yaml matches it, so nothing is generated from it.
```

The command line says nothing: it never reads a file that no import matches.

**Cause:** `project.yaml` lists what it loads under `imports`, such as
`transforms/*.yaml`. A pattern does not reach into a subfolder, and
`.yml` does not match `*.yaml`. The editor reports this as `NOT_IMPORTED`; it is
not in [Errors](/docs/reference/errors), because only the editor checks for it.

**Fix:** use the warning's quick fix, which adds a pattern that matches the file to
`imports` (`Import "transforms/finance/*.yaml" in project.yaml`), or add one
yourself. Then plan again.

## Environment variables and `.env`

### A variable is not set

**Symptom:** the command line stops with
[`ENVVAR_MISSING`](/docs/reference/errors#ENVVAR_MISSING) as an error, and
usually a link that depends on the value as well:

```text
connections/shop.yaml:8:9  error  ENVVAR_MISSING
  Environment variable SAMPLES_DIR is not set.
  Set SAMPLES_DIR, add it to .env.dev or .env, or remove "${envvar:SAMPLES_DIR}".
flows/orders.yaml:4:9  error  BROKEN_LINK
  "shop" is not the id of a Connection document.
```

In VS Code, the value has a blue information mark, not an error:

```text
SAMPLES_DIR isn't set; add it to .env.dev or set it before running Ingestron.
```

**Cause:** the variable is unset or empty in the environment of the process
that runs Ingestron, in `.env.<environment>` and in `.env`. A document that
uses it is not loaded, so what links to that document is reported too, in
VS Code as well. This applies where a value is read when generating, as for
DuckDB; for Databricks, Data Factory and Synapse, the value is supplied when
deploying, and plan does not need it (see
[Supplied when deploying](/docs/concepts/yaml-references#supplied-when-deploying)).

**Fix:** add `SAMPLES_DIR=./samples` to `.env`, or to `.env.dev` for `dev`
alone, or set the variable before you run the command. In CI, set it in the
pipeline. The links report goes away with the variable. In VS Code, saving the
file checks again. The editor reads the environment VS Code was started with, so a
variable you export in a terminal afterwards is not seen: put it in `.env`. See
[Environment files](/docs/concepts/yaml-references#use-environment-files).

### A line of `.env` is ignored

**Symptom:** a warning, [`ENV_FILE_LINE`](/docs/reference/errors#ENV_FILE_LINE),
and the variable it should have set is reported as not set:

```text
.env:1:1  warning  ENV_FILE_LINE
  .env line 1 is not a setting, so it is ignored.
  Write NAME=value, with a name of letters, digits and _ that does not start with a digit. Close any quote, and put only a # comment after it.
```

**Cause:** the line is not `NAME=value`: it has no `=`, an unclosed quote, or
a name with a hyphen or a leading digit. The message names the file and line,
never the text.

**Fix:** correct the line, or start it with `#` to make it a comment. A name
that is set to nothing counts as unset.

## VS Code

### The editor still behaves like the old version

**Symptom:** after you build and install a newer extension, a command from the
new version is missing from the Command Palette, or problems are the old ones.

**Cause:** a window that was open during the install may still be running the
earlier version.

**Fix:** after installing a new version, run **Developer: Reload Window** from
the Command Palette. See [Install the command and the extension](/docs/start/install).

### Plan in VS Code and in the command differ

**Symptom:** after `ingestron apply` in a terminal, **Ingestron: Plan** lists
changes, or the other way round.

**Cause:** a different version. The extension carries its own copy of the
command, which need not be the one you run. Both plan every environment, so
the environment in the status bar makes no difference.

**Fix:** run the same version in both, as
[Upgrade Ingestron and its packs](/docs/how-to/upgrade) describes, and reload
the window after installing the extension again.

## Azure Data Factory

### A connection is missing a setting

**Symptom:** the plan stops before any file is written:

```text
flows/postgresql.yaml:15:5  error  METHOD_CHECK
  "adf-table" for table "postgresql_records": the connection needs "settings.server" as non-empty text.
```

**Cause:** the connector needs a setting the connection does not give, or the
connection gives one the connector does not accept
(`the connection setting "ssl" is not supported for postgresql`).

**Fix:** add the setting to the connection, or remove the one the message says
is not supported. Find your connector in the [catalogue](/docs/connectors); its
page, such as [PostgreSQL](/docs/connectors/postgresql), lists the connection
fields. See [Azure Data Factory](/docs/platforms/adf).

### A pipeline fails when it runs

**Symptom:** `plan` and `apply` succeed, but a deployed pipeline fails in Data
Factory before it copies, or while it reads the source or writes the landing
folder.

**Cause:** Ingestron generates the factory's files. It does not provision the
runtime, the Key Vault or the storage, and does not test credentials or
network access. Whatever is missing, such as the runtime, a secret, the
identity's access to the Key Vault or the landing storage, or the source
permissions and runtime prerequisites, fails only when the pipeline runs.

**Fix:** run `ingestron request --env dev`, or **Ingestron: Prepare platform
request** in VS Code. Its **ADF prerequisites** section lists, with this
project's values, the integration runtime, the Key Vault, the landing folder
and the source's permissions that must exist. Give the list to the team that
creates them. See
[Before you deploy](/docs/platforms/adf-deploy#prerequisites).

### Every plan and check prints a notice about a runtime [#runtime-notice]

**Symptom:** `plan`, `apply` and `check` print a warning before the folders,
and still succeed:

```text
adf: warnings
(project)  warning  PACK_NOTICE
  Integration runtime `shir-erp` (self-hosted): the deployment writes it by name and type, as Data Factory Studio does; where it creates it, register a node, with network access and any required source drivers, before the copies run.
```

**Cause:** the factory holds each integration runtime its linked services
use, and an ARM deployment sets a runtime's whole resource. The
[`PACK_NOTICE`](/docs/reference/errors#PACK_NOTICE) says what a deployment
does to it. It is a warning, so it shows on every run, in CI too.

**Fix:** nothing to change in the definitions. Before the first deployment to
a factory that already has the runtime, run `az deployment group what-if` with
the template and that environment's parameter file, and describe a linked or
Azure runtime with the method's `runtime` setting; see
[Runtime and Key Vault](/docs/platforms/adf#runtime-and-key-vault).

### Development triggers do not run

**Symptom:** the pipelines are in the factory, but a `dev` copy never starts
on its schedule.

**Cause:** triggers start only in `prod` and `production`
([platform defaults](/docs/reference/packs/adf#platform-configuration)). The
trigger file in `factory/trigger/` says `"runtimeState": "Stopped"`, and
`parameters/prod.json` sets the trigger's state to `"Started"`.

**Fix:** start the trigger in Data Factory when you want development copies to
run, or set `paused: false` for the copy method in the platform and generate
again, which starts it in every environment. Check `start` first: a started trigger runs every window since `start`. See [Retry and pause](/docs/platforms/adf-pipelines#retry-and-pause).

## Synapse serverless views

### A view's SQL starts with WITH

**Symptom:**

```text
transforms/customer_totals.yaml:3:5  error  METHOD_CHECK
  "synapse-sql" for table "customer_totals": a view's SQL cannot start with WITH; write the common table expression as a subquery.
```

**Cause:** a transform's SQL sits inside `CREATE VIEW`, so it cannot open with
a common table expression.

**Fix:** write the expression as a subquery in `FROM`. A transform's SQL also
names only the tables listed in `inputs`; the message
`the SQL names {{ tables.customers }}, which is not in inputs` means one is missing.
See [What each engine makes of it](/docs/how-to/write-a-transform#what-each-engine-makes-of-it).

### A view reads files outside the data source

**Symptom:**

```text
flows/erp.yaml:6:14  error  METHOD_CHECK
  "synapse-view" for table "customers": abfss://landing@saleslakedev.dfs.core.windows.net/erp/erp.dbo.Customers/erp.dbo.Customers.parquet is not under the data source landing (abfss://other@saleslakedev.dfs.core.windows.net).
```

**Cause:** the files ADF lands are not under `data_source_location` in the
platform, so the external data source cannot reach them.

**Fix:** set `data_source_location` to a folder above every landing folder, or
point the landing folder inside it. See
[Settings that shape it](/docs/platforms/synapse#settings).

### Running the views fails the first time [#running-viewssql-fails-the-first-time]

**Symptom:** `sqlcmd -i environments/<environment>.sql` fails in Synapse for a
new environment, although `apply` succeeded.

**Cause:** Ingestron writes the views but creates nothing in Synapse. The
serverless database, a master key, the credential, the external data source and
the workspace's read access to the storage must exist first.

**Fix:** run `ingestron request --env dev`. Its **Synapse serverless database**,
**External data source** and **Report users** sections list each statement and
permission, with this project's names. Ask the team that owns the workspace to
create them, then run the environment's script again.

### sqlcmd cannot find views.sql

**Symptom:** `sqlcmd -i environments/<environment>.sql` stops at once, saying
it cannot open `views.sql`, or Synapse Studio reports an error at the first
`$(…)` in `views.sql`.

**Cause:** sqlcmd reads the `:r views.sql` line from the folder it starts in,
not from the script's folder. `views.sql` holds sqlcmd variables, which only
sqlcmd replaces, so Synapse Studio cannot run it.

**Fix:** run sqlcmd from `build/synapse`, with the environment's script. See
[Deploy](/docs/platforms/synapse#deploy).

## DuckDB

### Append would miss later loads

**Symptom:**

```text
flows/erp.yaml:6:13  error  METHOD_CHECK
  "duckdb-table" for table "invoices": append reads each file once, but "adf-copy" replaces its file each run, so later loads would be missed; use replace or upsert.
```

**Cause:** `append` reads each file name once. A copy that replaces its file
under the same name every load would never be read again. For the same reason,
a file you re-export under its old name is skipped.

**Fix:** keep the table with `history: none` (the method's `replace`) or
`history: latest` (`upsert`) instead of `mode: append`, or give each load its
own file, such as with `increments`. To reload everything, delete `ingestron.duckdb` and run
again. See [Keep a table current](/docs/how-to/keep-a-table-current#on-duckdb).

### Upsert needs a primary key

**Symptom:**

```text
flows/erp.yaml:6:13  error  METHOD_CHECK
  "duckdb-table" for table "invoices": upsert needs the contract's primaryKey.
```

**Cause:** `history: latest`, the method's `upsert`, replaces rows with the
same key, and the contract names no key. `sequence` has to be a column of the
contract too.

**Fix:** mark the key column `primaryKey: true` in the contract. See
[Keep a table current](/docs/how-to/keep-a-table-current).

### A run keeps going after an error

**Symptom:** a DuckDB error is printed, but the run carries on, and some tables
and Parquet files exist although another table failed.

**Cause:** as the generated `README.md` says, without `-bail` DuckDB carries on
after an error and commits what it built. With `-bail`, a run that fails while
building publishes nothing.

**Fix:** run it as the generated `README.md` says, from the project folder:

```sh
duckdb -bail ingestron.duckdb -c ".read build/duckdb/dev/run.sql"
```

### Publishing fails after the tables are built

**Symptom:** the run reaches the step that publishes and fails there, or no
`<schema>.<table>.parquet` file appears.

**Cause:** `run.sql` publishes each table to the `published` folder in
`platform.yaml`, and that folder must exist.

**Fix:** create the folder, such as `published/`, or correct the setting, and
run again. Running again is safe.

### Paths mix local and Azure

**Symptom:** the environment's `README.md` begins:

```text
This environment reads or writes both local paths and paths in Azure storage,
and local paths cannot run in Azure: a job there cannot see them. Give it only
paths in Azure storage, or only local paths. `run.sql` has no Azure sign-in of
its own.
```

and `ingestron request` adds `give this environment only paths in Azure storage`.

**Cause:** one path in the environment is local, such as `./published`, and
another is in Azure. A job in Azure cannot see a local path, and `run.sql`
has no Azure sign-in of its own, so a laptop cannot read the Azure ones.

**Fix:** give the environment only Azure paths, or only local ones. To try a
cloud project on a laptop, use an environment with `runs-on: duckdb`. See
[Run a cloud project locally](/docs/platforms/duckdb#run-a-cloud-project-locally).

### The job after the copies fails or times out

**Symptom:** the parent pipeline `pl_<project>_every_<interval>_<unit>` fails
in Data Factory with one of:

```text
The job after the copies ended Failed.
The job after the copies did not finish within 01:00:00, so it was stopped.
The job after the copies did not finish within 01:00:00 and could not be stopped: <reason>
```

The status can be another word than `Failed`, and the time is the
`after_copy` timeout.

**Cause:** the Container Apps job ended without succeeding, or ran past the
timeout (one hour by default). The pipeline reads the run's status every 30
seconds. The last message means ADF could not stop the run: the factory's
identity may lack the **Container Apps Jobs Operator** role on the job.

**Fix:** open the job's run in Azure for the error. The job retries a failed run
when its retry limit is 1, as `ingestron request` asks, and running again is
safe because each run rebuilds everything.
Raise `after_copy.timeout` for a larger load. `ingestron request --env dev`
lists the job and the access it needs. See
[Run and operate](/docs/platforms/duckdb-in-azure#operate).

## Databricks

### A change mode needs a key or a sequence column

**Symptom:**

```text
flows/crm.yaml:9:5  error  METHOD_CHECK
  "streaming-table" for table "accounts": mode upsert needs "sequence_by".
```

or `mode upsert needs primary key columns in the contract`.

**Cause:** `history: latest` or `full`, which the method writes as
`mode: upsert` or `mode: history`, keeps a table current by key, in the order
of a column.

**Fix:** set `sequence` on the flow or the table to the column that orders a
key's changes, and mark the key columns `primaryKey: true` in the contract.
See [Keep a table current](/docs/how-to/keep-a-table-current).

### Databricks rejects the bundle

**Symptom:** `databricks bundle validate` or `deploy` fails.

**Check:** read Databricks' own message; Ingestron does not produce it. If a
schema is missing, the schemas are not created yet: ask the team that owns
them, or see
[Let the bundle create the schemas](/docs/platforms/databricks#create-the-schemas).
A Lakeflow Connect pipeline refers to a Unity Catalog connection, which
Ingestron does not create.

**Fix:** when the platform sets `databricks.manage.schemas`, an administrator runs the
generated `prerequisites/<environment>.sql` once before the first deploy: it grants
`USE CATALOG` and `CREATE SCHEMA` on each catalog to the identity the pipelines
run as, and the same must be given to the identity that deploys when it
differs. Run `ingestron request` for everything else the platform team
provides.

### The refresh job does not run in development

**Symptom:** the job and the pipelines are deployed, and nothing refreshes on
its schedule in `dev`.

**Cause:** schedules run only in `prod` and `production`
([platform defaults](/docs/reference/packs/databricks#platform-configuration)).
`dev` is in development mode, which pauses every schedule, and another
environment's target in `databricks.yml` sets
`presets: { trigger_pause_status: PAUSED }`.

**Fix:** unpause it in Databricks, or set `paused: false` in the platform's
`schedule` and generate again: the job then says `pause_status: UNPAUSED` in
every environment. See
[Refresh on a schedule](/docs/platforms/databricks#schedule).

Every code is explained in [Errors](/docs/reference/errors).
