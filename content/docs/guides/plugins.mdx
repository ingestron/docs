A provider decides where and how a flow runs. A connector reads a source.
The GitHub tutorial needs both `local` and `github`.

## Install a provider or connector

From the project directory, install `local` and the connectors your project uses.
CLI 0.15.0 supports these official names:

| Name         | Purpose                             |
| ------------ | ----------------------------------- |
| `local`      | Execute flows on your machine       |
| `files`      | Read local files                    |
| `github`     | Read GitHub issues                  |
| `azure-blob` | Read Azure Blob and ADLS Gen2 files |
| `sql-server` | Read SQL Server or Azure SQL tables |

For example:

```sh
ingestron provider install local
ingestron connector install files
```

On first install, an omitted version selects the latest release in the official
catalogue qualified for your CLI's core version. `github@latest` has the same
meaning. Ingestron then records an exact version, commit and file hashes in
`packages.lock.yaml`. It caches files under `.ingestron/packages`.

Official names do not need `--tag-prefix` or a repository path. Project and lock
files keep the full versioned reference so the selected package remains explicit
and portable. Use full references when installing custom packages.
The commands reject a package of the wrong type before changing the lock.

Installation does not edit `project.yaml`. The old `--cache-only` option is accepted
but unnecessary. Use the exact versions in a tutorial when reproducing its result:

```sh
ingestron connector install github@1.33.0
ingestron provider list
ingestron connector list
```

## Reuse or update a lock

```sh
ingestron connector install github --frozen
ingestron connector update github
```

`--frozen` requires an existing lock. A repeated normal installation also reuses
the highest stable version already locked for that name. It does not silently
check for an upgrade. `update` explicitly checks the catalogue and caches a newer
qualified version if available. It does not change a project's selected version
or replace an existing version's commit.

To adopt another version, update the exact reference in your project, check it,
and build and review again. Keep the previous configuration and lock in Git so
you can restore them. See [change a project](/docs/guides/update-project).

## Configure a provider

The GitHub example already includes provider configuration. For a project without
it, inspect the installed package and use its exact reference:

```sh
ingestron plugin configure ingestron/provider-local@0.4.1 --name local
```

This is a separate authoring step. Review its files and add any required connection
settings before building. The old `plugin install --name` spelling reports this
new step instead of registering a provider implicitly.

## Other repositories

Full references remain available for third-party packages and custom manifest paths:

```text
ingestron provider install owner/repository@1.2.3
ingestron connector install owner/repository/connector.yaml@1.2.3
```

`owner/repository` and `connector.yaml` are placeholders for your repository and
manifest path. A package must implement the matching provider or connector
contract. `plugin install` remains available for older scripts and other package
types. Custom repositories do not get official `@latest` resolution. Use
`plugin versions owner/repository` to inspect stable tags; tag availability alone
does not establish compatibility.
