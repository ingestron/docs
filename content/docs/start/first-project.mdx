---
title: Run your first project on your laptop
description: Create a project from the DuckDB starter, generate its SQL, and build two tables on your laptop. No cloud account, no source, nothing deployed.
---

In this tutorial you create a small project from YAML, let Ingestron write the
SQL for it, and run that SQL with DuckDB on your own machine. At the end you
have a DuckDB database with two tables, `bronze.orders` and
`silver.customer_totals`, each also published as a Parquet file. You need no
cloud account and no source, and nothing is deployed.

Start in any folder where you can create a new one, such as your home folder.

## Before you start

- **Node.js 22.13 or later.**
- **The [DuckDB command line](https://duckdb.org/docs/installation/).** The
  SQL Ingestron writes for DuckDB is tested with DuckDB <DuckdbTested />.

Install Ingestron from npm:

```sh
npm install -g ingestron
```

`ingestron --help` should then list its commands. If the shell says the
command is not found, see
[Troubleshooting](/docs/troubleshooting#ingestron-command-not-found). To use
VS Code instead, see [Install the command and the extension](/docs/start/install).

## 1. Create the project

<ToolSteps>
<Tool name="CLI">

```sh

cd shop
```

</Tool>
<Tool name="VS Code">

Create an empty folder named `shop`. Run **Ingestron: New project**, choose
**From a starter**, then **DuckDB on a laptop**. Keep the name `shop` and the
environment `dev`, leave the standard empty to keep the starter's own, and
select the `shop` folder. Open that folder in VS Code.

`init` copies the starter into `shop` and prints

remaining steps run in the `shop` folder.

## 2. Plan

<ToolSteps>
<Tool name="CLI">

```sh
ingestron plan
```

</Tool>
<Tool name="VS Code">

Run **Ingestron: Plan**. The output appears in the **Ingestron** output panel.

</Tool>
</ToolSteps>

You should see:

```text
duckdb → build/duckdb (dev)
create    dev/README.md
create    dev/run.sql
create    dev/tables/bronze.orders.sql
create    dev/tables/silver.customer_totals.sql

```

Each platform's files go to one folder, here `build/duckdb/`, with a folder
for each environment that DuckDB runs: `dev` is the project's one environment.
Plan writes nothing: it shows what `apply` would write.

## 4. Build the tables

Run DuckDB in the `shop` folder (in VS Code, open a terminal there):

```sh
duckdb -bail ingestron.duckdb -c ".read build/duckdb/dev/run.sql"
duckdb ingestron.duckdb -c "SELECT * FROM silver.customer_totals ORDER BY customer"
```

The first line runs the generated SQL and prints nothing when it succeeds. The
second shows the totals it built from the five sample orders:

```text
┌──────────┬────────┬────────┐
│ customer │ orders │ total  │
│ varchar  │ int64  │ double │
├──────────┼────────┼────────┤
│ Ana      │      2 │  65.75 │
│ Ben      │      2 │   42.0 │
│ Chen     │      1 │   8.75 │
└──────────┴────────┴────────┘
```

`run.sql` also published both tables as Parquet, which Power BI and other
tools read as files:

```sh
ls published
```

```text
bronze.orders.parquet  silver.customer_totals.parquet
```

`run.sql` builds both tables in one transaction, so if a statement fails,
neither table changes. `-bail` then stops DuckDB before it publishes anything.
If you pipe `run.sql` into DuckDB without `-bail`, it can go on to the `COPY`
statements and publish the tables as they were before the run. Running `run.sql` again is safe: it
rebuilds both tables and replaces both files. The project's `.gitignore` keeps
`ingestron.duckdb` and the Parquet files out of Git, because they are data
built from the files.

## 5. Read what you wrote

The project is a handful of short YAML files. `standard.yaml` chooses the
DuckDB pack, the part of Ingestron that writes DuckDB SQL, and says the source
files are CSV:

<Example name="duckdb" file="standard.yaml" />

`platform.yaml` says where this machine publishes each table:

<Example name="duckdb" file="platform.yaml" />

The connection is the source: a folder of files beside the project.

<Example name="duckdb" file="connections/shop.yaml" />

The flow reads `orders.csv` from that connection into the table `orders`,
described by a contract:

<Example name="duckdb" file="flows/orders.yaml" />

The contract is an [Open Data Contract Standard](https://bitol-io.github.io/open-data-contract-standard/)
file. It names the columns and their types, and those columns are what the
table gets:

<Example name="duckdb" file="contracts/orders.yaml" />

The transform builds `customer_totals` from `orders` with SQL. Its own
contract, `contracts/customer_totals.yaml`, types the result:

<Example name="duckdb" file="transforms/customer_totals.yaml" />

From those files Ingestron wrote `run.sql`. It is plain DuckDB SQL: every
column cast to its contract's type, both tables built in one transaction, and
published only once both are built. Nothing in it calls Ingestron.

<Example name="duckdb" file="build/duckdb/dev/run.sql" />

The [definition model](/docs/concepts/definitions) explains how the files link
to each other.

## Add a column

Add a `channel` column. First add this line at the end of
`contracts/orders.yaml`, under the other columns, with the same indentation:

{/* prettier-ignore */}
```yaml
      - { name: channel, logicalType: string }
```

Then replace `samples/orders.csv` with orders that have a channel:

```csv
order_id,customer,amount,ordered_at,channel
1,Ana,25.50,2026-10-01,web
2,Ben,12.00,2026-10-01,store
3,Ana,40.25,2026-10-02,web
4,Chen,8.75,2026-10-03,web
5,Ben,30.00,2026-10-03,store
```

Plan again:

```sh
ingestron plan
```

Plan shows each changed line: the `channel` column is read, cast and
published. A reviewer sees the same change in a pull request.

```sh

duckdb ingestron.duckdb -c "SELECT * FROM bronze.orders ORDER BY order_id"
```

## Break it on purpose

Two mistakes show how Ingestron protects your work.

### Edit a generated file

Add the line `-- my change` at the end of `build/duckdb/dev/run.sql`, save it, and
plan:

```sh
ingestron plan
```

```text
duckdb → build/duckdb (dev)
conflict  dev/run.sql
          Changed by hand since it was generated. Move the change into the definitions, or delete the file to generate it again.

4 files: 3 unchanged, 1 conflict. Resolve the conflicts before applying.
```

Plan exits with an error, and `apply` refuses in the same way, so your edit is
never overwritten. A change belongs in the definitions, where the next plan
shows it to a reviewer. To undo it, delete the file and apply:

```sh
rm build/duckdb/dev/run.sql
ingestron apply
```

```text
duckdb → build/duckdb (dev)
create    dev/run.sql

4 files: 1 create, 3 unchanged. Ready to apply.
Applied.
```

[Generated files and ownership](/docs/concepts/generated-files) explains how Ingestron
tracks what it wrote.

### Name a connection that does not exist

In `flows/orders.yaml`, change `source: shop` to `source: shops`, save it, and
plan:

```sh
ingestron plan
```

```text
dev: the definitions have problems
flows/orders.yaml:4:9  error  BROKEN_LINK
  "shops" is not the id of a Connection document.
  Known Connection ids: shop.
  Fix: Change to "shop".
```

Each problem names the file, line and column, the
[error code](/docs/reference/errors#BROKEN_LINK) and a fix, and nothing is
written. VS Code underlines the value as you type and offers
**Change to "shop"** as a quick fix. Change it back, and plan reports
`4 files: 4 unchanged. Up to date.`

## Clean up

Delete the `shop` folder. Nothing else was created: no account, no service and
no file outside the folder. Ingestron stays installed for your next project;
`npm uninstall -g ingestron` removes it.
