Start with the source you need to read and the result you want to keep. Choose
compatible capabilities for ingestion, any transformation, and storage. Your
editor is a separate choice; it does not determine the platform architecture.

## Make four decisions

1. **Source and access.** Choose a connector and declare its reachability.
   Check the connection page for authentication and runtime requirements.
2. **Ingestion.** Choose a method that supports that connector and reachability.
   Decide whether its copy or change-capture behaviour meets your needs.
3. **Destination and later processing.** Check which methods can store the
   ingestion result and whether you need transforms or quality checks.
4. **Standard.** Select one standard containing compatible packs and policy for
   all the required actions.

## What works in the current distribution

New project, in the CLI and VS Code, offers these routes for a source; `--via`
names them on the command line.

| Route (`--via`)                               | What it does                                                                                      | Packs            | Guide                                                   |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------- | ---------------- | ------------------------------------------------------- |
| Databricks directly (`databricks`)            | Reads supported sources into Databricks tables                                                    | Databricks       | [Databricks](/docs/how-to/databricks)                   |
| ADF ingestion into Databricks (`adf`)         | Copies sources to ADLS Gen2 landing storage, then reads the landed files into Databricks tables   | Databricks + ADF | [Azure Data Factory](/docs/how-to/adf)                  |
| ADF, served as Synapse views (`adf-synapse`)  | Lands each table as a file, and shows the files and transforms as Synapse serverless SQL views    | Synapse + ADF    | [Serve files as SQL](/docs/how-to/serve-files-as-sql)   |
| ADF into DuckDB tables (`adf-duckdb`)         | Lands each table as a file; DuckDB builds tables from them, runs transforms and publishes Parquet | DuckDB + ADF     | [Run DuckDB in Azure](/docs/how-to/run-duckdb-in-azure) |
| ADF, ending at the landed files (`adf-files`) | Copies sources to landing storage, for reports that read the files                                | ADF              | [Land files only](/docs/how-to/land-files-only)         |

Synapse and DuckDB are offered where ADF copies tables, not where it copies
files as they are; Synapse not for Microsoft 365, which lands JSON. To try
DuckDB on a laptop with no source at all, start from the **DuckDB on a laptop**
starter: [Run locally with DuckDB](/docs/how-to/run-locally-with-duckdb).

Selecting another provider name in YAML will not enable a destination no pack
implements. See the [pack catalogue](/docs/reference/packs) for the current
boundary.

`public`, `workspace` and `private` describe [reachability](/docs/concepts/connectivity).
They do not provision networking or test credentials. A standard can also reject
an otherwise supported method.

ADF can be selected for supported public and workspace sources as well as private
ones. In the combined route, Databricks reads the landing files; it does not run
a second direct connection to the original source.

## Create the selected project

Use [Create a project](/docs/how-to/start-from-a-template) for the available
interfaces. The builder writes an explicit ingestion choice into the definitions
and checks its standard. Generation and deployment remain separate steps.
