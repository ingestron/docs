Ingestron writes the files a data engineer would otherwise write by hand:
Databricks bundles and pipelines, Azure Data Factory pipelines, Synapse
serverless views and DuckDB SQL. You describe the sources, tables and rules in
YAML your team reviews. Ingestron applies your organisation's standard and
writes ordinary platform files, and you deploy them with your platform's own
tools. Nothing in them calls Ingestron; the one optional route that runs
something Ingestron publishes is [named below](#no-dependency-once-its-deployed).

## Run it on your laptop

You need Node.js 22.13 or later and the
[DuckDB command line](https://duckdb.org/docs/installation/); no cloud account
and no source. In a folder where you can create a new one:

```sh
npx ingestron@1 init shop --template duckdb --yes
cd shop
npx ingestron@1 plan
npx ingestron@1 apply
duckdb -bail ingestron.duckdb -c ".read build/dev/run.sql"
duckdb ingestron.duckdb -c "SELECT * FROM silver.customer_totals ORDER BY customer"
```

The last command shows a table that DuckDB built from sample orders, with SQL
that Ingestron generated:

```text
┌──────────┬────────┬────────┐
│ customer │ orders │ total  │
│ varchar  │ int64  │ double │
├──────────┼────────┼────────┤
│ Aroha    │      2 │  65.75 │
│ Ben      │      2 │   42.0 │
│ Chen     │      1 │   8.75 │
└──────────┴────────┴────────┘
```

[Run your first project on your laptop](/docs/start/first-project) explains
each step and each file, then changes the project and breaks it on purpose.

The bundle around it is YAML, Azure Data Factory gets pipeline JSON, and
Synapse gets view SQL. [How Ingestron works](/docs/start/how-it-works) follows
a project from the YAML to the platform.

### No dependency once it's deployed

The generated files need only your platform, so if you stop using Ingestron,
they still deploy and run, and you edit them yourself from then on. One
optional route uses something Ingestron publishes:
DuckDB in Azure runs in a public container image, which you can copy to your
own registry. [Generated files](/docs/concepts/generated-files) explains what
Ingestron writes and how it tracks it.

### Your standards on every project

The platform team writes one standard: the packs, names, layers, types,
default settings, settings no project may change, and what every data product
must declare. VS Code marks a break as you type, `ingestron plan` reports
every one, and `ingestron check` fails the CI build. See
[Configure the project standard](/docs/how-to/configure-a-standard).

### Reuse your team's work

Start a project from a template your team keeps in Git with
`ingestron init <name> --template <git url>`, and take the standard from a shared
repository with `--standard`. A template is a project folder and a standard is
one YAML file, so you can keep them in any Git repository your team, or anyone
else, can clone. The packs are open source under Apache-2.0. See
[Share a template](/docs/how-to/share-a-template).

## What Ingestron does not do

- It doesn't connect to your sources or your cloud. Its only network call is
  to fetch a template or standard from a Git URL you give it.
- It doesn't deploy anything. Your platform's tools do.
- It doesn't read secret values. A `${secret:…}` reference carries only the
  secret's name.
- It doesn't send telemetry, from the command line or from VS Code.
- It doesn't overwrite a file someone edited. It reports a conflict instead.
