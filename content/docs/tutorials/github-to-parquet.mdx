---
title: "Read GitHub issues into Parquet"
description: "Build, review and run a local snapshot of issue IDs and titles."
---

This tutorial reads a GitHub.com repository and writes `id` and `title` columns
to a local Parquet file. You choose the repository and review the projection before
extraction. The result is a full snapshot; this example does not keep an incremental cursor.

You need:

- [CLI 0.13.2, Git and Python 3.12](/docs/start/installation) on macOS or Linux.
- Internet access to GitHub.com. No account or token is needed for this public example.
- A local directory for the project, downloaded dependencies and output.

No cloud compute is created. The first runtime preparation downloads Python packages.
Live row counts change as issues and pull requests are added. GitHub permits
60 unauthenticated REST requests per hour per originating IP; other users on your
network share that allowance. Start with this small public repository.

## 1. Download the project

Create an empty directory:

```sh
mkdir github-project
cd github-project
```

Download the three example files:

```sh
curl --fail --location --output project.yaml https://docs.ingestron.io/examples/github/project.yaml
curl --fail --location --output .gitignore https://docs.ingestron.io/examples/github/gitignore.txt
curl --fail --location --output inspect-output.py https://docs.ingestron.io/examples/github/inspect-output.py
```

You can also save [project.yaml](/examples/github/project.yaml),
[gitignore.txt](/examples/github/gitignore.txt) (rename it to `.gitignore`) and
[inspect-output.py](/examples/github/inspect-output.py) using your browser.

## 2. Inspect the project

Open `project.yaml`. It selects the public `ingestron/cli` repository and
`authentication: anonymous`. Leave those values unchanged for your first run.
There is no `.env` file to create. To read another public repository later, change
`connections.github.settings.repositories` and use a fresh reviewed build.

The project selects the local provider, GitHub connector and an `issues_local`
flow. The contract at the bottom selects only `id` and `title`. The `sourceId` and
`tenantId` values label the output; they are not credentials. Keep them stable for
this exercise. See [project configuration](/docs/reference/project) for a field guide.

## 3. Install the two plugins

```sh
ingestron plugin install local@0.4.1
ingestron plugin install github@1.33.0
ingestron plugin list
```

These are short names for the published packages already selected in `project.yaml`.
Installation writes the package cache and `packages.lock.yaml`. It does not change
project configuration or start a flow. Commit the lock alongside your configuration.

## 4. Build and prepare

```sh
ingestron check
ingestron build
ingestron runtime prepare
```

`check` validates the project. `build` writes the files the provider needs under
`build/generated`, without reading GitHub. `runtime prepare` installs the locked
Python dependencies under `.ingestron/runtimes`. Running preparation again reuses
a matching environment.

If Python cannot be found, retry preparation with `--python` and the full path to
Python 3.12. Do not edit the generated runtime files to fix configuration; change
`project.yaml` and rebuild.

## 5. Discover and review

```sh
ingestron run --action discover
ingestron run --action review
```

Open `build/generated/flows/issues_local/review.json`. Check the source identity,
selected `issues` stream and projected `id`/`title` fields against your contract.
Discovery describes the supported schemas. Review uses that information locally;
extraction contacts the selected repository after approval.

Discovery includes the supporting repository schema, but the selected output stream
is `issues`. GitHub's issues endpoint can also include pull requests; the connector
does not remove those entries. See [connector behaviour](/docs/reference/github)
before treating the output as an issues-only business dataset.

## 6. Approve and run

When the review matches your intended source and fields:

```sh
ingestron run --action approve
ingestron run --run-id issues-001
ingestron run status issues-001
```

Expect a succeeded receipt and a row count. The count depends on the selected
repository; an empty repository may produce no rows. Extraction requires approval;
trying it before approval should fail without publishing output.

## 7. Inspect the result

```sh
python3 inspect-output.py
```

The helper uses the prepared Python environment to print the Parquet schema and
row count, without displaying titles. Expect `id` as int64 and `title` as string.
Compare the count with the receipt. The file is under:

```text
build/generated/data/issues_local/<identity-hash>/issues-001/issues.parquet
```

The adjacent `commit.json` describes the committed snapshot. The identity hash
separates the source and tenant labels; you do not need to choose it yourself.

## 8. Retry without another extraction

```sh
ingestron run --retry issues-001
```

For a completed, unchanged snapshot, retry verifies and reuses the output without
reading GitHub again. This completed retry needs no source access.
A new run ID requests a new extraction. Incomplete runs can need source access;
see [run and retry behaviour](/docs/guides/runs).

## If something goes wrong

For rate limits, wait before retrying or add an authorised token using the
[connector authentication guide](/docs/reference/github#use-a-token). A missing or
inaccessible repository fails the run; it is not treated as an empty dataset.
Never put a token in a command, project YAML or issue report.

If the project or generated files changed, rebuild and review before starting new
work. If a review already exists, use a fresh build directory as described in
[updating a project](/docs/guides/update-project). If committed output changed,
preserve it for investigation; do not edit the receipt to make verification pass.

Keep any Parquet and receipts you need before removing this disposable directory.
Deleting `.ingestron` also
removes the local runtime environments and run records.
