<Only on="synapse">

In this tutorial you create a Synapse project for one Azure SQL Database
table, and let Ingestron write what Synapse runs: a workspace pipeline that
copies the table into storage, and a serverless SQL view that reads the copy.
Everything happens on your computer. Ingestron never connects to the database
or to Azure, and nothing is deployed.

Start in any folder where you can create a new one, such as your home folder.

## Before you start

You need Node.js 22.13 or later. Install Ingestron from npm:

```sh
npm install -g ingestron
```

`ingestron --help` should then list its commands. If the shell says the
command is not found, see
[Troubleshooting](/docs/troubleshooting#ingestron-command-not-found). To use
VS Code instead, see [Install the command and the extension](/docs/~/install).

## 1. Create the project

<ToolSteps>
<Tool name="CLI">

```sh
ingestron init shop --platform synapse --set storage_account=stshoplanding --set key_vault=kv-shop --yes
cd shop
```

</Tool>
<Tool name="VS Code">

Create an empty folder named `shop`. Run **Ingestron: New project**, choose
**Azure Synapse**, then **A new standard for Azure Synapse**, and select the
`shop` folder. In `project.yaml`, write `stshoplanding` and `kv-shop` in place
of the two `REPLACE_ME` values in each environment.

</Tool>
</ToolSteps>

`storage_account` is the storage account the copies land in, and `key_vault`
the Key Vault that holds the database's password. Both names are made up;
write your own before you deploy. Ingestron prints:

```text
Created shop from synapse (5 files).
Platform and standard created. Review target settings, then add a connection and a flow.
```

`standard.yaml` says the Synapse pack copies each table in full once a day and
shows it as a view; `platform.yaml` holds the landing folder and the Key
Vault; `project.yaml` has two environments, `dev` and `prod`. `README.md`
lists what is left to do.

## 2. Add the database

```sh
ingestron connection add sales --connector azure-sql-database --connectivity public
```

`connections/sales.yaml` has `REPLACE_ME` for the server and the account that
reads it. Write them in:

```yaml title="connections/sales.yaml"
apiVersion: ingestron.io/v1
kind: Connection
id: sales
connector: azure-sql-database
connectivity: public
settings:
  server: sql-shop.database.windows.net
  user: reader
  password: ${secret:sales-password}
```

`${secret:sales-password}` names a secret in the Key Vault: the password
itself never goes in the project. In VS Code, **Ingestron: Add connection**
asks for the same values.

## 3. Add the table

```sh
ingestron flow add orders --connection sales --object sales.dbo.orders
```

`flows/orders.yaml` now copies `sales.dbo.orders` into a table named
`orders`. Ingestron also needs the table's columns. Save a few of its rows as
`samples/orders.csv`:

```csv title="samples/orders.csv"
order_id,customer,amount,ordered_at
1,acme,120.50,2026-11-02
2,globex,75.00,2026-11-03
```

Draft a contract from them:

```sh
ingestron contract samples/orders.csv --name orders
```

`contracts/orders.yaml` lists the four columns with the types the rows
suggest. Name it in the flow's last line:

```yaml title="flows/orders.yaml"
apiVersion: ingestron.io/v1
kind: Flow
id: orders
source: sales
ingest:
  uses: synapse-copy
tables:
  orders:
    object: sales.dbo.orders
    contract: orders
```

Without a contract, plan stops with `TABLE_NO_COLUMNS`. A table can take its
columns from the database's own description instead; see
[Describe a source](/docs/~/describe-a-source).

## 4. Plan

```sh
ingestron plan --no-diff
```

```text

create    environments/dev.sql
create    environments/prod.sql
create    queries/dev/pl_shop_sales/copy_orders.sql
create    queries/prod/pl_shop_sales/copy_orders.sql
create    views.sql
create    workspace/dev/dataset/ds_shop_landing.json
create    workspace/dev/dataset/ds_shop_sales_sales.json
create    workspace/dev/linkedService/ls_shop_keyvault.json
create    workspace/dev/linkedService/ls_shop_landing.json
create    workspace/dev/linkedService/ls_shop_sales_sales.json
create    workspace/dev/pipeline/pl_shop_sales.json
create    workspace/dev/trigger/tr_shop_sales.json
create    workspace/prod/dataset/ds_shop_landing.json
create    workspace/prod/dataset/ds_shop_sales_sales.json
create    workspace/prod/linkedService/ls_shop_keyvault.json
create    workspace/prod/linkedService/ls_shop_landing.json
create    workspace/prod/linkedService/ls_shop_sales_sales.json
create    workspace/prod/pipeline/pl_shop_sales.json
create    workspace/prod/trigger/tr_shop_sales.json

19 files: 19 create. Ready to apply.
```

Each environment gets its own pipeline, datasets, linked services and
stopped trigger under `workspace/<environment>/`, laid out as the workspace's
Git integration expects. `views.sql` is the same for both environments;
`environments/<environment>.sql` sets each one's database and runs it.

```sh
ingestron apply
```

Open the `shop` folder in [VS Code](/docs/tools/vscode) and the Explorer shows the
files you wrote. In a flow, **Generated files (N)** above each table lists
the files generated for it, and its full name follows it:

<Screenshot

  dark="/images/vscode/first-project-synapse-dark.png"

/>

The view reads the Parquet file the pipeline copies, with each column's type
from the contract:

```sql title="build/synapse/views.sql"
-- Generated by Ingestron for shop: Synapse serverless SQL views. Do not edit.
-- It switches to each view's database and creates or alters each view, so it can run again.

USE [$(database)];
GO

IF SCHEMA_ID(N'bronze') IS NULL EXEC(N'CREATE SCHEMA [bronze]');
GO
CREATE OR ALTER VIEW [bronze].[orders] AS
SELECT *
FROM OPENROWSET(
  BULK 'shop/sales.dbo.orders/sales.dbo.orders.parquet',
  DATA_SOURCE = 'landing',
  FORMAT = 'PARQUET'
) WITH (
  [order_id] BIGINT,
  [customer] VARCHAR(8000) COLLATE Latin1_General_100_BIN2_UTF8,
  [amount] FLOAT,
  [ordered_at] DATE
) AS [rows];
GO
```

The query the pipeline sends to the database is beside it, to review:

```sql title="build/synapse/queries/dev/pl_shop_sales/copy_orders.sql"
-- Source query embedded in workspace/dev/pipeline/pl_shop_sales.json. Review only.
SELECT
  [order_id],
  [customer],
  [amount],
  [ordered_at]
FROM [dbo].[orders];
```

`ingestron check` now prints `synapse: up to date`. Run it in CI, and a pull
request fails whenever the committed files are not what the definitions
generate; see [Check generated files in CI](/docs/~/check-in-ci).

## 6. See what Azure needs

```sh
ingestron request --env prod
```

prints what must exist in Azure before the files can run, as Markdown to send
to whoever manages the workspace. It starts:

```text

- `synapse-copy` `landing`: `abfss://landing@stshoplanding.dfs.core.windows.net/shop`
- `synapse-copy` `key_vault`: `https://kv-shop.vault.azure.net`
- `synapse-copy` `integration_runtime`: `AutoResolveIntegrationRuntime`
- `synapse-copy` `runtime_kind`: `azure`
- `synapse-copy` `paused`: `true`
- `synapse-view` `data_source`: `landing`
- `synapse-view` `data_source_location`: `abfss://landing@stshoplanding.dfs.core.windows.net`

## Synapse serverless database

- Create the serverless SQL database `shop_prod`; the views live in it.
```

and goes on to the external data source, the report users' permissions and
the workspace's access to storage and the Key Vault; see
[Ask the platform team](/docs/~/ask-the-platform-team).

## Clean up

Delete the `shop` folder. Nothing else was created. Ingestron stays installed
for your next project; `npm uninstall -g ingestron` removes it.

<Only on="databricks">

In this tutorial you create a small Databricks project from the **Minimal**
starter, and let Ingestron write the bundle Databricks deploys: a pipeline
that reads order files from a Unity Catalog volume into a streaming table.
Everything happens on your computer. Ingestron never connects to Databricks,
and nothing is deployed.

Start in any folder where you can create a new one, such as your home folder.

## Before you start

You need Node.js 22.13 or later. Install Ingestron from npm:

```sh
npm install -g ingestron
```

`ingestron --help` should then list its commands. If the shell says the
command is not found, see
[Troubleshooting](/docs/troubleshooting#ingestron-command-not-found). To use
VS Code instead, see [Install the command and the extension](/docs/~/install).

## 1. Create the project

<ToolSteps>
<Tool name="CLI">

```sh
ingestron init shop --template minimal --set landing=/Volumes/main/landing/shop --yes
cd shop
```

</Tool>
<Tool name="VS Code">

Create an empty folder named `shop`. Run **Ingestron: New project**, choose
**Try a sample project**, then **Minimal project**, and select the `shop`
folder. In `project.yaml`, write `/Volumes/main/landing/shop` in place of
`REPLACE_ME`.

</Tool>
</ToolSteps>

`landing` is the Unity Catalog volume the order files arrive in; write your
own before you deploy. Ingestron creates the project and plans it at once:

```text
Created shop from the template minimal (7 files).
databricks → shop/build/databricks (dev)
create    databricks.yml
create    resources/shop.pipeline.yml
create    src/shop/bronze/orders.sql

3 files: 3 create. Ready to apply.
Nothing to replace: the project runs as written.
```

## 2. Read the definitions

`standard.yaml` names the Databricks pack, and everything it does not say
comes from the pack's defaults. The connection says where the files are:

```yaml title="connections/shop.yaml" kind="plain"
apiVersion: ingestron.io/v1
kind: Connection
id: shop
connector: files
connectivity: public
settings:
  path: ${values.landing}
```

The flow reads the `orders` folder into a table, with the columns its
contract lists:

```yaml title="flows/orders.yaml" kind="plain"
apiVersion: ingestron.io/v1
kind: Flow
id: orders
source: shop
tables:
  orders: { object: orders, contract: shop.orders }
```

```yaml title="contracts/orders.yaml" kind="plain"
apiVersion: v3.1.0
kind: DataContract
id: shop.orders
version: 1.0.0
status: active
schema:
  - name: orders
    logicalType: object
    description: One row per order.
    properties:
      - { name: id, logicalType: integer, required: true, primaryKey: true }
      - { name: customer_id, logicalType: integer }
      - { name: total, logicalType: number, physicalType: "DECIMAL(18,2)" }
      - { name: ordered_at, logicalType: timestamp }
```

## 3. Apply and read what you wrote

```sh
ingestron apply
```

Open the `shop` folder in [VS Code](/docs/tools/vscode) and the Explorer shows the
files you wrote. In a flow, **Generated files (N)** above each table lists
the files generated for it, and its full name follows it:

<Screenshot
  light="/images/vscode/first-project-databricks-light.png"
  dark="/images/vscode/first-project-databricks-dark.png"
  alt="The Explorer lists the shop project, with build/databricks open: resources, src, .generated.json and databricks.yml, then the project's folders and files. Beside it, flows/orders.yaml; above the orders table, Generated files (1), and after it, → dev.bronze.orders."
  caption="The shop project after apply: the bundle under build/databricks, and the orders table labelled with its file and its name in dev."
/>

The table reads each new file once, casts the columns to the contract's
types, and checks that `id` is never empty:

```sql title="build/databricks/src/shop/bronze/orders.sql"
-- Generated by Ingestron from flows/orders.yaml (table orders). Do not edit: change the definitions and generate again.
CREATE OR REFRESH STREAMING TABLE `bronze`.`orders` (
  CONSTRAINT `id_not_null` EXPECT (`id` IS NOT NULL)
)
COMMENT 'One row per order.'
CLUSTER BY AUTO
AS SELECT
  *
FROM STREAM read_files(
  '/Volumes/main/landing/shop/orders',
  format => 'parquet',
  schemaHints => '`id` BIGINT, `customer_id` BIGINT, `total` DECIMAL(18,2), `ordered_at` TIMESTAMP',
  schemaEvolutionMode => 'addNewColumns'
);
```

`databricks.yml` makes the folder one bundle, with a `dev` target, and
`resources/shop.pipeline.yml` the serverless pipeline that runs the SQL in the
`dev` catalog. `ingestron check` now prints `databricks: up to date`. Run it
in CI, and a pull request fails whenever the committed files are not what the
definitions generate; see [Check generated files in CI](/docs/~/check-in-ci).

## 4. Build the tables

Run DuckDB in the `shop` folder (in VS Code, open a terminal there):

```sh
duckdb -bail ingestron.duckdb -c ".read build/duckdb/dev/run.sql"
duckdb ingestron.duckdb -c "SELECT * FROM silver.customer_totals ORDER BY customer"
```

The first line runs the generated SQL and prints nothing when it succeeds. The
second shows the totals it built from the five sample orders:

```text
┌──────────┬────────┬────────┐
│ customer │ orders │ total  │
│ varchar  │ int64  │ double │
├──────────┼────────┼────────┤
│ Ana      │      2 │  65.75 │
│ Ben      │      2 │   42.0 │
│ Chen     │      1 │   8.75 │
└──────────┴────────┴────────┘
```

`run.sql` also published both tables as Parquet, which Power BI and other
tools read as files:

```sh
ls published
```

```text
bronze.orders.parquet  silver.customer_totals.parquet
```

`run.sql` builds both tables in one transaction, so if a statement fails,
neither table changes. `-bail` then stops DuckDB before it publishes anything.
If you pipe `run.sql` into DuckDB without `-bail`, it can go on to the `COPY`
statements and publish the tables as they were before the run. Running `run.sql` again is safe: it
rebuilds both tables and replaces both files. The project's `.gitignore` keeps
`ingestron.duckdb` and the Parquet files out of Git, because they are data
built from the files.

## Break it on purpose

Two mistakes show how Ingestron protects your work.

### Edit a generated file

Add the line `-- my change` at the end of `build/duckdb/dev/run.sql`, save it, and
plan:

```sh
ingestron plan
```

```text
Not applied on this platform
dev:
contracts/orders.yaml:11:59  warning  NOT_APPLIED
  The notNull rule isn't applied on duckdb: it is applied only in a layer whose does lists check.
  Add `check` to the layer's `does` to apply it here.
duckdb → build/duckdb (dev)
conflict  dev/run.sql
          Changed by hand since it was generated. Move the change into the definitions, or delete the file to generate it again.

4 files: 3 unchanged, 1 conflict. Resolve the conflicts before applying.
```

Plan exits with an error, and `apply` refuses in the same way, so your edit is
never overwritten. A change belongs in the definitions, where the next plan
shows it to a reviewer. To undo it, delete the file and apply:

```sh
rm build/duckdb/dev/run.sql
ingestron apply
```

```text
Not applied on this platform
dev:
contracts/orders.yaml:11:59  warning  NOT_APPLIED
  The notNull rule isn't applied on duckdb: it is applied only in a layer whose does lists check.
  Add `check` to the layer's `does` to apply it here.
duckdb → build/duckdb (dev)
create    dev/run.sql

4 files: 1 create, 3 unchanged. Ready to apply.
Applied.
```

[Generated files and ownership](/docs/concepts/generated-files) explains how Ingestron
tracks what it wrote.

### Name a connection that does not exist

In `flows/orders.yaml`, change `source: shop` to `source: shops`, save it, and
plan:

```sh
ingestron plan
```

```text
dev: the definitions have problems
flows/orders.yaml:4:9  error  BROKEN_LINK
  "shops" is not the id of a Connection document.
  Known Connection ids: shop.
  Fix: Change to "shop".
```

Each problem names the file, line and column, the
[error code](/docs/reference/errors#BROKEN_LINK) and a fix, and nothing is
written. VS Code underlines the value as you type and offers
**Change to "shop"** as a quick fix. Change it back, and plan reports
`4 files: 4 unchanged. Up to date.`
