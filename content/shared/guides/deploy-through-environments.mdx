Ingestron writes one set of files per platform for every environment, as
[Where the files go](/docs/concepts/generated-files#where-the-files-go) shows.
A deployment pipeline deploys the same commit to each environment in turn, so
prod runs the files that test ran. The templates on this page do that: they
check the generated files, build what needs building once, then deploy to
`dev`, `test` and `prod`, each stage waiting for the one before and for
approval.

<FlowDiagram
  title="One commit, promoted"
  steps={[
    { title: "Check", detail: "ingestron check: the committed files are current" },
    { title: "Build", detail: "The files every stage deploys, packed once" },
    { title: "dev", detail: "Deployed straight away" },
    { title: "test", detail: "After approval" },
    { title: "prod", detail: "After approval, from main only" },
  ]}
/>

The deploy stages never install Ingestron: they run each platform's own
tools on the committed files. Ingestron runs only in the check, and on the
computers where you change the definitions.

## What each stage runs [#what-each-stage-runs]

Each environment's stage signs in as that environment's identity, then runs a
block for each platform. Delete the blocks of the platforms your project does
not use:

<Only on="synapse">

- **Synapse:** `sqlcmd -i environments/<environment>.sql`, in `build/synapse`;
  see [Deploy](/docs/synapse/deploy#deploy). The templates run the views
  script only: the workspace pipelines of `--via synapse` go through your
  workspace's own publishing process, as Deploy says.

</Only>

<Only on="databricks">

- **Databricks:** `databricks bundle validate` and `deploy -t <environment>`,
  in `build/databricks`; see [Deploy](/docs/databricks/deploy#deploy).

</Only>

<Only on="adf">

- **Azure Data Factory:** the pre-deployment script, an incremental ARM
  deployment with `build/adf/parameters/<environment>.json`, and the
  post-deployment script; see [Deploy the factory](/docs/adf/deploy#deploy).

</Only>

The templates also hold the steps of platforms your project may not use,
including a step in the build stage that builds a template: delete those.

The tools are pinned, each download checked by its SHA-256 where the template
downloads it:<Only on="databricks"> the Databricks CLI v1.23.0.</Only><Only on="synapse"> sqlcmd (Go) v1.10.0.</Only><Only on="adf">
Microsoft's `@microsoft/azure-data-factory-utilities` 1.0.3 for the factory.</Only>
Each GitHub action is
pinned to a full commit, with its version beside it, and the check installs an
exact Ingestron, `ingestron@2.5.0`: change them when you upgrade.<Only on="adf"> The
factory's build fetches its build tool from `adf.azure.com`, so the build stage
needs network access there.</Only>

## GitHub Actions [#github-actions]

Copy
[`deploy.yml`](https://github.com/ingestron/docs/blob/main/ci-templates/github-actions/deploy.yml)
and
[`deploy-environment.yml`](https://github.com/ingestron/docs/blob/main/ci-templates/github-actions/deploy-environment.yml)
to `.github/workflows/` in your definitions repository. `deploy.yml` runs on
each push to `main`: it checks, builds once, and calls
`deploy-environment.yml` for each environment in turn:

<Template file="github-actions/deploy.yml" from="  dev:" to="      environment: prod" />

`deploy-environment.yml` runs in the GitHub environment of the same name, one
deployment at a time, signed in with OpenID Connect, so no secret holds a
password:

<Template
  file="github-actions/deploy-environment.yml"
  from="  deploy:"
  to="          enable-AzPSSession: true"
/>

Set up once, in the repository's settings:

1. **Environments** named `dev`, `test` and `prod`. Give `test` and `prod`
   required reviewers, and let only the `main` branch deploy to `prod`. A
   stage waits until a reviewer approves it. On GitHub Free, Pro and Team,
   required reviewers work only in public repositories; a private repository
   needs GitHub Enterprise for them, see
   [deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)
   (checked 5 November 2026). Without them, the stages are not gated: every
   push to `main` deploys to `test` and `prod` once `dev` succeeds. The branch
   rule still keeps every other branch out of `prod`.
2. **An Azure identity for each environment,** with a federated credential
   for the job's subject and the roles its steps need on that environment's
   resources. A repository created, renamed or transferred before 15 July 2026
   has the subject `repo:<owner>/<repository>:environment:<environment>`; one
   created, renamed or transferred since, or opted in, has
   `repo:<owner>@<owner id>/<repository>@<repository id>:environment:<environment>`,
   with the IDs that `gh api repos/<owner>/<repository>` gives as `owner.id`
   and `id`. GitHub's
   [OpenID Connect guide](https://docs.github.com/en/actions/concepts/security/openid-connect)
   says which your repository uses.
3. **Each environment's variables,** which the file lists at its top:
   `AZURE_CLIENT_ID`, `AZURE_TENANT_ID` and `AZURE_SUBSCRIPTION_ID`, the
   identity the environment deploys as, and<Only on="databricks">
   `DATABRICKS_CLIENT_ID`, the service principal the bundle deploys as.</Only><Only on="synapse">
   `SYNAPSE_SERVER`, `<workspace>-ondemand.sql.azuresynapse.net`.</Only><Only on="adf">
   `ADF_RESOURCE_GROUP` and `ADF_FACTORY_NAME`, the environment's factory.</Only>

<Only on="adf">

4. **The repository variable `ADF_DEV_FACTORY_ID`,** the development factory's
   resource ID, which names the template's resources.

</Only>

<Only on="databricks">

Then create **a Databricks service principal for each environment**, with a
federation policy for the same subject; see
[GitHub Actions workload identity federation](https://docs.databricks.com/aws/en/dev-tools/auth/provider-github)
(checked 5 November 2026).

</Only>

## Azure DevOps [#azure-devops]

Copy
[`azure-pipelines.yml`](https://github.com/ingestron/docs/blob/main/ci-templates/azure-devops/azure-pipelines.yml)
and
[`templates/deploy-environment.yml`](https://github.com/ingestron/docs/blob/main/ci-templates/azure-devops/templates/deploy-environment.yml)
to your definitions repository, and add `azure-pipelines.yml` as a pipeline.
Its `Build` stage checks and builds once, then a stage for each environment
deploys, each after the one before:

<Template
  file="azure-devops/azure-pipelines.yml"
  from="  - template:"
  to="dependsOn: Deploy_test"
/>

Each stage's deployment job targets the Azure DevOps environment of the same
name, so that environment's approvals and checks gate it:

<Template
  file="azure-devops/templates/deploy-environment.yml"
  from="  - stage: Deploy_"
  to="                  artifact: deploy"
/>

Set up once, in the project's settings:

1. **Environments** named `dev`, `test` and `prod`. Add approvals to `test`
   and `prod`, a branch control check to `prod` that allows only `main`, and an
   exclusive lock check to each. With the lock, and the stage's
   `lockBehavior: sequential`, runs deploy an environment one at a time, in the
   order they started; see
   [exclusive lock](https://learn.microsoft.com/en-us/azure/devops/pipelines/process/approvals#exclusive-lock)
   (checked 5 November 2026).
2. **An Azure Resource Manager service connection for each environment,**
   named `ingestron-dev`, `ingestron-test` and `ingestron-prod`, using workload
   identity federation, with the roles its steps need on that environment's
   resources.
3. **A variable group for each environment,** named `ingestron-<environment>`,
   with the variables the template lists at its top.

<Only on="adf">

4. **The pipeline variable `ADF_DEV_FACTORY_ID`,** the development factory's
   resource ID.

</Only>

<Only on="databricks">

The Databricks step signs in as the service connection's identity, through
the Azure CLI with `useGlobalConfig`, which `databricks bundle` needs, so add
it to each workspace too.

</Only>

<Only on="synapse">

The sqlcmd step signs in as the service connection's identity, through the
Azure CLI with `useGlobalConfig`, so make it a user of each environment's
serverless database too.

</Only>

<Only on="adf">

The template deploys the factory with `AzurePowerShell@5`, in PowerShell 7,
and `AzureResourceManagerTemplateDeployment@3` in incremental mode, as
[Deploy the factory](/docs/adf/deploy#build-and-deploy) explains.

</Only>

## Values supplied when deploying [#values-supplied-when-deploying]

A value written as `${envvar:NAME}` is supplied by the deploying stage, not
read when generating; see
[Supplied when deploying](/docs/concepts/yaml-references#supplied-when-deploying).
`ingestron request --env <environment>` lists each one under **Values to
provide**, with the name to set; see
[Ask the platform team](/docs/~/ask-the-platform-team#values-to-provide).
Set each name in each environment's variables, or as a secret, and pass it
where the template's comments say:

<Only on="databricks">

- **Databricks:** a line under the bundle step's `env`, such as
  `BUNDLE_VAR_landing_path`. A host supplied this way is `DATABRICKS_HOST`.

</Only>

<Only on="adf">

- **Data Factory:** `name=value` after `factoryName` in the deployment
  (GitHub Actions), or `-name value` in `overrideParameters` (Azure DevOps),
  for each ARM parameter the request names.

</Only>

<Only on="synapse">

- **Synapse:** a line under the sqlcmd step's `env`, named exactly as the
  request gives it, in the same case. Azure DevOps passes a secret to a step
  only through its `env`.

</Only>

A stage that leaves one out fails:<Only on="adf"> ARM refuses a parameter with no value.</Only><Only on="databricks">
the bundle has no value for the variable.</Only><Only on="synapse"> the
views script stops before any view.</Only>

## Add an environment [#add-an-environment]

1. Add it to `project.yaml`, apply and commit, as in
   [Add an environment](/docs/~/add-an-environment).
2. Create its GitHub or Azure DevOps environment, its identity, its variables
   and, in Azure DevOps, its service connection and variable group.
3. Add a stage for it, after the stage it follows: in `deploy.yml`, a job that
   calls `deploy-environment.yml` with its name and `needs` the job before; in
   `azure-pipelines.yml`, a `template` entry with its name, its service
   connection and `dependsOn` the stage before.

What each environment deploys to must exist before its first deployment;
`ingestron request --env <environment>` lists it.

## Limits [#limits]

<Only on="adf">

- **One factory per project and environment;** see
  [One factory per project](/docs/adf/deploy#one-factory-per-project).

</Only>

- **To roll back,** deploy an earlier commit through the same stages.
- **What has been tried.** Tests check that each template parses, orders its
  stages dev, test, prod, and names the pinned versions above. The
  templates have not yet run against a live platform.

<Only on="databricks">

On Databricks, also:

- **One identity per environment.** A target deployed by another identity,
  without a shared `root_path`, gets a second copy of every pipeline and job;
  see [Deploy as one identity](/docs/databricks/deploy#one-identity).
- **A deploy that would delete a resource stops**, such as a managed schema;
  the templates do not approve it. Review it, then deploy from your computer,
  or add `--auto-approve` to that one run.

</Only>
