The new environment gets no folder of its own. It joins the files the bundle
already has: a `test` target in `databricks.yml`, with the values that differ
between environments:

<Example name="environments" file="build/databricks/databricks.yml" pick="targets.test" />

Only an environment named `dev` is in development mode; every other one,
`test` included, is in production mode. A platform can set `databricks.mode`
itself; see the
[platform defaults](/docs/reference/packs/databricks#platform-configuration).

</Only>

<Only on="synapse">

The new environment gets its own script, `environments/test.sql`, beside the
others, and on the workspace route its own `workspace/test/` folder; `views.sql`
is shared by every environment.

</Only>

<Only on="adf">

The new environment gets its own parameter file, `parameters/test.json`; the
factory is shared by every environment.

</Only>

<Only on="duckdb">

The new environment gets its own folder, `build/duckdb/test/`, with its
`run.sql` and tables.

</Only>

See [Where the files go](/docs/concepts/generated-files#where-the-files-go).

<Only on="databricks adf duckdb">

Schedules run only in an environment named `prod` or `production`, so
`test`'s schedules are paused; a platform can set `schedule.paused` itself.

</Only>

<Only on="synapse">

The workspace route's triggers stay stopped in every environment while
`platform.yaml` sets `paused: true`, as a new Synapse project does; start each
in the workspace when you approve it.

</Only>
Environments may differ only in values, such as names, paths and hosts: a table
built in one environment only is refused as
[`ENVIRONMENTS_DIFFER`](/docs/reference/errors#ENVIRONMENTS_DIFFER).

To deploy the new environment, add it to your deployment pipeline as
[Deploy through environments](/docs/~/deploy-through-environments#add-an-environment)
shows.

`compare` resolves both environments first, with every value and default in
place, and lists only what differs:

- **Platform:** the platform document's values, and the defaults that follow
  from the environment, such as `mode`.<Only on="databricks"> The values of a pack's own section,
  such as `databricks:` in the example, show twice: as the pack reads them, such as
  `workspace.root_path`, and as written, under `sections.databricks`. Compared with `prod`, it also shows
  `schedule.paused`, because only `prod` runs its schedule.</Only>
- **Names:** the pipeline and job names, which are not per table.
- **Table:** one section for each table that differs: its full name, each
  step's method and settings, the connection's settings and the table's
  checks.

A value one environment has and the other lacks shows as `not set`. A
`${secret:…}` reference shows as `a secret`, never its value. Without `--env`,
`compare` takes the first two environments in `project.yaml`. The output is
Markdown, so you can paste it into a pull request. When either environment has
problems, it lists them instead and exits with `1`.

In VS Code, run **Ingestron: Compare environments**. With more than two
environments it asks which two.
